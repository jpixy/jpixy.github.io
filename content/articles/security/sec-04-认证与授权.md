## 认证与授权的区别

### 认证（Authentication）

回答"你是谁"的问题。验证用户或系统的身份。

### 授权（Authorization）

回答"你能做什么"的问题。确定已认证的主体可以访问哪些资源。

认证是授权的前提。必须先知道你是谁，才能决定你能做什么。

---

## 身份认证方式

### 基于知识的认证

用户知道的东西：密码、PIN、安全问题。

**密码**是最常见的认证方式，但也是最容易被攻破的。密码面临的威胁包括：弱密码、密码复用、钓鱼、暴力破解、凭证填充（Credential Stuffing）。

**密码最佳实践**：
- 最小长度12字符
- 允许长密码（至少64字符）
- 不限制字符类型
- 不定期强制更换
- 检查常见密码和已泄露密码
- 使用密码管理器

### 基于拥有的认证

用户拥有的东西：手机、硬件Token、智能卡。

**OTP（一次性密码）**：TOTP（基于时间）和HOTP（基于计数器）。Google Authenticator、Authy等应用实现。

**硬件Token**：YubiKey、RSA Token。更安全但成本更高。

**短信验证码**：方便但不安全，易受SIM交换攻击。不推荐作为唯一第二因素。

### 基于生物特征的认证

用户本身的特征：指纹、面部、虹膜、声纹。

**优点**：方便，无法忘记或丢失。

**缺点**：一旦泄露无法更换，存在隐私问题，可能被欺骗（如照片解锁）。

生物特征应作为多因素之一，而非唯一认证方式。

### 多因素认证（MFA）

结合两种或更多不同类型的认证因素。即使一个因素被攻破，其他因素仍提供保护。

**WebAuthn/FIDO2**：无密码认证标准。使用公钥密码学，抵抗钓鱼。浏览器和操作系统广泛支持。是未来的方向。

## OAuth 2.0

### 解决的问题

用户想让第三方应用访问其在某服务上的数据，但不想把密码给第三方。

OAuth 2.0是授权框架，让用户授权第三方应用访问其资源，而无需暴露凭证。

### 角色

**资源所有者**：用户

**客户端**：第三方应用

**授权服务器**：颁发令牌

**资源服务器**：持有用户资源，接受令牌访问

### 授权码流程

1. 用户访问客户端，客户端重定向到授权服务器
2. 用户在授权服务器登录并同意授权
3. 授权服务器重定向回客户端，携带授权码
4. 客户端用授权码向授权服务器换取访问令牌
5. 客户端用访问令牌访问资源服务器

授权码流程最安全，因为令牌不经过浏览器。

### 其他流程

**隐式流程**：令牌直接返回给浏览器。不安全，已不推荐。

**客户端凭证流程**：机器对机器通信，无用户参与。

**资源所有者密码流程**：用户直接提供密码。仅适用于高度信任的客户端。

### PKCE

Proof Key for Code Exchange。增强授权码流程的安全性。

客户端生成code_verifier，发送其哈希（code_challenge）。换取令牌时提供code_verifier。防止授权码被截获后使用。

公共客户端（如移动应用、SPA）必须使用PKCE。

## OpenID Connect

OAuth 2.0只是授权框架，不处理认证。OpenID Connect在OAuth 2.0之上增加了身份层。

### ID Token

JWT格式的令牌，包含用户身份信息（如用户ID、邮箱、姓名）。

### UserInfo端点

客户端可以用访问令牌调用UserInfo端点获取更多用户信息。

### 用途

单点登录（SSO）、联合身份、社交登录（"使用Google登录"）。

---

## JWT（JSON Web Token）

### 结构

JWT由三部分组成：Header.Payload.Signature

**Header**：算法和令牌类型

**Payload**：声明（Claims），包含用户信息和元数据

**Signature**：对Header和Payload的签名

### 常用声明

- iss：签发者
- sub：主题（通常是用户ID）
- aud：受众
- exp：过期时间
- iat：签发时间
- jti：令牌ID

### 安全注意事项

**必须验证签名**：不验证签名等于不验证。

**检查算法**：算法应在服务端白名单中，不信任Header中指定的算法。曾有攻击者将算法改为"none"绕过验证。

**短过期时间**：JWT签发后无法撤销，应使用短过期时间。需要撤销时使用刷新令牌或黑名单。

**不存储敏感信息**：Payload只是Base64编码，不是加密。任何人都能读取。

**选择合适的算法**：对称（HS256）适合单一服务，非对称（RS256、ES256）适合微服务和第三方验证。

## 授权模型

### RBAC（基于角色的访问控制）

用户被分配角色，角色拥有权限。

用户 → 角色 → 权限

**优点**：概念简单，易于管理。

**适用场景**：角色划分清晰的系统。

### ABAC（基于属性的访问控制）

基于主体属性、资源属性、环境属性和操作属性做决策。

例如：用户部门=销售 AND 资源类型=销售报告 AND 当前时间=工作时间 → 允许访问

**优点**：细粒度控制，灵活。

**缺点**：策略复杂，难以审计。

### ReBAC（基于关系的访问控制）

基于实体间的关系做决策。

例如：用户是文档的创建者 → 可以编辑。用户是文件夹的成员 → 可以访问文件夹内的文件。

**优点**：直观地表达复杂的共享关系。

**代表**：Google Zanzibar（Google Drive、YouTube等使用）。

## 零信任架构

### 核心原则

**永不信任，始终验证**

传统模型信任内网，不信任外网。零信任认为没有可信的网络位置，所有访问都需要验证。

### 关键要素

**身份认证**：每次访问都需要认证。使用强认证和MFA。

**设备验证**：检查设备的安全状态，如是否安装补丁、是否有杀毒软件。

**最小权限**：只授予完成任务所需的最小权限，权限应是短暂的。

**微分段**：网络细粒度划分，每个服务独立保护。

**持续监控**：持续评估风险，动态调整访问权限。

### 实施

**BeyondCorp**：Google的零信任实现。

**SDP（软件定义边界）**：基于身份的网络访问控制。

零信任不是产品，而是架构理念，需要逐步实施。

## 总结

| 场景 | 推荐方案 |
|------|----------|
| 用户认证 | MFA + WebAuthn |
| 第三方授权 | OAuth 2.0 + PKCE |
| 单点登录 | OpenID Connect |
| API认证 | JWT + 短过期 |
| 权限管理 | RBAC（简单）/ ABAC（复杂） |
| 安全架构 | 零信任 |

认证和授权是安全的核心，需要根据场景选择合适的方案。
