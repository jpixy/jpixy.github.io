## 密码学概述

### 核心目标

密码学解决四个核心问题：

**机密性**：确保只有授权方能读取信息。通过加密实现。

**完整性**：确保信息未被篡改。通过哈希和MAC实现。

**认证**：确认通信方的身份。通过数字签名和证书实现。

**不可否认性**：发送方不能否认发送过信息。通过数字签名实现。

### 柯克霍夫原则

密码系统的安全性应仅依赖于密钥的保密性，而非算法的保密性。这意味着即使攻击者了解加密算法，只要不知道密钥，系统仍应安全。

现代密码学算法（AES、RSA等）都是公开的，经过全球密码学家的审查，比私有算法更可信。

## 对称加密

### 原理

加密和解密使用同一把密钥。发送方用密钥加密明文得到密文，接收方用相同密钥解密密文得到明文。

### 主要算法

**AES（高级加密标准）**

当前最广泛使用的对称加密算法。支持128、192、256位密钥长度。AES-256被认为可以抵抗可预见的计算攻击，包括量子计算。

**ChaCha20**

由Daniel Bernstein设计的流密码。在移动设备上比AES更快（无AES硬件加速时）。Google在TLS中推广使用ChaCha20-Poly1305。

**3DES**

对DES的三重应用，已被AES取代。仍存在于遗留系统中，但不推荐新系统使用。

### 加密模式

分组密码（如AES）需要加密模式来处理任意长度的数据：

**ECB（电子密码本）**：每个块独立加密。相同明文块产生相同密文块，不安全，不应使用。

**CBC（密码块链接）**：每个块与前一个密文块异或后再加密。需要随机IV。曾是主流，但易受padding oracle攻击。

**CTR（计数器模式）**：将分组密码变为流密码。可并行加密，无padding问题。

**GCM（伽罗瓦/计数器模式）**：CTR加密 + 认证标签。提供加密和完整性保护（AEAD）。现代系统的首选。

### 密钥管理

对称加密最大的挑战是密钥分发：如何安全地让双方共享同一密钥？这引出了非对称加密和密钥交换协议。

## 非对称加密

### 原理

使用一对密钥：公钥和私钥。公钥可以公开，私钥必须保密。

用公钥加密的内容只能用私钥解密（加密场景）。用私钥签名的内容可以用公钥验证（签名场景）。

### 主要算法

**RSA**

基于大整数分解的困难性。密钥长度通常2048位或4096位。速度较慢，通常只用于加密对称密钥或签名。

**ECC（椭圆曲线密码学）**

基于椭圆曲线离散对数的困难性。相同安全等级下密钥更短（256位ECC ≈ 3072位RSA）。移动设备上更高效。常用曲线：P-256、Curve25519。

**Ed25519**

基于Curve25519的签名算法。高性能、高安全性。现代系统的首选签名算法。

### 混合加密

非对称加密速度慢，不适合加密大量数据。实践中使用混合加密：

1. 生成随机对称密钥
2. 用对称密钥加密数据
3. 用接收方公钥加密对称密钥
4. 发送加密的数据和加密的密钥

接收方用私钥解密对称密钥，再用对称密钥解密数据。

## 哈希函数

### 特性

**单向性**：从哈希值无法逆推原文。

**确定性**：相同输入总是产生相同输出。

**抗碰撞**：难以找到两个不同输入产生相同输出。

**雪崩效应**：输入微小变化导致输出巨大变化。

### 常用算法

**SHA-256/SHA-3**

安全的哈希算法，输出256位。用于数字签名、证书、区块链。

**BLAKE2/BLAKE3**

高性能安全哈希，比SHA-256更快。适合性能敏感场景。

**MD5/SHA-1**

已被破解，不应用于安全场景。可用于非安全目的（如校验文件完整性，但有碰撞风险）。

### 密码哈希

普通哈希不适合存储密码，因为：

1. 速度太快，便于暴力破解
2. 无盐的情况下相同密码产生相同哈希，可用彩虹表攻击

密码应使用专用哈希函数：

**bcrypt**：自带盐，可调整工作因子控制计算时间。

**Argon2**：2015年密码哈希竞赛获胜者。抵抗GPU/ASIC攻击。推荐使用Argon2id变体。

**scrypt**：内存密集型，抵抗硬件攻击。

## 消息认证码（MAC）

### 作用

确保消息的完整性和认证。发送方用密钥和消息计算MAC，接收方用相同密钥验证。

### HMAC

基于哈希函数的MAC。HMAC-SHA256是常见选择。

应用：API认证、JWT签名、Cookie完整性。

### AEAD

认证加密（Authenticated Encryption with Associated Data）将加密和MAC合二为一。GCM模式和ChaCha20-Poly1305都是AEAD。

AEAD避免了单独使用加密和MAC可能导致的错误组合。现代系统应优先使用AEAD。

## 数字签名

### 原理

发送方用私钥对消息哈希进行签名，接收方用公钥验证签名。

签名证明：

1. 消息确实来自持有私钥的人（认证）
2. 消息未被篡改（完整性）
3. 发送方不能否认发送（不可否认性）

### 流程

签名：Hash(消息) → 用私钥加密哈希 → 签名

验证：用公钥解密签名 → 与Hash(消息)比较

### 应用

- 代码签名
- 文档签名
- TLS证书
- JWT
- 区块链交易

## PKI（公钥基础设施）

### 问题

非对称加密解决了密钥分发问题，但引入了新问题：如何确信某个公钥确实属于声称的实体？

### 证书

数字证书将公钥与身份绑定，由可信第三方（CA）签名。

证书包含：主体信息、公钥、有效期、CA签名。

### 证书链

根CA签发中间CA证书，中间CA签发终端实体证书。形成信任链。

浏览器和操作系统预装了受信任的根CA证书。验证服务器证书时，会沿证书链向上验证到受信任的根CA。

### 证书吊销

证书可能因私钥泄露、信息变更等原因需要吊销。

**CRL**：证书吊销列表，CA定期发布。

**OCSP**：在线证书状态协议，实时查询证书状态。

**OCSP Stapling**：服务器主动获取OCSP响应并随证书一起发送，改善性能和隐私。

## TLS握手

### 过程概述

1. 客户端发送支持的密码套件和随机数
2. 服务器选择密码套件，发送证书和随机数
3. 客户端验证证书
4. 密钥交换（通常使用ECDHE）
5. 双方推导会话密钥
6. 使用会话密钥加密通信

### 前向保密

使用临时密钥交换（如ECDHE）实现前向保密：即使服务器长期私钥泄露，历史会话仍然安全，因为每次会话使用不同的临时密钥。

### TLS 1.3改进

- 简化握手，1-RTT完成
- 移除不安全的算法
- 默认前向保密
- 支持0-RTT恢复（牺牲一定安全性换取性能）

## 总结

| 场景 | 推荐方案 |
|------|----------|
| 数据加密 | AES-256-GCM |
| 密钥交换 | ECDHE |
| 数字签名 | Ed25519 |
| 哈希 | SHA-256 |
| 密码存储 | Argon2id |
| 传输安全 | TLS 1.3 |

密码学是安全的基石，但正确使用比选择算法更重要。使用经过验证的库，不要自己实现密码算法。
