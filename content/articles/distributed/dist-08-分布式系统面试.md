## 基础概念

### CAP定理

**问题**：解释CAP定理，举例说明CP和AP系统。

**解答**：

CAP定理：分布式系统在网络分区时，只能在一致性（C）和可用性（A）之间选择一个。

**CP系统**：选择一致性，分区时可能拒绝服务。
- ZooKeeper：选举期间无法提供服务
- etcd：Raft需要多数派才能工作

**AP系统**：选择可用性，分区时可能返回过时数据。
- Cassandra：最终一致，分区时各分区独立工作
- DynamoDB：可配置一致性级别

注意：CAP是关于网络分区时的权衡，正常情况可以同时满足C和A。

### 一致性级别

**问题**：解释强一致性、最终一致性、因果一致性的区别。

**解答**：

**强一致性（线性化）**：所有操作按全局时间顺序，读到最新写入。代价高，需要协调。

**因果一致性**：有因果关系的操作保持顺序，并发操作顺序可以不同。比强一致弱，比最终一致强。

**最终一致性**：停止写入后，所有副本最终收敛。不保证读到最新值。

选择依据：
- 银行转账：强一致性
- 社交媒体评论：因果一致性
- DNS、缓存：最终一致性

## 共识算法

### Paxos vs Raft

**问题**：Paxos和Raft有什么区别？为什么Raft更常用？

**解答**：

**相同点**：
- 都解决共识问题
- 都能容忍少数节点故障
- 安全性证明类似

**Raft的优势**：
- 更易理解，论文以可理解性为设计目标
- 有明确的Leader，简化日志复制
- 日志连续，不允许空洞
- 成员变更有清晰协议

**Paxos更灵活**：
- 无Leader版本，无单点瓶颈
- 可以乱序提交，某些场景更高效
- 各种优化变种（Fast Paxos、EPaxos等）

实践中Raft更常用（etcd、Consul），因为实现和调试更容易。

### Raft选举

**问题**：Raft如何保证选举安全性？

**解答**：

**投票限制**：
- 每个任期每个节点只投一票
- 只投给日志至少和自己一样新的候选人
- 日志比较：最后条目任期更大者更新；任期相同则索引更大者更新

**保证**：
- 已提交的条目一定在当选Leader的日志中
- 不会选出丢失已提交数据的Leader

**活锁避免**：
- 选举超时随机化
- 避免多个节点同时发起选举

## 分布式存储

### 一致性哈希

**问题**：解释一致性哈希，它解决什么问题？

**解答**：

**问题**：传统hash(key) % N在节点增减时，几乎所有数据需要重新分配。

**解决**：
- 哈希空间组织成环
- 节点和数据都哈希到环上
- 数据分配给顺时针第一个节点
- 增减节点只影响相邻数据

**虚拟节点**：
- 物理节点对应多个虚拟节点
- 解决负载不均问题
- 支持异构节点（容量不同）

**应用**：Cassandra、DynamoDB、Redis Cluster

### 法定人数

**问题**：什么是法定人数（Quorum）？R+W>N有什么意义？

**解答**：

**法定人数**：操作需要的最少节点数。

**R+W>N**：
- N：副本总数
- W：写入确认节点数
- R：读取查询节点数

当R+W>N时，读取的节点和写入的节点必有交集，保证读到最新值。

**权衡**：
- W=N, R=1：写慢读快，写入必须所有节点成功
- W=1, R=N：写快读慢，可能读到过时数据
- W=R=(N+1)/2：平衡方案

## 分布式事务

### 2PC的问题

**问题**：两阶段提交有什么问题？如何改进？

**解答**：

**问题**：
1. **阻塞**：参与者在准备后阻塞等待，持有锁
2. **单点故障**：协调者崩溃，参与者可能永久阻塞
3. **网络分区**：可能导致不一致

**改进方案**：
- **3PC**：增加超时和预提交阶段，减少阻塞
- **Saga**：拆分为本地事务+补偿，无阻塞
- **TCC**：业务层面预留/确认/取消

**最佳实践**：
- 尽量避免分布式事务
- 接受最终一致性
- 设计幂等和补偿

### Saga补偿

**问题**：Saga模式如何保证最终一致性？

**解答**：

**Saga原理**：
- 长事务拆分为多个本地事务
- 每个本地事务有对应的补偿事务
- 失败时执行已完成事务的补偿

**执行方式**：
- 编排：事件驱动，服务自主响应
- 协调：中央协调者控制流程

**保证**：
- 所有事务成功提交，或
- 失败的事务及之前的事务全部补偿

**注意**：
- 没有隔离性，中间状态可见
- 补偿必须幂等
- 某些操作可能无法完美补偿

## 系统设计问题

### 设计分布式锁

**要求**：设计一个分布式锁服务。

**方案**：

**基于Redis**：
- SET key value NX PX timeout
- 释放时验证value（避免误释放）
- 问题：主从切换可能导致锁失效

**RedLock**：
- 向N个独立Redis实例获取锁
- 多数成功才算获取成功
- 问题：对时钟假设敏感

**基于ZooKeeper/etcd**：
- 创建临时顺序节点
- 最小序号节点持有锁
- 利用会话机制自动释放
- 更安全，但延迟较高

**Fencing Token**：
- 锁带有单调递增的token
- 资源服务拒绝旧token的操作
- 解决锁失效后的操作冲突

### 设计分布式ID生成器

**要求**：生成全局唯一、大致有序的ID。

**方案**：

**UUID**：
- 简单，无需协调
- 128位太长，无序

**Snowflake**：
- 64位：时间戳+机器ID+序列号
- 有序，支持高并发
- 需要解决时钟回拨

**号段模式**：
- 从中心服务获取ID段
- 本地分配，减少网络开销
- 需要处理服务重启

**数据库自增**：
- 可靠但性能有限
- 多主时需要不同步长

## 故障场景

### 网络分区

**问题**：系统发生网络分区时如何处理？

**解答**：

**检测**：
- 心跳超时
- 无法区分分区和节点故障

**处理策略取决于系统选择**：

**CP系统**：
- 少数派停止服务
- 避免脑裂和数据不一致

**AP系统**：
- 继续服务，接受可能不一致
- 分区恢复后合并冲突

**防止脑裂**：
- Fencing：旧Leader被隔离后不能写
- 租约：必须续期才能继续操作

### 时钟问题

**问题**：分布式系统中时钟可能带来什么问题？

**解答**：

**物理时钟问题**：
- 时钟偏差：不同节点时间不同
- 时钟回拨：NTP同步可能导致时间倒退

**影响**：
- 超时判断不准确
- 顺序判断错误
- 租约失效判断不准

**解决方案**：
- 逻辑时钟（Lamport、Vector Clock）
- 混合逻辑时钟（HLC）
- TrueTime（需要硬件支持）

## 面试技巧

### 系统设计展开

从高层开始，逐步深入：
1. 明确需求和约束
2. 高层架构
3. 核心组件设计
4. 深入关键技术点
5. 权衡和替代方案

### 展示深度

不只说是什么，还要解释为什么。

讨论权衡：性能vs一致性、复杂度vs可靠性。

提到实际系统的做法。

### 处理开放问题

没有标准答案，展示思考过程。

主动讨论权衡和限制。

能够在面试官引导下深入。
