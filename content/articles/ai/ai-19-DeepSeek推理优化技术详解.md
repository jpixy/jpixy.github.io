# DeepSeek 推理优化技术详解：CPU-GPU 协同计算

---

## 一、背景与动机

### 1.1 大模型推理面临的挑战

随着大语言模型（LLM）规模不断增长，推理部署面临严峻挑战：

```
┌─────────────────────────────────────────────────────────────────┐
│                    推理部署核心挑战                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. GPU 显存瓶颈                                                 │
│     ┌─────────────────────────────────────────────────────┐     │
│     │  模型参数    + KV Cache    = 显存需求                │     │
│     │  (数百GB)     (随上下文增长)   (超出单卡容量)         │     │
│     └─────────────────────────────────────────────────────┘     │
│                                                                  │
│  2. 长上下文推理                                                 │
│     ┌─────────────────────────────────────────────────────┐     │
│     │  上下文长度: 4K → 32K → 128K → 1M                    │     │
│     │  KV Cache 大小: 线性增长，显存迅速耗尽               │     │
│     └─────────────────────────────────────────────────────┘     │
│                                                                  │
│  3. 成本与性能矛盾                                               │
│     ┌─────────────────────────────────────────────────────┐     │
│     │  更多 GPU = 更高成本                                 │     │
│     │  更少 GPU = 更低吞吐量                               │     │
│     └─────────────────────────────────────────────────────┘     │
│                                                                  │
│  4. 批量处理限制                                                 │
│     ┌─────────────────────────────────────────────────────┐     │
│     │  batch_size 受限于 GPU 显存                          │     │
│     │  小 batch = GPU 利用率低                             │     │
│     └─────────────────────────────────────────────────────┘     │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 DeepSeek 的解决思路

DeepSeek 提出了一套系统性的优化方案，核心思想是**充分利用异构计算资源**：

| 资源 | 特点 | DeepSeek 的利用方式 |
|------|------|-------------------|
| **GPU** | 算力强、显存贵 | 专注计算密集型操作 |
| **CPU** | 内存便宜、带宽够 | 存储和调度缓存数据 |
| **网络** | 节点间互联 | 跨节点专家并行 |

## 三、ESS（Extended Sparse Server）架构

### 3.1 核心思想

ESS 的核心创新是将 **Latent-Cache 从 GPU 显存卸载到 CPU 内存**：

```
┌─────────────────────────────────────────────────────────────────┐
│                    ESS 架构原理                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  传统架构:                                                       │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │                       GPU                                │    │
│  │  ┌─────────────────────────────────────────────────────┐│    │
│  │  │  模型权重 (Weights)                                  ││    │
│  │  ├─────────────────────────────────────────────────────┤│    │
│  │  │  KV Cache (随序列长度线性增长)                       ││    │
│  │  │  ████████████████████████████████████████████       ││    │
│  │  ├─────────────────────────────────────────────────────┤│    │
│  │  │  计算工作空间                                        ││    │
│  │  └─────────────────────────────────────────────────────┘│    │
│  │                                                          │    │
│  │  问题: 长上下文时 KV Cache 占满显存                      │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                  │
│  ESS 架构:                                                       │
│  ┌────────────────────────┐    ┌────────────────────────┐       │
│  │         GPU            │    │         CPU            │       │
│  │  ┌──────────────────┐  │    │  ┌──────────────────┐  │       │
│  │  │   模型权重       │  │    │  │                  │  │       │
│  │  ├──────────────────┤  │    │  │  Latent-Cache    │  │       │
│  │  │   热点 Cache     │  │◄──►│  │  (冷数据存储)    │  │       │
│  │  │   (当前计算)     │  │    │  │                  │  │       │
│  │  ├──────────────────┤  │    │  │  ████████████    │  │       │
│  │  │   计算工作空间   │  │    │  │  ████████████    │  │       │
│  │  │   (更大空间)     │  │    │  │  ████████████    │  │       │
│  │  └──────────────────┘  │    │  └──────────────────┘  │       │
│  └────────────────────────┘    └────────────────────────┘       │
│                                                                  │
│  优势: GPU 显存释放，可容纳更大 batch                            │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 Latent-Cache 机制

DeepSeek 使用 **MLA（Multi-head Latent Attention）** 技术，将传统的 KV Cache 压缩为 Latent-Cache：

```
┌─────────────────────────────────────────────────────────────────┐
│                    MLA 压缩原理                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  传统 Multi-Head Attention:                                      │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  每个 token 存储:                                        │    │
│  │  - K 向量: [n_heads × head_dim]                         │    │
│  │  - V 向量: [n_heads × head_dim]                         │    │
│  │                                                          │    │
│  │  总大小: 2 × n_heads × head_dim × seq_len × n_layers    │    │
│  │          = 巨大的显存占用                                │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                  │
│  MLA (Multi-head Latent Attention):                              │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  每个 token 存储:                                        │    │
│  │  - Latent 向量: [latent_dim]  (远小于 n_heads × head_dim)│    │
│  │                                                          │    │
│  │  推理时通过线性变换恢复 K、V:                            │    │
│  │  K = W_k @ Latent                                       │    │
│  │  V = W_v @ Latent                                       │    │
│  │                                                          │    │
│  │  压缩比: 通常可达 4-8 倍                                 │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                  │
│  Latent-Cache 特点:                                              │
│  - 体积小，适合 CPU-GPU 传输                                     │
│  - 可按需从 CPU 调度到 GPU                                       │
│  - 解耦 batch_size 与 GPU 显存                                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 CPU-GPU 数据调度

```
┌─────────────────────────────────────────────────────────────────┐
│                    数据调度策略                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  时间轴:  ──────────────────────────────────────────────────▶   │
│                                                                  │
│  GPU:     ┌────────┐       ┌────────┐       ┌────────┐          │
│           │Compute │       │Compute │       │Compute │          │
│           │ Token1 │       │ Token2 │       │ Token3 │          │
│           └────────┘       └────────┘       └────────┘          │
│                                                                  │
│  PCIe:         ┌──────┐        ┌──────┐        ┌──────┐         │
│  传输:         │Fetch │        │Fetch │        │Fetch │         │
│                │Cache2│        │Cache3│        │Cache4│         │
│                └──────┘        └──────┘        └──────┘         │
│                                                                  │
│  关键优化:                                                       │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  1. 预取 (Prefetch): 提前加载下一批数据                  │    │
│  │  2. 异步传输: PCIe 传输与 GPU 计算并行                   │    │
│  │  3. 双缓冲: 读写分离，避免等待                           │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 四、专家并行（Expert Parallelism）

### 4.1 MoE 架构回顾

DeepSeek 采用 **Mixture of Experts (MoE)** 架构：

```
┌─────────────────────────────────────────────────────────────────┐
│                    MoE 架构                                      │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  输入 Token                                                      │
│      │                                                           │
│      ▼                                                           │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │                   Router (门控网络)                      │    │
│  │            计算每个专家的激活概率                         │    │
│  └───────────────────────┬─────────────────────────────────┘    │
│                          │                                       │
│         ┌────────────────┼────────────────┐                     │
│         ▼                ▼                ▼                     │
│    ┌─────────┐     ┌─────────┐     ┌─────────┐                  │
│    │Expert 1 │     │Expert 2 │     │Expert 3 │  ... Expert 256  │
│    │  (FFN)  │     │  (FFN)  │     │  (FFN)  │                  │
│    └────┬────┘     └────┬────┘     └────┬────┘                  │
│         │               │               │                        │
│         └───────────────┼───────────────┘                        │
│                         ▼                                        │
│                    加权求和                                      │
│                         │                                        │
│                         ▼                                        │
│                   输出 Token                                     │
│                                                                  │
│  DeepSeek 配置:                                                  │
│  - 总专家数: 256                                                 │
│  - 每次激活: 8 个专家 + 1 个共享专家                             │
│  - 稀疏激活: 仅 3% 的参数参与计算                                │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 跨节点专家并行

```
┌─────────────────────────────────────────────────────────────────┐
│                    跨节点 EP 策略                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  单节点限制:                                                     │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  一个节点 8 块 GPU                                       │    │
│  │  每块 GPU 存储 32 个专家                                 │    │
│  │  256 专家 ÷ 8 GPU = 32 专家/GPU                         │    │
│  │                                                          │    │
│  │  问题: GPU 显存压力大，batch 受限                        │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                  │
│  跨节点 EP:                                                      │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │                                                          │    │
│  │   Node 1        Node 2        Node 3       ...  Node 18 │    │
│  │  ┌──────┐     ┌──────┐     ┌──────┐          ┌──────┐  │    │
│  │  │ GPU  │     │ GPU  │     │ GPU  │          │ GPU  │  │    │
│  │  │ E1-2 │◄───►│ E3-4 │◄───►│ E5-6 │  ...     │E35-36│  │    │
│  │  │+共享 │     │+共享 │     │+共享 │          │+共享 │  │    │
│  │  └──────┘     └──────┘     └──────┘          └──────┘  │    │
│  │                                                          │    │
│  │  每个 GPU: 2 个路由专家 + 1 个共享专家                   │    │
│  │  优势: 显存压力降低 16 倍                                │    │
│  │                                                          │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                  │
│  通信优化:                                                       │
│  - All-to-All 通信: 分发 token 到对应专家节点                   │
│  - 高速互联: NVLink + InfiniBand                                │
│  - 通信计算重叠: 流水线调度                                      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 4.3 EP 带来的优势

| 优势 | 说明 |
|------|------|
| **更大 Batch** | 每个 GPU 存储更少专家，释放显存给 batch |
| **更高 GPU 利用率** | 大 batch 意味着更好的矩阵乘法效率 |
| **更低延迟** | 访存需求减少，计算更快 |
| **可扩展性** | 通过增加节点线性扩展吞吐量 |

## 五、流水线优化

### 5.1 五阶段流水线

DeepSeek 将 Attention 计算细分为五个阶段，实现通信与计算的完美重叠：

```
┌─────────────────────────────────────────────────────────────────┐
│                    五阶段流水线                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  时间轴: ───────────────────────────────────────────────────▶   │
│                                                                  │
│  阶段 1: All-to-All Dispatch                                    │
│         ┌─────────────────────────────────────────────────────┐ │
│  Token  │ Token 分发到对应专家所在的 GPU 节点                  │ │
│  分发   └─────────────────────────────────────────────────────┘ │
│                                                                  │
│  阶段 2: Expert Compute (Part 1)                                │
│         ┌─────────────────────────────────────────────────────┐ │
│  专家   │ 专家 FFN 的第一部分计算 (Up Projection)              │ │
│  计算1  └─────────────────────────────────────────────────────┘ │
│                                                                  │
│  阶段 3: Expert Compute (Part 2)                                │
│         ┌─────────────────────────────────────────────────────┐ │
│  专家   │ 专家 FFN 的第二部分计算 (Down Projection)            │ │
│  计算2  └─────────────────────────────────────────────────────┘ │
│                                                                  │
│  阶段 4: All-to-All Combine                                     │
│         ┌─────────────────────────────────────────────────────┐ │
│  结果   │ 收集各专家的计算结果                                 │ │
│  汇总   └─────────────────────────────────────────────────────┘ │
│                                                                  │
│  阶段 5: Attention + Residual                                   │
│         ┌─────────────────────────────────────────────────────┐ │
│  注意力 │ Attention 计算 + 残差连接                            │ │
│         └─────────────────────────────────────────────────────┘ │
│                                                                  │
│  流水线重叠:                                                     │
│                                                                  │
│  Layer N:   [1][2][3][4][5]                                     │
│  Layer N+1:    [1][2][3][4][5]                                  │
│  Layer N+2:       [1][2][3][4][5]                               │
│                                                                  │
│  效果: 通信延迟被计算完全隐藏                                    │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 六、Prefill 与 Decode 分离

│  │  │                                                      ││    │

│  │  ┌─────────────────────────────────────────────────────┐│    │
│  │  │  特点:                                               ││    │

### 6.2 为什么要分离？

| 阶段 | 瓶颈 | 优化目标 | DeepSeek 方案 |
