## 概述

作为技术管理者，保障项目按时、高质量交付是核心职责。本文系统介绍敏捷实践、项目管理和交付保障的方法论。

## 一、敏捷开发基础

### 1.1 敏捷宣言

```
敏捷宣言四大价值观：

┌─────────────────────────────────────────────────────────┐
│                                                          │
│   个体和互动      高于      流程和工具                  │
│                                                          │
│   可工作的软件    高于      详尽的文档                  │
│                                                          │
│   客户协作        高于      合同谈判                    │
│                                                          │
│   响应变化        高于      遵循计划                    │
│                                                          │
│   ──────────────────────────────────────────────────   │
│   右边的也重要，但更重视左边的                          │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 1.2 Scrum vs Kanban

```
两种主流敏捷框架对比：

┌────────────────┬──────────────────┬──────────────────┐
│     维度       │      Scrum       │      Kanban      │
├────────────────┼──────────────────┼──────────────────┤
│ 迭代周期       │ 固定（1-4周）    │ 无固定周期       │
├────────────────┼──────────────────┼──────────────────┤
│ 角色           │ PO/SM/Team       │ 无强制角色       │
├────────────────┼──────────────────┼──────────────────┤
│ 会议           │ 多（站会/评审等）│ 少，按需         │
├────────────────┼──────────────────┼──────────────────┤
│ 变更           │ Sprint内不变     │ 随时可变         │
├────────────────┼──────────────────┼──────────────────┤
│ WIP限制        │ Sprint容量       │ 每列WIP限制      │
├────────────────┼──────────────────┼──────────────────┤
│ 适用场景       │ 产品开发         │ 运维/支持        │
└────────────────┴──────────────────┴──────────────────┘
```

## 二、Sprint 管理

### 2.1 Sprint Planning

**面试问题**：你如何进行 Sprint Planning？

```
Sprint Planning 流程（2-4小时）：

第一部分：What（做什么）
├── PO 介绍最高优先级的 Stories
├── 团队澄清需求和验收标准
└── 确定 Sprint 目标

第二部分：How（怎么做）
├── 分解 Stories 为 Tasks
├── 估算工作量
└── 团队承诺可完成的范围

输出：
├── Sprint Goal
├── Sprint Backlog
└── 任务分配（或自选）
```

**容量规划：**

```
Sprint 容量计算：

团队容量 = Σ (每人可用天数 × 每天可用小时 × 专注系数)

示例：
┌─────────────────────────────────────────────────────┐
│ 成员    │ 天数 │ 小时/天 │ 专注系数 │ 有效小时    │
├─────────────────────────────────────────────────────┤
│ 张三    │  10  │    8    │   0.8    │   64       │
│ 李四    │   8  │    8    │   0.8    │   51       │
│ 王五    │  10  │    8    │   0.6    │   48       │ (新人)
├─────────────────────────────────────────────────────┤
│ 总计    │      │         │          │  163 小时   │
└─────────────────────────────────────────────────────┘

注意：
• 专注系数考虑会议、支持等非开发时间
• 新人系数更低
• 预留 Buffer（约 10-20%）
```

### 2.2 故事点估算

```
估算方法：

相对估算（推荐）：
┌─────────────────────────────────────────────────────┐
│                                                      │
│   故事点（Story Points）                            │
│   ────────────────────                              │
│   • 不是时间，是相对复杂度                          │
│   • 常用序列：1, 2, 3, 5, 8, 13, 21...              │
│   • 与基准 Story 比较                               │
│                                                      │
│   Planning Poker：                                   │
│   1. 介绍 Story                                     │
│   2. 各自出牌（独立估算）                           │
│   3. 最高最低说明原因                               │
│   4. 再次估算直到共识                               │
│                                                      │
└─────────────────────────────────────────────────────┘

估算基准示例：
┌────────┬──────────────────────────────────────┐
│ 点数   │               描述                    │
├────────┼──────────────────────────────────────┤
│   1    │ 简单改动，几小时完成                  │
│   3    │ 小功能，1天左右                       │
│   5    │ 中等复杂度，2-3天                     │
│   8    │ 较复杂，需要几天，可能需要拆分        │
│  13    │ 很复杂，一周以上，建议拆分            │
│  21+   │ 太大，必须拆分                        │
└────────┴──────────────────────────────────────┘
```

### 2.3 Daily Standup

```
每日站会最佳实践：

基本格式（15分钟以内）：
├── 昨天完成了什么？
├── 今天计划做什么？
└── 有什么障碍/需要帮助？

常见问题及改进：

❌ 变成状态汇报会
   → 应该是团队同步，不是向领导汇报

❌ 超时冗长
   → 严格 15 分钟，详细讨论会后单聊

❌ 流于形式
   → 聚焦 Sprint Goal，不是走过场

❌ 只说任务不说障碍
   → 鼓励暴露问题，领导帮助解决

站会改进 Tips：
• 站着开（字面意思）
• 固定时间地点
• 迟到者带零食（玩笑性惩罚）
• Scrum Master 引导而非主持
```

### 2.4 Sprint Review & Retrospective

**Sprint Review：**

```
Sprint Review 目的：

┌─────────────────────────────────────────────────────┐
│                                                      │
│   展示成果                                          │
│   ────────                                          │
│   向利益相关方展示完成的工作                        │
│                                                      │
│   收集反馈                                          │
│   ────────                                          │
│   获取产品反馈，调整优先级                          │
│                                                      │
│   透明沟通                                          │
│   ────────                                          │
│   让所有人了解进展                                  │
│                                                      │
└─────────────────────────────────────────────────────┘

参与者：团队 + PO + 利益相关方
时长：1-2 小时（2周 Sprint）
```

**Sprint Retrospective：**

```
回顾会框架：

经典三问法：
├── 哪些做得好？（继续保持）
├── 哪些需要改进？（找问题）
└── 下个 Sprint 改进什么？（行动项）

其他常用格式：
├── Start-Stop-Continue
├── 4Ls (Liked, Learned, Lacked, Longed for)
├── 帆船法（风/锚/礁石）
└── 时间线回顾

回顾会要点：
• Blameless（不指责）
• 产出具体 Action Item
• 跟踪上次 Action 完成情况
• 定期变换形式，避免疲劳
```

## 三、项目风险管理

### 3.1 风险识别

**面试问题**：你如何识别和管理项目风险？

```
常见技术项目风险：

┌─────────────────────────────────────────────────────┐
│                                                      │
│   需求风险                                          │
│   ├── 需求不清晰/频繁变更                           │
│   ├── 范围蔓延（Scope Creep）                       │
│   └── 利益相关方期望不一致                          │
│                                                      │
│   技术风险                                          │
│   ├── 技术选型不当                                  │
│   ├── 技术难点评估不足                              │
│   ├── 依赖的外部系统/API                            │
│   └── 性能/安全问题                                 │
│                                                      │
│   资源风险                                          │
│   ├── 人员变动（离职/请假/调岗）                    │
│   ├── 技能缺口                                      │
│   └── 多项目资源竞争                                │
│                                                      │
│   外部风险                                          │
│   ├── 跨团队依赖                                    │
│   ├── 第三方服务                                    │
│   └── 合规/政策变化                                 │
│                                                      │
└─────────────────────────────────────────────────────┘
```

### 3.2 风险评估矩阵

```
风险评估矩阵：

              高影响
                │
    ┌───────────┼───────────┐
    │  主动管理 │   紧急    │
    │           │   处理    │
────┼───────────┼───────────┼──── 高概率
    │   监控    │   关注    │
    │           │           │
    └───────────┼───────────┘
                │
              低影响

风险等级 = 概率 × 影响

处理策略：
┌────────┬────────────────────────────────────────┐
│ 等级   │               策略                      │
├────────┼────────────────────────────────────────┤
│ 高危   │ 制定应对计划，分配责任人，定期跟踪      │
├────────┼────────────────────────────────────────┤
│ 中危   │ 制定应对策略，定期检查                  │
├────────┼────────────────────────────────────────┤
│ 低危   │ 记录观察，被动响应                      │
└────────┴────────────────────────────────────────┘
```

### 3.3 风险应对策略

```
风险应对四策略：

┌─────────────────────────────────────────────────────┐
│                                                      │
│   规避（Avoid）                                     │
│   ────────────                                      │
│   改变计划，消除风险来源                            │
│   例：放弃高风险技术选型                            │
│                                                      │
│   转移（Transfer）                                  │
│   ────────────                                      │
│   将风险转移给第三方                                │
│   例：外包、保险、SLA保障                           │
│                                                      │
│   缓解（Mitigate）                                  │
│   ────────────                                      │
│   降低概率或影响                                    │
│   例：增加测试、设计容错、准备备选方案              │
│                                                      │
│   接受（Accept）                                    │
│   ────────────                                      │
│   接受风险，准备应急计划                            │
│   例：小概率小影响的风险                            │
│                                                      │
└─────────────────────────────────────────────────────┘
```

## 四、项目延期处理

### 4.1 延期预警

**面试问题**：项目快延期了，你怎么处理？

```
延期信号识别：

┌─────────────────────────────────────────────────────┐
│                                                      │
│   早期信号                                          │
│   ├── Sprint Burndown 不健康                        │
│   ├── 持续的"差一点就完成"                         │
│   ├── 需求澄清频繁                                  │
│   ├── 技术债务拖累速度                              │
│   └── 团队士气下降                                  │
│                                                      │
│   关键指标监控                                      │
│   ├── Velocity 趋势                                 │
│   ├── Sprint 完成率                                 │
│   ├── Bug 趋势                                      │
│   └── Burndown/Burnup 图                            │
│                                                      │
└─────────────────────────────────────────────────────┘
```

### 4.2 延期处理策略

```
处理延期的四种选择：

┌─────────────────────────────────────────────────────┐
│                                                      │
│   1. 调整范围 (Cut Scope)                          │
│   ──────────────────────                            │
│   减少功能，保证核心交付                            │
│   与 PO 协商优先级，砍掉 Nice-to-Have               │
│                                                      │
│   2. 增加资源 (Add Resources)                      │
│   ──────────────────────                            │
│   加人或加班                                        │
│   注意：布鲁克斯定律 - 加人可能让项目更慢          │
│                                                      │
│   3. 延长时间 (Extend Timeline)                    │
│   ──────────────────────                            │
│   推迟 Deadline                                     │
│   需要与利益相关方协商                              │
│                                                      │
│   4. 降低质量 (Reduce Quality)                     │
│   ──────────────────────                            │
│   技术债务/临时方案                                 │
│   慎用，会产生长期成本                              │
│                                                      │
└─────────────────────────────────────────────────────┘

"铁三角"权衡：范围、时间、资源（质量）
```

### 4.3 沟通策略

```
向上沟通延期风险：

1. 尽早沟通
   └── 发现风险就说，不要藏着

2. 带方案不带纯问题
   ├── 现状：项目预计延期 2 周
   ├── 原因：关键依赖方 API 变更
   ├── 方案A：砍掉 X 功能，按时上线
   ├── 方案B：延期 2 周，完整交付
   └── 建议：我建议方案A，因为...

3. 持续更新
   └── 承诺的汇报节点要兑现

4. 展示控制力
   └── 说明已采取的措施
```

## 五、跨团队协作

### 5.1 依赖管理

**面试问题**：如何处理跨团队依赖？

```
依赖管理最佳实践：

┌─────────────────────────────────────────────────────┐
│                                                      │
│   识别依赖                                          │
│   ────────                                          │
│   • 在 Planning 时识别外部依赖                      │
│   • 标注依赖类型（API/数据/服务）                   │
│   • 评估风险等级                                    │
│                                                      │
│   提前沟通                                          │
│   ────────                                          │
│   • 依赖方 Tech Lead 对接                           │
│   • 明确交付物和时间线                              │
│   • 约定接口规范                                    │
│                                                      │
│   持续跟踪                                          │
│   ────────                                          │
│   • 依赖状态可视化                                  │
│   • 定期同步进展                                    │
│   • 有 Blocker 立即升级                             │
│                                                      │
│   降低耦合                                          │
│   ────────                                          │
│   • Mock/Stub 先行开发                              │
│   • 接口契约先行                                    │
│   • 设计松耦合架构                                  │
│                                                      │
└─────────────────────────────────────────────────────┘
```

### 5.2 跨团队会议

```
跨团队协作会议：

Scrum of Scrums（适用于多团队）：
├── 频率：每天或隔天
├── 参与者：各团队代表（通常是 Scrum Master 或 TL）
├── 时长：15-30 分钟
├── 议题：
│   ├── 各团队进展
│   ├── 跨团队障碍
│   └── 依赖和协调

PI Planning（SAFe 框架）：
├── 频率：每季度
├── 时长：2天
├── 目的：多团队对齐季度目标
└── 产出：团队级别的 Sprint 计划

技术协调会：
├── 频率：每周
├── 参与者：相关团队 Tech Lead
└── 议题：技术方案对齐、接口约定
```

## 六、质量保障

### 6.1 Definition of Done

```
DoD（完成的定义）示例：

┌─────────────────────────────────────────────────────┐
│                                                      │
│   代码层面                                          │
│   □ 代码已提交并通过 CI                             │
│   □ 代码已 Code Review 并 Approved                  │
│   □ 单元测试覆盖率 > 80%                            │
│   □ 无新增 Lint 警告                                │
│                                                      │
│   测试层面                                          │
│   □ 集成测试通过                                    │
│   □ 功能测试完成                                    │
│   □ 无阻塞性 Bug                                    │
│   □ 回归测试通过                                    │
│                                                      │
│   文档层面                                          │
│   □ API 文档更新                                    │
│   □ 必要的用户文档                                  │
│   □ 发布说明                                        │
│                                                      │
│   部署层面                                          │
│   □ 已部署到 Staging 环境                           │
│   □ 配置和脚本就绪                                  │
│   □ 监控和告警配置                                  │
│                                                      │
└─────────────────────────────────────────────────────┘

注意：DoD 是团队共识，需要全员遵守
```

### 6.2 持续集成/持续交付

```
CI/CD 最佳实践：

┌─────────────────────────────────────────────────────┐
│                                                      │
│   代码提交                                          │
│       │                                             │
│       ▼                                             │
│   ┌─────────────────────────────────────────┐      │
│   │              CI Pipeline                 │      │
│   ├─────────────────────────────────────────┤      │
│   │  Build → Lint → Unit Test → Coverage   │      │
│   │            → Security Scan              │      │
│   └─────────────────────────────────────────┘      │
│       │                                             │
│       ▼                                             │
│   Code Review & Merge                               │
│       │                                             │
│       ▼                                             │
│   ┌─────────────────────────────────────────┐      │
│   │              CD Pipeline                 │      │
│   ├─────────────────────────────────────────┤      │
│   │  Deploy Staging → Integration Tests    │      │
│   │        → Deploy Prod (Canary/Blue-Green)│      │
│   └─────────────────────────────────────────┘      │
│                                                      │
└─────────────────────────────────────────────────────┘

CI/CD 原则：
• 每次提交触发构建
• 失败快速反馈
• 主干始终可发布
• 自动化一切
```

## 七、度量与改进

### 7.1 敏捷指标

```
常用敏捷指标：

┌─────────────────┬────────────────────────────────────┐
│      指标       │              说明                   │
├─────────────────┼────────────────────────────────────┤
│ Velocity        │ 每 Sprint 完成的故事点              │
│                 │ 用于容量规划，不用于绩效评估        │
├─────────────────┼────────────────────────────────────┤
│ Sprint Burndown │ Sprint 内剩余工作趋势               │
│                 │ 识别进度风险                        │
├─────────────────┼────────────────────────────────────┤
│ Lead Time       │ 从需求提出到交付的时间              │
│                 │ 端到端效率指标                      │
├─────────────────┼────────────────────────────────────┤
│ Cycle Time      │ 从开始开发到完成的时间              │
│                 │ 开发效率指标                        │
├─────────────────┼────────────────────────────────────┤
│ Throughput      │ 单位时间内完成的 Story 数量         │
│                 │ 产出能力指标                        │
├─────────────────┼────────────────────────────────────┤
│ Defect Rate     │ Bug 数量/功能数量                   │
│                 │ 质量指标                            │
└─────────────────┴────────────────────────────────────┘
```

### 7.2 持续改进

```
持续改进循环：

        ┌─────────────┐
        │    Plan     │ ← 识别改进点
        └──────┬──────┘
               │
               ▼
        ┌─────────────┐
        │     Do      │ ← 实施改进
        └──────┬──────┘
               │
               ▼
        ┌─────────────┐
        │    Check    │ ← 验证效果
        └──────┬──────┘

               ▼

                               ▼

```

## 八、面试常见问题

### Q1: 你如何确保项目按时交付？

```
回答框架：

1. 前期规划
   ├── 清晰的需求和验收标准
   ├── 合理的估算和容量规划
   └── 识别风险和依赖

2. 过程管理
   ├── 敏捷迭代，小步快跑
   ├── 每日站会跟踪进度
   ├── 可视化看板
   └── 定期检查点

3. 风险应对
   ├── 持续监控预警信号
   ├── 有 Buffer 应对意外
   └── 及时升级和沟通

4. 质量内建
   ├── DoD 确保完成质量
   ├── CI/CD 快速反馈
   └── 避免返工
```

### Q2: 描述一次项目严重延期的经历

```
回答结构（STAR-L）：

Situation：
"负责一个 3 个月的项目，在第 2 个月发现将延期 6 周"

Task：
"作为 Tech Lead，需要处理延期并保证最终交付"

Action：
├── 分析原因（需求变更 + 技术难点）
├── 与 PM/业务沟通，协商范围
├── 调整计划，分阶段交付
├── 技术攻坚（关键模块加强投入）
└── 每周向上同步进展

Result：
"最终延期 3 周交付核心功能，完整功能 4 周后补齐"
"客户满意度仍保持 8/10"

Learning：
├── 需求变更管理需要更严格
├── 技术风险要更早识别
└── 建立了变更影响评估机制
```

### Q3: 你如何处理范围蔓延（Scope Creep）？

```
处理范围蔓延：

预防：
├── 明确的需求基线
├── 变更管理流程
└── PO/业务方理解范围约束

发现时：
├── 评估变更影响（时间、资源、风险）
├── 与 PO 沟通权衡
├── 如果接受，调整时间线或砍其他功能
└── 记录变更原因

沟通话术：
"这个新需求很有价值。我评估了一下，大约需要额外 X 天。
 我们可以：
 A) 延期 X 天
 B) 替换掉 Y 功能
 C) 放到下个版本
 你倾向哪个？"
```

### Q4: Agile 有什么局限性？

```
Agile 的局限性（展示深度思考）：

1. 需要高度协作的环境
   └── 分布式/外包团队难度大

2. 对人员要求高
   └── 需要自驱力和跨职能能力

3. 文档可能不足
   └── 对合规/审计有挑战

4. 难以应对固定范围合同
   └── 传统甲乙方模式不适合

5. 规模化挑战
   └── 多团队协调复杂度高

6. 不适合所有项目
   └── 硬件、嵌入式、安全关键系统

应对方式：
"Agile 是工具不是教条，
 根据团队和项目特点灵活调整，
 取其精华。"
```

### 9.2 实践清单

```
Scrum 实践自检：

□ 有明确的 Product Owner 负责需求优先级
□ Sprint 周期固定（1-4周）
□ Sprint Planning 产出清晰的目标和承诺
□ 每日站会不超过 15 分钟

□ Retrospective 持续改进
□ DoD 明确且被遵守
□ Velocity 稳定可预测
□ 团队自组织，自己领取任务
```
