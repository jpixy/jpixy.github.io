## 概述

线上故障是技术团队不可避免的挑战。作为技术管理者，建立有效的 On-Call 制度和事故响应机制是保障系统稳定性的关键。本文系统介绍故障应急管理的最佳实践。

## 一、On-Call 制度设计

### 1.1 什么是 On-Call

```
On-Call 的本质：

┌─────────────────────────────────────────────────────────┐
│                                                          │
│   On-Call = 在指定时间段内，随时准备响应系统告警        │
│                                                          │
│   职责：                                                │
│   ├── 监控系统状态                                      │
│   ├── 响应告警和事故                                    │
│   ├── 执行初步诊断和止血                                │
│   ├── 升级需要帮助的问题                                │
│   └── 记录和交接                                        │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 1.2 On-Call 轮换设计

**面试问题**：你如何设计团队的 On-Call 制度？

```
轮换模式：

┌─────────────────────────────────────────────────────────┐
│                                                          │
│   周轮换（推荐）                                        │
│   ──────────────                                        │
│   • 每人每周轮一次                                      │
│   • 周一交接                                            │
│   • 足够时间熟悉当前状况                                │
│                                                          │
│   日轮换                                                │
│   ──────────────                                        │
│   • 每人每天轮一次                                      │
│   • 降低单人负担                                        │
│   • 但交接频繁，上下文丢失                              │
│                                                          │
│   Follow-the-Sun                                        │
│   ──────────────                                        │
│   • 跨时区团队                                          │
│   • 各时区只覆盖工作时间                                │
│   • 无需夜间值班                                        │
│                                                          │
└─────────────────────────────────────────────────────────┘

团队规模建议：
• 5人团队：每人约 1周/月 On-Call
• 低于4人：On-Call 负担过重，考虑合并或外部支持
```

### 1.3 On-Call 层级

```
On-Call 分层响应：

┌─────────────────────────────────────────────────────────┐
│                                                          │
│   L1 - Primary On-Call                                  │
│   ──────────────────                                    │
│   • 第一响应人                                          │
│   • 处理大多数告警                                      │
│   • 初步诊断和止血                                      │
│                                                          │
│   L2 - Secondary On-Call                                │
│   ──────────────────                                    │
│   • 备份，Primary 无法响应时接手                        │
│   • 复杂问题的支持                                      │
│   • 通常是上周的 Primary                                │
│                                                          │
│   L3 - Escalation                                       │
│   ──────────────────                                    │
│   • 领域专家或 Tech Lead                                │
│   • 处理需要深度专业知识的问题                          │
│   • 重大事故的决策支持                                  │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 1.4 On-Call 补偿与关怀

```
On-Call 负担管理：

┌─────────────────────────────────────────────────────────┐
│                                                          │
│   补偿机制                                              │
│   ────────                                              │
│   • On-Call 津贴                                        │
│   • 调休（如夜间处理事故）                              │
│   • 节假日额外补偿                                      │
│                                                          │
│   负担控制                                              │
│   ────────                                              │
│   • 告警数量监控（目标：< 2次/天）                      │
│   • 噪音告警清理                                        │
│   • 自动化减少人工介入                                  │
│                                                          │
│   心理健康                                              │
│   ────────                                              │
│   • 避免长期高强度 On-Call                              │
│   • 事故后的心理支持                                    │
│   • 鼓励分享压力                                        │
│                                                          │
└─────────────────────────────────────────────────────────┘

"On-Call 不应该是痛苦的。
 如果 On-Call 很痛苦，说明系统需要改进。"
```

## 二、事故响应流程

### 2.1 事故严重级别

```
事故分级标准：

┌────────┬──────────────────────────────────────────────┐
│  级别  │                    定义                       │
├────────┼──────────────────────────────────────────────┤
│  SEV1  │ 核心业务完全不可用                           │
│ (P0)   │ 大规模用户影响                               │
│        │ 数据丢失风险                                 │
│        │ 响应时间：立即                               │
├────────┼──────────────────────────────────────────────┤
│  SEV2  │ 核心功能严重受损                             │
│ (P1)   │ 部分用户受影响                               │
│        │ 有降级方案                                   │
│        │ 响应时间：15分钟内                           │
├────────┼──────────────────────────────────────────────┤
│  SEV3  │ 非核心功能异常                               │
│ (P2)   │ 少量用户受影响                               │
│        │ 业务可继续                                   │
│        │ 响应时间：工作时间内                         │
├────────┼──────────────────────────────────────────────┤
│  SEV4  │ 轻微问题                                     │
│ (P3)   │ 几乎无用户感知                               │
│        │ 可按正常流程处理                             │
│        │ 响应时间：下个 Sprint                        │
└────────┴──────────────────────────────────────────────┘
```

### 2.2 事故响应流程

```
事故响应阶段：

┌──────────────┐
│   1. 检测    │ ← 告警/用户报告/监控发现
└──────┬───────┘
       ▼
┌──────────────┐
│   2. 响应    │ ← On-Call 确认，初步评估
└──────┬───────┘
       ▼
┌──────────────┐
│   3. 止血    │ ← 恢复服务优先（回滚/切流/降级）
└──────┬───────┘
       ▼
┌──────────────┐
│   4. 根因    │ ← 深入分析根本原因
└──────┬───────┘
       ▼
┌──────────────┐
│   5. 修复    │ ← 彻底解决问题
└──────┬───────┘
       ▼
┌──────────────┐
│   6. 复盘    │ ← Postmortem，防止再发
└──────────────┘
```

## 三、Blameless Postmortem

### 3.1 什么是 Blameless Postmortem

**面试问题**：你如何进行事故复盘？

```
Blameless Postmortem 核心理念：

┌─────────────────────────────────────────────────────────┐
│                                                          │
│   "我们假设每个人在当时的情境下，                       │
│    基于他们掌握的信息，做出了合理的决定。"              │
│                                                          │
│   ─────────────────────────────────────────────────    │
│                                                          │
│   不是找"谁的错"                                        │
│   而是找"系统哪里可以改进"                              │
│                                                          │
│   目的：                                                │
│   • 学习和改进，不是惩罚                                │
│   • 暴露系统性问题                                      │
│   • 防止同类问题再发                                    │
│   • 知识共享                                            │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 3.2 Postmortem 文档结构

```
Postmortem 模板：

┌─────────────────────────────────────────────────────────┐
│                     事故复盘报告                         │
│                    [事故标题]                           │
├─────────────────────────────────────────────────────────┤
│                                                          │
│   基本信息                                              │
│   ────────                                              │
│   • 日期/时间                                           │
│   • 严重级别                                            │
│   • 影响范围                                            │
│   • 影响时长                                            │
│   • 参与人员                                            │
│                                                          │
│   摘要                                                  │
│   ────────                                              │
│   • 一句话描述发生了什么                                │
│                                                          │
│   影响                                                  │
│   ────────                                              │
│   • 用户影响（数量、程度）                              │
│   • 业务影响（收入、SLA）                               │
│                                                          │
│   时间线                                                │
│   ────────                                              │
│   • 完整的事件时间线                                    │
│   • 从检测到恢复的每个关键节点                          │
│                                                          │
│   根因分析                                              │
│   ────────                                              │
│   • 直接原因                                            │
│   • 根本原因（5 Whys）                                  │
│   • 促成因素                                            │
│                                                          │
│   做得好的地方                                          │
│   ────────                                              │
│   • 响应中有效的部分                                    │
│                                                          │
│   可改进的地方                                          │
│   ────────                                              │
│   • 哪里可以做得更好                                    │
│                                                          │
│   行动项（Action Items）                                │
│   ────────                                              │
│   • 具体的改进措施                                      │
│   • 责任人和截止日期                                    │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 3.3 5 Whys 分析法

```
5 Whys 示例：

问题：网站宕机 2 小时

Why 1: 为什么宕机？
→ 数据库连接池耗尽

Why 2: 为什么连接池耗尽？
→ 查询变慢导致连接占用时间变长

Why 3: 为什么查询变慢？
→ 有个 SQL 没有使用索引

Why 4: 为什么没有索引？
→ 新功能上线时忘记添加

Why 5: 为什么会忘记？
→ 没有 SQL review 流程，也没有性能测试

根因：缺少 SQL 审查和性能测试机制
Action Item：建立 SQL review checklist，增加性能测试
```

### 3.4 Postmortem 会议

```
Postmortem 会议流程：

会前：
├── 事故负责人撰写初稿
├── 提前发送给参与者
└── 参与者提前阅读

会中（1 小时）：
├── 回顾时间线（10分钟）
├── 讨论根因分析（20分钟）
├── 讨论改进项（20分钟）
└── 确定 Action Items 和责任人（10分钟）

会后：
├── 更新文档
├── 发送给更广泛的团队
├── 跟踪 Action Items 完成情况
└── 存档供未来参考

注意：
• 保持 Blameless 氛围
• 聚焦系统改进，不是个人
• 确保 Action Items 可执行
```

## 四、SLA/SLO/SLI 管理

### 4.1 概念区分

```
SLI / SLO / SLA 三层体系：

┌─────────────────────────────────────────────────────────┐
│                                                          │
│   SLI (Service Level Indicator)                         │
│   ─────────────────────────────                         │
│   服务水平指标 - 测量什么                               │
│   例：请求成功率、P99 延迟、可用性                      │
│                                                          │
│   SLO (Service Level Objective)                         │
│   ─────────────────────────────                         │
│   服务水平目标 - 目标是多少                             │
│   例：可用性 99.9%，P99 延迟 < 200ms                    │
│                                                          │
│   SLA (Service Level Agreement)                         │
│   ─────────────────────────────                         │
│   服务水平协议 - 承诺给客户的                           │
│   例：可用性 99.9%，否则赔偿                            │
│                                                          │
│   关系：SLI 是指标，SLO 是目标，SLA 是承诺              │
│   通常：SLO > SLA（内部目标高于对外承诺）               │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 4.2 常见 SLI 指标

```
四大黄金信号（Google SRE）：

┌─────────────────────────────────────────────────────────┐
│                                                          │
│   延迟 (Latency)                                        │
│   ──────────────                                        │
│   请求处理时间                                          │
│   指标：P50, P95, P99 延迟                              │
│                                                          │
│   流量 (Traffic)                                        │
│   ──────────────                                        │
│   系统负载                                              │
│   指标：QPS, 并发连接数                                 │
│                                                          │
│   错误 (Errors)                                         │
│   ──────────────                                        │
│   失败请求比例                                          │
│   指标：错误率, 5xx 比例                                │
│                                                          │
│   饱和度 (Saturation)                                   │
│   ──────────────                                        │
│   资源使用程度                                          │
│   指标：CPU, 内存, 磁盘, 连接池使用率                   │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 4.3 Error Budget

```
Error Budget（错误预算）：

概念：
┌─────────────────────────────────────────────────────────┐
│                                                          │
│   SLO = 99.9% 可用性                                    │
│   → 每月允许 0.1% 不可用                                │
│   → 约 43 分钟/月 的 Error Budget                       │
│                                                          │
│   如果 Error Budget 用完：                              │
│   • 冻结新功能发布                                      │
│   • 聚焦稳定性改进                                      │
│   • 直到 Budget 恢复                                    │
│                                                          │
│   如果 Error Budget 充足：                              │
│   • 可以更激进地发布                                    │
│   • 可以做更多实验                                      │
│                                                          │
└─────────────────────────────────────────────────────────┘

Error Budget 的价值：
• 量化风险容忍度
• 平衡发布速度和稳定性
• 为"是否发布"提供客观依据
```

## 五、告警管理

### 5.1 告警设计原则

```
好的告警原则：

┌─────────────────────────────────────────────────────────┐
│                                                          │
│   可操作 (Actionable)                                   │
│   ─────────────────                                     │
│   收到告警后，应该有明确的行动                          │
│   如果不需要行动，不应该告警                            │
│                                                          │
│   紧急 (Urgent)                                         │
│   ─────────────────                                     │
│   需要立即处理的才应该告警                              │
│   可以等的用其他方式通知                                │
│                                                          │
│   有上下文 (Contextual)                                 │
│   ─────────────────                                     │
│   告警应包含足够信息用于诊断                            │
│   链接到 Runbook 和监控面板                             │
│                                                          │
│   不重复 (Deduplicated)                                 │
│   ─────────────────                                     │
│   同一问题不应该重复告警                                │
│   避免告警疲劳                                          │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 5.2 告警疲劳

```
告警疲劳的信号和解决：

信号：
├── 大量告警被忽略
├── On-Call 人员抱怨
├── 真正的问题被淹没
└── 团队对告警麻木

解决方法：
┌─────────────────────────────────────────────────────────┐
│                                                          │
│   1. 审计告警                                           │
│   ─────────────                                         │
│   • 回顾过去 30 天的所有告警                            │
│   • 分类：真正问题 vs 噪音                              │
│   • 删除或调整噪音告警                                  │
│                                                          │
│   2. 合理阈值                                           │
│   ─────────────                                         │
│   • 基于历史数据设定                                    │
│   • 考虑业务特征（如流量周期）                          │
│   • 定期回顾调整                                        │
│                                                          │
│   3. 告警分级                                           │
│   ─────────────                                         │
│   • Page（立即响应）                                    │
│   • Ticket（工作时间处理）                              │
│   • Log（记录观察）                                     │
│                                                          │
│   4. 告警 SLO                                           │
│   ─────────────                                         │
│   • 目标：< 2 次 Page/天                                │
│   • 监控告警数量趋势                                    │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

## 六、面试常见问题

### Q1: 描述一次你处理的线上事故

```
回答结构（STAR）：

Situation：
"去年 Black Friday，我们的支付服务突然无法处理订单，
 影响了约 10% 的用户。"

Task：
"作为 On-Call，我需要快速恢复服务，减少业务损失。"

Action：
├── 立即拉起 War Room
├── 快速定位：数据库连接池耗尽
├── 止血：回滚最近的发布 + 重启服务
├── 通知：更新 Status Page，同步利益相关方
├── 根因：新代码有慢查询，流量高峰触发
└── 后续：添加连接池监控，SQL review 流程

Result：
"服务在 35 分钟内恢复，
 后续复盘建立了 SQL 审查流程，
 类似问题再未发生。"

Learning：
"关键学习：
 1. 止血优先于根因
 2. 高峰期发布要谨慎
 3. 监控覆盖要全面"
```

### Q2: 你如何建立 On-Call 文化？

```
回答要点：

1. 公平分担
   ├── 所有人参与（包括 Manager）
   ├── 合理的轮换频率
   └── 适当补偿

2. 降低痛苦
   ├── 减少告警噪音
   ├── 自动化常见处理
   ├── 完善 Runbook
   └── 持续改进系统

3. 学习成长
   ├── Blameless 文化
   ├── Postmortem 知识共享
   └── 事故处理作为学习机会

4. 支持体系
   ├── 清晰的升级路径
   ├── Backup 机制
   └── 管理层支持
```

### Q3: 如何平衡发布速度和系统稳定性？

```
回答框架：

1. Error Budget 机制
   └── 用数据驱动决策

2. 渐进式发布
   ├── Canary 发布
   ├── 灰度发布
   └── 快速回滚能力

3. 质量门禁
   ├── 自动化测试
   ├── Code Review
   └── 性能测试

4. 监控覆盖
   ├── 发布后密切监控
   └── 自动化告警

5. 文化
   └── "You build it, you run it"
```

### Q4: Postmortem 中如何保持 Blameless？

```
具体做法：

1. 会议开场明确规则
   └── "我们聚焦系统，不是个人"

2. 语言使用
   ├── ❌ "张三搞砸了"
   └── ✅ "这个流程缺少校验"

3. 关注"如何改进"
   └── 而非"谁的错"

4. 领导以身作则
   └── 承认系统性问题，而非追责

5. Action Items
   └── 都是流程/系统改进，不是对人的惩罚

6. 心理安全
   └── 让人敢于说真话
```
