## 核心概念

### SLI（Service Level Indicator）

**服务水平指标**：量化服务行为的指标，通常表示为比率或百分比。

**好的SLI特征**：
- 直接反映用户体验
- 可测量、可计算
- 有明确的好/坏边界

**常见SLI类型**：

| 类型 | 定义 | 适用场景 |
|------|------|----------|
| **可用性** | 成功请求数 / 总请求数 | API服务、网站 |
| **延迟** | 低于阈值的请求占比 | 实时系统 |
| **吞吐量** | 单位时间处理的请求数 | 数据处理管道 |
| **正确性** | 正确响应数 / 总响应数 | 计算服务 |
| **新鲜度** | 数据更新及时的比例 | 数据同步服务 |
| **覆盖率** | 成功处理的数据占比 | 批处理作业 |

### SLO（Service Level Objective）

**服务水平目标**：SLI的目标值，是团队内部的可靠性承诺。

**SLO = SLI + 目标值 + 时间窗口**

示例：
- 可用性：99.9%的请求在30天内成功
- 延迟：95%的请求延迟 < 200ms（P95）
- 延迟：99%的请求延迟 < 1s（P99）

### SLA（Service Level Agreement）

**服务水平协议**：与客户的正式契约，包含SLO及违约后果。

**SLA = SLO + 后果（赔偿/惩罚）**

示例：
- 月可用性低于99.9%，赔偿10%费用
- 月可用性低于99.0%，赔偿30%费用

**关键区别**：
- SLO是内部目标，可以激进
- SLA是外部承诺，必须保守
- 通常 SLA目标 < SLO目标（留有buffer）

## SLI设计原则

### 原则一：以用户为中心

**错误做法**：监控服务器CPU使用率
**正确做法**：监控用户请求的成功率和延迟

用户不关心你的服务器负载，只关心"能不能用"和"快不快"。

### 原则二：选择正确的测量点

```
用户 → CDN → 负载均衡 → 应用服务 → 数据库
  ↑                                      
  测量点越靠近用户越好
```

**测量位置选择**：
- **客户端测量**：最真实，但数据收集困难
- **边缘测量**：负载均衡/网关处，推荐
- **服务端测量**：应用内部，可能遗漏网络问题

### 原则三：区分好坏请求

明确定义什么是"成功"：
- HTTP 2xx/3xx = 成功
- HTTP 4xx = 客户端错误（通常不计入SLI）
- HTTP 5xx = 服务端错误
- 超时 = 失败

特殊情况处理：
- 429 Too Many Requests：限流是保护措施，可能不算失败
- 重试后成功：首次失败是否计入？

### 原则四：聚合与分层

**按重要性分层**：
- 核心路径：登录、支付、核心业务 → 更高SLO
- 次要功能：推荐、统计 → 较低SLO

**按用户分层**：
- 付费用户 → 更高SLO
- 免费用户 → 较低SLO

## SLO制定方法

### 方法一：基于历史数据

1. 收集过去3-6个月的SLI数据
2. 计算各百分位数（P50, P90, P95, P99）
3. 选择略低于当前表现的值作为起点

示例：
- 历史可用性：99.95%
- 初始SLO：99.9%（留有余地）

### 方法二：基于业务需求

从业务角度倒推：
- 用户能接受的最大等待时间是多少？
- 多少次失败会导致用户流失？
- 竞争对手的服务水平如何？

### 方法三：基于成本收益

可用性 vs 成本的关系是非线性的：

| 可用性 | 每月停机时间 | 实现成本 |
|--------|-------------|----------|
| 99% | 7.2小时 | 低 |
| 99.9% | 43分钟 | 中 |
| 99.99% | 4.3分钟 | 高 |
| 99.999% | 26秒 | 极高 |

从99.9%提升到99.99%的成本，远高于从99%到99.9%。

### SLO设置建议

**不要追求100%**：
- 100%是不可能的
- 0%错误预算意味着无法做任何变更

**不要太保守**：
- 过低的SLO失去指导意义
- 团队没有改进动力

**定期Review**：
- 每季度评估SLO是否合理
- 根据业务变化调整

## 错误预算机制

### 错误预算计算

**错误预算 = 1 - SLO目标**

示例（30天周期）：

| SLO | 错误预算 | 允许的停机时间 | 允许的失败请求（假设100万QPS） |
|-----|----------|---------------|------------------------------|
| 99% | 1% | 7.2小时 | 259.2亿次 |
| 99.9% | 0.1% | 43分钟 | 25.9亿次 |
| 99.99% | 0.01% | 4.3分钟 | 2.59亿次 |

### 错误预算的使用

错误预算是"可以花费"的：

**计划内消耗**：
- 新功能发布
- 架构升级
- 性能测试
- 混沌工程演练

**计划外消耗**：
- 生产事故
- 性能退化
- 依赖服务故障

### 错误预算策略

**预算充足时**：
- 加快发布节奏
- 尝试新技术
- 进行风险较高的优化

**预算紧张时**：
- 放慢发布节奏
- 增加测试覆盖
- 优先修复稳定性问题

**预算耗尽时**：
- 冻结非紧急发布
- 全力投入稳定性工作
- 启动事故复盘

### 错误预算Policy

制定明确的政策，避免争议：

```
错误预算消耗 < 50%：正常发布节奏
错误预算消耗 50-80%：加强发布审核
错误预算消耗 80-100%：仅允许Bug修复和安全补丁
错误预算耗尽：冻结所有变更，专注稳定性
```

## 多SLO管理

### 复合SLO

一个服务通常需要多个SLO：

```
服务健康 = 可用性 AND 延迟 AND 正确性

其中任何一个不达标，服务都不健康
```

### SLO层级

```
业务SLO
    ├── 服务A的SLO
    │     ├── API可用性
    │     └── API延迟
    └── 服务B的SLO
          ├── 处理成功率
          └── 处理延迟
```

上层SLO由下层SLO组合而成，需要合理分配预算。

### 依赖链SLO

当服务A依赖服务B时：

- 服务B的SLO应该高于服务A
- 否则服务A无法达成其SLO

计算公式：
```
服务A可用性 ≤ 服务B可用性 × 自身可用性

如果服务B是99.9%，服务A自身99.9%
则服务A整体最高99.8%
```

## SLO实施步骤

### 第一步：识别关键用户旅程

列出用户最核心的操作：
1. 用户登录
2. 浏览商品
3. 添加购物车
4. 完成支付

### 第二步：定义SLI

为每个旅程定义可测量的指标：
- 登录成功率
- 页面加载时间
- 支付成功率

### 第三步：设定初始SLO

基于历史数据和业务需求：
- 登录成功率 ≥ 99.9%
- 页面加载P95 ≤ 2s
- 支付成功率 ≥ 99.95%

### 第四步：建立测量系统

- 在合适的位置采集指标
- 建立Dashboard可视化
- 配置告警规则

### 第五步：建立Review机制

- 每周查看SLO达成情况
- 每月进行错误预算Review
- 每季度评估SLO合理性

## 常见陷阱

### 陷阱一：指标爆炸

为每个API设置独立SLO，导致无法管理。

**解决**：聚合为少数关键SLO。

### 陷阱二：虚荣指标

选择容易达成但无意义的指标。

**解决**：指标必须反映用户体验。

### 陷阱三：忽略长尾

只看平均值，忽略P99延迟。

**解决**：关注百分位数，而非平均值。

### 陷阱四：SLO过高

追求不切实际的目标，团队疲于奔命。

**解决**：根据业务需求设定合理目标。

### 陷阱五：缺乏行动

有SLO但不根据错误预算采取行动。

**解决**：建立明确的Policy并执行。

## 总结

| 概念 | 本质 | 关键点 |
|------|------|--------|
| SLI | 测量什么 | 以用户为中心 |
| SLO | 目标是什么 | 合理可达成 |
| SLA | 承诺是什么 | 留有Buffer |
| 错误预算 | 如何权衡 | 指导决策 |

SLI/SLO/错误预算是SRE的核心工具，让可靠性工作从"凭感觉"变成"有数据"，让创新与稳定的权衡有据可依。
