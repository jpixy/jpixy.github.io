## 分布式系统挑战

### 八大谬误

分布式计算的八大谬误（Fallacies of Distributed Computing）：

1. 网络是可靠的 → **网络会断、会延迟、会丢包**
2. 延迟为零 → **网络传输需要时间**
3. 带宽是无限的 → **带宽有限且昂贵**
4. 网络是安全的 → **需要认证和加密**
5. 拓扑不会变化 → **节点会增减、IP会变**
6. 只有一个管理员 → **多团队、多系统**
7. 传输成本为零 → **序列化、网络IO有开销**
8. 网络是同构的 → **不同协议、不同版本**

### 故障类型

| 故障类型 | 描述 | 应对策略 |
|----------|------|----------|
| 崩溃故障 | 节点停止工作 | 冗余、自动重启 |
| 遗漏故障 | 消息丢失 | 重试、确认机制 |
| 时序故障 | 响应超时 | 超时设置、异步处理 |
| 响应故障 | 返回错误结果 | 校验、多副本比对 |
| 拜占庭故障 | 任意恶意行为 | 共识算法、签名验证 |

## CAP理论

### CAP定义

在分布式系统中，以下三者最多只能同时满足两个：

- **C（Consistency）**：一致性 - 所有节点看到相同的数据
- **A（Availability）**：可用性 - 每个请求都能得到响应
- **P（Partition Tolerance）**：分区容错 - 网络分区时系统继续工作

### CAP选择

网络分区是不可避免的，所以实际是在C和A之间选择：

**CP系统**（牺牲可用性）：
- 分区时拒绝服务，保证一致性
- 适用：金融交易、库存系统
- 例子：ZooKeeper、etcd

**AP系统**（牺牲一致性）：
- 分区时继续服务，允许暂时不一致
- 适用：社交媒体、缓存系统
- 例子：Cassandra、DynamoDB

### PACELC

CAP的扩展：

```
如果发生分区(P)：选择A还是C？
否则(E)：选择延迟(L)还是一致性(C)？
```

例如：
- PA/EL：Cassandra（分区时可用，正常时低延迟）
- PC/EC：ZooKeeper（始终一致性优先）
- PA/EC：？（很少见）

## 一致性模型

### 强一致性

**线性一致性（Linearizability）**：
- 所有操作看起来是原子的、瞬时完成的
- 读总能读到最新写入的值
- 实现成本高

**顺序一致性（Sequential Consistency）**：
- 所有进程看到相同的操作顺序
- 顺序可能与实时顺序不同

### 弱一致性

**最终一致性（Eventual Consistency）**：
- 如果没有新的更新，最终所有副本一致
- 读可能读到旧值
- 适用于对一致性要求不高的场景

**因果一致性（Causal Consistency）**：
- 有因果关系的操作保持顺序
- 无因果关系的操作可以乱序

### 读写一致性

| 级别 | 描述 | 适用场景 |
|------|------|----------|
| 读己写 | 能读到自己的写入 | 用户资料更新 |
| 单调读 | 不会读到更旧的数据 | 消息流浏览 |
| 单调写 | 写操作按顺序执行 | 文档编辑 |
| 写后读 | 读操作反映之前的写 | 库存查询 |

## 容错模式

### 冗余（Redundancy）

**数据冗余**：
- 主从复制
- 多副本存储
- 跨机房备份

**计算冗余**：
- 多实例部署
- 跨可用区分布
- 热备/冷备

### 超时与重试

**超时设置原则**：
```
超时时间 = P99延迟 × 安全系数

例：正常P99是200ms
超时设置为500ms-1s
```

**重试策略**：

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| 立即重试 | 失败后马上重试 | 瞬时故障 |
| 固定间隔 | 每隔N秒重试 | 简单场景 |
| 指数退避 | 间隔指数增长 | 避免雪崩 |
| 抖动退避 | 退避+随机抖动 | 避免同时重试 |

**指数退避示例**：
```
第1次重试：等待1秒
第2次重试：等待2秒
第3次重试：等待4秒
第4次重试：等待8秒
最大等待：30秒
最大重试：5次
```

**重试风险**：
- 重试放大：1次请求变N次
- 重试风暴：大量客户端同时重试
- 解决：退避+抖动+限制重试次数

### 幂等性

确保多次执行结果相同：

**幂等操作**：
- GET请求
- DELETE（删除同一资源）
- 带唯一ID的创建操作

**非幂等操作**：
- POST创建（每次创建新资源）
- 计数器增加

**实现幂等**：
```
# 使用幂等键
POST /orders
X-Idempotency-Key: uuid-12345

# 服务端检查：
if exists(idempotency_key):
    return cached_response
else:
    process_request()
    cache_response(idempotency_key)
```

## 熔断器模式

### 熔断器原理

```
Closed（正常）
    ↓ 错误率超过阈值
Open（熔断）→ 直接返回错误，不调用下游
    ↓ 冷却时间后
Half-Open（半开）→ 允许部分请求
    ↓ 请求成功
Closed（恢复正常）
```

### 熔断器配置

```yaml
circuit_breaker:
  # 触发熔断的条件
  error_threshold_percentage: 50  # 错误率超过50%
  request_volume_threshold: 20     # 至少20个请求
  
  # 熔断持续时间
  sleep_window_ms: 5000           # 5秒后进入半开
  
  # 半开状态
  half_open_requests: 5           # 允许5个请求测试
```

### 熔断 vs 重试

| 重试 | 熔断 |
|------|------|
| 处理瞬时故障 | 处理持续故障 |
| 增加请求量 | 减少请求量 |
| 可能加重问题 | 保护下游服务 |

**最佳实践**：先重试，多次失败后熔断

## 降级策略

### 降级类型

**功能降级**：
- 关闭非核心功能
- 例：关闭推荐、关闭评论

**数据降级**：
- 返回缓存数据
- 返回默认值
- 例：库存查询失败返回"有货"

**用户降级**：
- 限制部分用户
- 例：非VIP用户排队

### 降级触发

**自动降级**：
- 依赖服务不可用
- 错误率超过阈值
- 延迟超过阈值

**手动降级**：
- 预期的大促
- 已知的故障
- 通过开关控制

### 降级开关

```python
class FeatureFlag:
    def is_enabled(self, feature, user_id=None):
        # 检查全局开关
        if self.is_globally_disabled(feature):
            return False
        
        # 检查灰度规则
        if self.is_in_rollout(feature, user_id):
            return True
            
        return False

# 使用
if feature_flag.is_enabled("recommendation"):
    return get_recommendations(user)
else:
    return get_default_recommendations()
```

## 限流

### 限流算法

**计数器算法**：
```
每个时间窗口内限制N个请求
缺点：窗口边界可能突发2N个请求
```

**滑动窗口**：
```
将窗口分成多个小窗口
解决边界突发问题
```

**漏桶算法**：
```
请求进入桶，以固定速率处理
多余请求丢弃或排队
适合平滑流量
```

**令牌桶算法**：
```
以固定速率生成令牌
请求需要获取令牌
允许一定程度的突发
```

### 限流维度

| 维度 | 示例 |
|------|------|
| 全局 | 系统总QPS不超过10万 |
| 用户 | 单用户每秒最多10个请求 |
| IP | 单IP每分钟最多100个请求 |
| 接口 | 单接口每秒最多1000个请求 |

### 限流响应

**拒绝请求**：
```
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

**排队等待**：
```
请求进入队列，等待处理
超时后返回错误
```

## 背压（Backpressure）

### 什么是背压

当下游处理能力不足时，通知上游减缓发送速度。

**没有背压**：
```
Producer(快) → Buffer溢出 → 数据丢失
```

**有背压**：
```
Producer(快) → Buffer满 → 减速 → 恢复 → 加速
```

### 背压策略

**丢弃策略**：
- 丢弃最新数据
- 丢弃最旧数据
- 随机丢弃

**阻塞策略**：
- 生产者等待
- 适合不能丢失数据的场景

**采样策略**：
- 只处理部分数据
- 适合统计类场景

## 故障隔离

### 舱壁模式（Bulkhead）

像船舱一样隔离故障：

**线程池隔离**：
```
服务A → 线程池A（10线程）
服务B → 线程池B（20线程）

服务A阻塞只影响线程池A
```

**实例隔离**：
```
用户群A → 实例组A
用户群B → 实例组B

一组故障不影响另一组
```

### 故障域

**可用区隔离**：
- 跨AZ部署
- 单AZ故障不影响整体

**区域隔离**：
- 跨Region部署
- 区域级灾难恢复

**单元化架构**：
- 用户分配到固定单元
- 单元间完全隔离

## 总结

| 模式 | 解决问题 | 关键点 |
|------|----------|--------|
| 超时 | 无限等待 | 合理设置，避免过短或过长 |
| 重试 | 瞬时故障 | 指数退避+抖动+限制次数 |
| 幂等 | 重复请求 | 幂等键、去重机制 |
| 熔断 | 持续故障 | 保护下游，快速失败 |
| 降级 | 资源不足 | 保证核心功能 |
| 限流 | 过载保护 | 多维度、多策略 |
| 隔离 | 故障扩散 | 舱壁、故障域 |

**设计原则**：
1. 假设一切都会失败
2. 设计可降级的系统
3. 快速失败优于慢慢等待
4. 隔离故障，防止蔓延
