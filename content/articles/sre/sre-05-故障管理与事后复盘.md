## 事故管理概述

### 事故的定义

**事故（Incident）**：任何导致服务降级或中断，需要人工干预恢复的事件。

**事故 vs 告警**：
- 告警是信号，事故是确认的问题
- 一个事故可能触发多个告警
- 并非所有告警都会成为事故

### 事故管理目标

1. **最小化影响时间**：快速检测、快速恢复
2. **防止复发**：找到根因，系统性修复
3. **持续改进**：从事故中学习，提升系统韧性
4. **保护团队**：Blameless文化，避免追责个人

---

## 事故分级

### 分级标准

| 级别 | 影响范围 | 用户影响 | 示例 |
|------|----------|----------|------|
| **SEV1** | 全站/核心业务 | 所有用户无法使用 | 支付系统完全瘫痪 |
| **SEV2** | 核心功能 | 大量用户受影响 | 登录成功率降至80% |
| **SEV3** | 部分功能 | 部分用户受影响 | 某地区访问缓慢 |
| **SEV4** | 边缘功能 | 少量用户受影响 | 头像上传失败 |

### 分级的意义

不同级别对应不同的：
- **响应速度**：SEV1立即响应，SEV4可以排队
- **参与人员**：SEV1全员响应，SEV4 On-Call独立处理
- **沟通频率**：SEV1每15分钟更新，SEV4解决后通知
- **复盘要求**：SEV1/2必须复盘，SEV3/4可选

---

## 事故响应流程

### 阶段一：检测（Detection）

**触发来源**：
- 监控告警（主动发现）
- 用户报告（被动发现）
- 内部人员发现

**响应动作**：
1. 确认告警，判断是否为真实事故
2. 初步评估影响范围
3. 确定事故级别

### 阶段二：响应（Response）

**On-Call职责**：
1. **确认（Acknowledge）**：表明已接手
2. **评估**：确定严重程度
3. **升级**：必要时呼叫支援
4. **通知**：告知相关方

**SEV1/2响应**：
- 建立War Room（专用沟通频道）
- 指定Incident Commander（IC）
- 定期状态更新（每15-30分钟）

### 阶段三：缓解（Mitigation）

**核心原则**：恢复服务优先于找根因

**常用缓解手段**：

| 手段 | 适用场景 | 风险 |
|------|----------|------|
| 回滚 | 发布后出问题 | 低 |
| 重启 | 内存泄漏、死锁 | 低 |
| 扩容 | 流量突增 | 低 |
| 切流量 | 单机房故障 | 中 |
| 降级 | 依赖服务故障 | 中 |
| 限流 | 系统过载 | 中 |

**缓解 vs 修复**：
- 缓解：临时措施，快速恢复服务
- 修复：根本解决，可以稍后进行

### 阶段四：恢复（Recovery）

**恢复确认清单**：
- [ ] 核心指标恢复正常
- [ ] 告警解除
- [ ] 用户反馈恢复
- [ ] 无二次问题
- [ ] 监控加强观察

**观察期**：
- 恢复后保持关注30-60分钟
- 确认没有复发或级联问题

### 阶段五：复盘（Post-mortem）

- SEV1/2：48小时内完成
- SEV3：一周内完成
- SEV4：可选

## 事故指挥官（IC）

### IC的职责

**负责**：
- 协调各方资源
- 推动问题解决
- 对外沟通状态
- 决策升级/降级

**不负责**：
- 亲自排查技术问题
- 写代码修复
- 被技术细节淹没

### IC的核心技能

**沟通能力**：
- 清晰简洁地描述问题
- 定期更新状态
- 管理期望

**协调能力**：
- 分配任务到合适的人
- 避免多人做同一件事
- 及时呼叫支援

**决策能力**：
- 信息不完整时做决策
- 权衡风险与收益
- 知道何时升级

### IC沟通模板

**状态更新模板**：
```
【事故更新 - HH:MM】
状态：处理中/已缓解/已恢复
影响：[描述用户影响]
当前进展：[正在做什么]
下一步：[接下来计划]
ETA：[预计恢复时间，如有]
```

## 根因分析

### 5 Whys方法

连续问"为什么"，直到找到根因：

```
问题：网站宕机10分钟

Why 1: 为什么宕机？
→ 数据库连接池耗尽

Why 2: 为什么连接池耗尽？
→ 慢查询占用连接不释放

Why 3: 为什么有慢查询？
→ 新功能上线引入了全表扫描

Why 4: 为什么没发现全表扫描？
→ 代码Review没有检查SQL

Why 5: 为什么Review没检查？
→ 没有SQL Review的Checklist

根因：缺乏SQL Review规范
改进：建立SQL Review Checklist，CI中加入慢查询检测
```

### 因果分析图

复杂事故可能有多个原因链：

```
                    ┌─ 监控缺失 ─┐
                    │            │
流量突增 ─→ 系统过载 ─┼─ 扩容超时 ─┼─→ 服务不可用
                    │            │
                    └─ 限流失效 ─┘
```

每条链都需要分析和改进。

### 区分根因与触发因素

**触发因素（Trigger）**：直接导致问题的事件
- 例：新版本发布

**根因（Root Cause）**：系统性问题
- 例：缺乏金丝雀发布机制

修复触发因素只能防止这次问题复发，修复根因才能防止同类问题。

## Blameless事后复盘

### Blameless文化

**核心理念**：人会犯错，系统应该容错

**Blameless不是**：
- 不追究责任
- 不关心谁做了什么
- 假装错误没发生

**Blameless是**：
- 关注"系统为什么允许这个错误发生"
- 关注"如何让系统更健壮"
- 假设每个人都在尽力做正确的事

### 复盘会议

**参与者**：
- 事故相关人员
- On-Call
- IC
- 服务Owner
- （可选）相关团队

**会议议程**：
1. 时间线回顾（15分钟）
2. 根因分析（20分钟）
3. 改进项讨论（20分钟）
4. Action Items确认（5分钟）

**会议规则**：
- 聚焦系统改进，不指责个人
- 鼓励分享信息，不隐瞒
- 基于事实讨论，不猜测

### 复盘文档模板

```markdown
# 事故复盘：[事故标题]

## 概述
- 日期：2026-01-19
- 级别：SEV2
- 持续时间：45分钟
- 影响：支付成功率降至85%

## 时间线
| 时间 | 事件 |
|------|------|
| 10:00 | 新版本发布 |
| 10:15 | 告警触发：支付错误率上升 |
| 10:18 | On-Call确认告警 |
| 10:25 | 定位到数据库连接问题 |
| 10:35 | 执行回滚 |
| 10:45 | 服务恢复正常 |

## 根因分析
### 触发因素
新版本引入的代码存在数据库连接泄漏

### 根因
1. 代码Review未发现资源泄漏
2. 缺乏连接池监控告警
3. 金丝雀发布覆盖率不足

## 影响分析
- 用户影响：约5000笔支付失败
- 业务损失：预估$XXX

## 改进项
| 改进项 | Owner | 优先级 | 截止日期 |
|--------|-------|--------|----------|
| 添加连接池监控 | @alice | P1 | 2026-01-26 |
| Code Review增加资源检查 | @bob | P2 | 2026-02-01 |
| 扩大金丝雀比例 | @charlie | P2 | 2026-02-01 |

## 经验教训
- 数据库连接是关键资源，需要专门监控
- 发布后需要关注更长时间的指标变化
```

## 改进项跟踪

### 改进项分类

**P0（立即）**：
- 必须在下次发布前完成
- 例：修复会导致数据丢失的Bug

**P1（紧急）**：
- 一周内完成
- 例：添加关键监控

**P2（重要）**：
- 一个月内完成
- 例：流程改进

**P3（一般）**：
- 纳入正常迭代
- 例：文档完善

### 跟踪机制

**工单系统**：
- 每个改进项创建工单
- 指定Owner和截止日期
- 关联到复盘文档

**定期Review**：
- 每周检查进度
- 每月汇总完成情况
- 未完成项需要说明原因

### 避免改进项流产

**常见问题**：
- 复盘时热情高涨，之后无人跟进
- 改进项太多，无法全部完成
- 优先级被日常工作淹没

**解决方案**：
- 限制改进项数量（每次3-5个）
- 指定明确的Owner
- 纳入团队OKR
- 领导层关注跟踪

---

## 事故度量

### 关键指标

**事故数量**：
- 各级别事故数量趋势
- 按原因分类统计

**影响时间**：
- MTTD（Mean Time to Detect）：平均检测时间
- MTTA（Mean Time to Acknowledge）：平均确认时间
- MTTM（Mean Time to Mitigate）：平均缓解时间
- MTTR（Mean Time to Resolve）：平均恢复时间

**复盘质量**：
- 复盘完成率
- 改进项完成率
- 复发事故比例

### 趋势分析

每月/季度分析：
- 事故数量是上升还是下降？
- 哪类问题最常见？
- 改进措施是否有效？
- 复发事故是否减少？

---

## 总结

| 阶段 | 关键点 |
|------|--------|
| 检测 | 快速识别，准确分级 |
| 响应 | 明确角色，有序协调 |
| 缓解 | 恢复优先，临时方案可接受 |
| 恢复 | 确认正常，持续观察 |
| 复盘 | Blameless，聚焦系统改进 |
| 跟踪 | 明确Owner，确保落地 |

事故不可避免，但**同样的事故不应该发生两次**。这是事故管理的核心目标。
