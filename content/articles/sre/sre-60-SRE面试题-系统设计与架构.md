# 一、高可用设计

## 1.1 如何设计高可用系统？

**标准答案**：

```
高可用设计原则：

1. 冗余
   - 无单点故障
   - 多副本部署
   - 跨机房/跨地域

2. 故障隔离
   - 服务拆分
   - 资源隔离
   - 故障域划分

3. 快速恢复
   - 自动故障检测
   - 自动故障转移
   - 快速回滚能力

4. 容错设计
   - 超时重试
   - 熔断降级
   - 限流保护

高可用等级：
| 可用性 | 年度宕机 | 月度宕机 |
|--------|----------|----------|
| 99%    | 3.65天   | 7.3小时  |
| 99.9%  | 8.76小时 | 43.8分钟 |
| 99.99% | 52.6分钟 | 4.38分钟 |
| 99.999%| 5.26分钟 | 26秒     |

架构要点：

                    └──────┬──────┘

                    ┌──────▼──────┐
```

## 1.2 如何实现故障转移？

**标准答案**：

```
故障转移类型：

1. 主从切换（数据库）
   - 检测主库故障
   - 选举新主库
   - 更新应用配置
   
   MySQL: MHA, Orchestrator
   Redis: Sentinel
   PostgreSQL: Patroni

2. 负载均衡故障转移
   - 健康检查机制
   - 自动剔除故障节点
   - 权重调整

   Nginx: upstream health check
   HAProxy: server check
   AWS: ELB health check

3. 应用层故障转移
   - 服务发现
   - 客户端负载均衡
   - 重试机制

4. DNS故障转移
   - DNS健康检查
   - 自动切换记录
   - 低TTL配置

故障检测机制：
- 主动探测：定期发送心跳
- 被动检测：请求失败计数
- 仲裁机制：避免脑裂

故障转移流程：
1. 检测故障（多次确认）
2. 触发告警
3. 执行切换
4. 更新路由
5. 通知相关方
```

## 1.3 如何避免脑裂？

**标准答案**：

```
脑裂（Split-Brain）：
- 集群分区后，多个节点都认为自己是主节点
- 导致数据不一致
- 非常危险的情况

预防措施：

1. 奇数节点 + 多数派（Quorum）
   - 至少N/2+1个节点同意
   - 少数派无法选举成功
   - 如：3节点允许1个故障

2. Fencing机制
   - 确保旧主节点被隔离
   - STONITH (Shoot The Other Node In The Head)
   - 强制关闭旧主节点

3. 租约机制
   - 主节点定期续约
   - 租约过期自动降级
   - 如：etcd的lease

4. 仲裁节点
   - 独立的仲裁服务
   - 判断谁是真正的主节点

5. 共享存储锁
   - 使用共享存储的锁机制
   - 只有获得锁才能成为主节点

Redis Sentinel防脑裂配置：
min-replicas-to-write 1
min-replicas-max-lag 10
# 至少1个从节点在线且延迟<10秒，主节点才接受写入
```

## 1.4 多活架构怎么设计？

**标准答案**：

```
多活类型：

1. 同城双活
   - 两个机房在同一城市
   - 延迟低（<3ms）
   - 可以同步复制

2. 异地双活
   - 两个机房在不同城市
   - 延迟较高（>20ms）
   - 通常异步复制

3. 异地多活
   - 三个及以上地域
   - 复杂度最高
   - 如：两地三中心

挑战和解决：

1. 数据一致性
   - 单元化：按用户分片
   - 每个单元有完整数据
   - 跨单元操作特殊处理

2. 流量调度
   - DNS智能解析
   - 就近接入
   - 容灾切换

3. 数据同步
   - 异步复制
   - 最终一致性
   - 冲突解决

4. 中间件
   - 消息队列：双向同步
   - 缓存：多级缓存
   - 数据库：分库分表

阿里双十一架构（简化）：
┌────────────────┐    ┌────────────────┐
│   单元A (华东)  │◄──►│   单元B (华南)  │
│  用户ID%2=0   │    │  用户ID%2=1   │
│  全量数据      │    │  全量数据      │
└───────┬────────┘    └───────┬────────┘
        │                     │
        └─────────┬───────────┘
                  │
           ┌──────▼──────┐
           │  数据同步层  │
           └─────────────┘
```

# 二、负载均衡

## 2.1 负载均衡算法有哪些？

**标准答案**：

```
常见负载均衡算法：

1. 轮询（Round Robin）
   - 依次分配请求
   - 简单公平
   - 不考虑服务器差异

2. 加权轮询（Weighted Round Robin）
   - 按权重分配
   - 性能好的服务器权重高
   - 考虑服务器差异

3. 最少连接（Least Connections）
   - 分配给连接数最少的服务器
   - 适合长连接场景

4. 加权最少连接
   - 结合权重和连接数

5. IP哈希（IP Hash）
   - 根据客户端IP哈希
   - 同一IP总是到同一服务器
   - 会话保持

6. URL哈希
   - 根据请求URL哈希
   - 提高缓存命中率

7. 一致性哈希
   - 节点变化时影响最小
   - 适合缓存场景

8. 随机
   - 随机选择服务器
   - 简单，大数定律保证均衡

Nginx配置示例：
upstream backend {
    least_conn;  # 最少连接
    server backend1.example.com weight=5;
    server backend2.example.com weight=3;
    server backend3.example.com backup;  # 备用
}
```

## 2.2 四层和七层负载均衡的区别？

**标准答案**：

```
四层负载均衡（L4）：
- 基于IP和端口
- 转发TCP/UDP数据包
- 性能高
- 无法基于内容路由

代表：LVS, F5, AWS NLB

七层负载均衡（L7）：
- 基于应用层协议（HTTP）
- 可以根据URL、Header路由
- 可以做SSL卸载
- 性能相对较低

代表：Nginx, HAProxy, AWS ALB

对比：
| 特性 | L4 | L7 |
|------|----|----|
| 协议层 | 传输层 | 应用层 |
| 路由依据 | IP:Port | URL/Header/Cookie |
| SSL卸载 | 不支持 | 支持 |
| 会话保持 | IP Hash | Cookie |
| 性能 | 高 | 相对低 |
| 典型场景 | 数据库、TCP服务 | Web服务 |

混合架构：
Internet → L4(LVS) → L7(Nginx) → 应用服务器
                       ↓
                    SSL卸载
                    路由分发
```

## 2.3 如何实现会话保持？

**标准答案**：

```
会话保持方案：

1. IP Hash
   - 根据客户端IP哈希到固定服务器
   - 问题：NAT环境IP相同
   
   upstream backend {
       ip_hash;
       server backend1;
       server backend2;
   }

2. Cookie注入
   - 负载均衡器注入Cookie
   - 根据Cookie路由
   
   upstream backend {
       sticky cookie srv_id expires=1h;
   }

3. URL重写
   - 将服务器标识加入URL
   - 如：session_id=server1

4. 应用层会话共享
   - 将Session存储到Redis
   - 任意服务器都可读取
   - 推荐方案

5. JWT Token
   - 无状态认证
   - 不需要会话保持
   - 现代化方案

推荐：
- 无状态设计 > 共享Session > 会话保持
- 尽量避免依赖会话保持
```

# 三、限流降级

## 3.1 限流算法有哪些？

**标准答案**：

```
常见限流算法：

1. 计数器（固定窗口）
   - 固定时间窗口内计数
   - 超过阈值拒绝
   - 问题：临界点突刺

   实现：
   if (count < threshold) {
       count++;
       process();
   } else {
       reject();
   }

2. 滑动窗口
   - 将窗口分成多个小格
   - 滑动统计
   - 解决临界点问题

3. 漏桶算法（Leaky Bucket）
   - 请求进入桶中
   - 固定速率流出
   - 平滑流量
   - 问题：无法应对突发

   特点：
   - 流入速率可变
   - 流出速率固定

4. 令牌桶算法（Token Bucket）
   - 固定速率放入令牌
   - 请求消耗令牌
   - 可以应对突发
   - 最常用

   特点：
   - 允许一定程度的突发
   - 桶满了令牌会丢弃

比较：
| 算法 | 突发流量 | 平滑度 | 复杂度 |
|------|----------|--------|--------|
| 计数器 | 有边界问题 | 差 | 低 |
| 滑动窗口 | 较好 | 中 | 中 |
| 漏桶 | 不支持 | 高 | 中 |
| 令牌桶 | 支持 | 高 | 中 |
```

## 3.2 熔断器模式是什么？

**标准答案**：

```
熔断器模式（Circuit Breaker）：
- 当下游服务故障时，快速失败
- 避免级联故障
- 给下游服务恢复时间

三种状态：

1. Closed（关闭）
   - 正常状态
   - 请求正常转发
   - 统计失败率

2. Open（打开）
   - 熔断状态
   - 请求直接拒绝
   - 不调用下游服务

3. Half-Open（半开）
   - 尝试恢复
   - 放行部分请求
   - 成功则关闭，失败则打开

状态转换：
       ┌────────────────────────────┐
       │                            │
       ▼                            │
   ┌────────┐    失败率>阈值    ┌────────┐
   │ Closed │ ───────────────► │  Open  │
   └────────┘                   └────────┘
       ▲                            │
       │      成功                  │ 超时
       │       │                    │
       │   ┌───┴────┐               │
       └───│Half-Open│◄─────────────┘
           └────────┘
               │
               │ 失败
               ▼
           ┌────────┐
           │  Open  │
           └────────┘

配置参数：
- 失败率阈值：50%
- 统计窗口：10秒
- 最小请求数：10
- 熔断时间：30秒
- 半开状态请求数：5

Hystrix/Resilience4j实现此模式
```

## 3.3 降级策略有哪些？

**标准答案**：

```
降级策略：

1. 服务降级
   - 关闭非核心功能
   - 如：评论、推荐
   - 保证核心功能可用

2. 返回缓存
   - 返回之前缓存的数据
   - 数据可能不是最新
   - 但比返回错误好

3. 返回默认值
   - 返回预设的默认响应
   - 如：默认商品列表

4. 返回兜底页面
   - 静态页面
   - 友好的错误提示

5. 功能降级
   - 异步改同步
   - 批量改单个
   - 精确改模糊

6. 数据降级
   - 减少返回字段
   - 降低数据精度
   - 分页数量减少

降级触发条件：
- 错误率超过阈值
- 响应时间超过阈值
- 资源使用率过高
- 人工触发（大促期间）

代码示例：
def get_recommendations(user_id):
    try:
        return recommendation_service.get(user_id)
    except ServiceUnavailable:
        # 降级：返回热门商品
        return get_hot_products()
    except Timeout:
        # 降级：返回缓存
        return cache.get(f"rec:{user_id}", [])
```

# 四、分布式系统

## 4.1 CAP理论是什么？

**标准答案**：

```
CAP理论：

C - Consistency（一致性）
    所有节点同一时刻看到的数据相同

A - Availability（可用性）
    每个请求都能收到响应（不保证最新数据）

P - Partition Tolerance（分区容错性）
    网络分区时系统继续运行

CAP定理：
分布式系统只能同时满足其中两个，不能三者兼得。

由于网络分区不可避免，实际是在C和A之间权衡：

CP系统：
- 保证一致性，牺牲可用性
- 分区时拒绝部分请求
- 如：ZooKeeper, etcd, HBase

AP系统：
- 保证可用性，牺牲一致性
- 分区时返回可能不一致的数据
- 如：Cassandra, DynamoDB, Redis

实际应用：
- 金融场景：CP优先
- 社交场景：AP优先
- 大多数场景：最终一致性
```

---

## 4.2 BASE理论是什么？

**标准答案**：

```
BASE理论：
CAP中AP的延伸，是对一致性的妥协

BA - Basically Available（基本可用）
    故障时，允许部分功能降级
    如：响应时间变长、部分功能不可用

S - Soft State（软状态）
    允许数据存在中间状态
    不同节点数据可以暂时不一致

E - Eventually Consistent（最终一致性）
    经过一段时间后，数据最终会一致
    而不是实时一致

最终一致性的实现：

1. 读时修复（Read Repair）
   - 读取时发现不一致，触发修复

2. 写时修复（Write Repair）
   - 写入时同步到所有节点

3. 异步修复（Anti-Entropy）
   - 后台定期检查和修复

4. Merkle Tree
   - 快速检测数据差异

一致性级别：
强一致性 > 会话一致性 > 因果一致性 > 最终一致性
```

## 4.3 分布式事务怎么实现？

**标准答案**：

```
分布式事务方案：

1. 2PC（两阶段提交）
   
   第一阶段（Prepare）：
   - 协调者询问所有参与者
   - 参与者执行事务但不提交
   - 返回准备结果
   
   第二阶段（Commit/Rollback）：
   - 全部准备成功 → 提交
   - 有一个失败 → 回滚
   
   问题：同步阻塞、单点故障、数据不一致

2. 3PC（三阶段提交）
   - 增加CanCommit阶段
   - 引入超时机制
   - 减少阻塞

3. TCC（Try-Confirm-Cancel）
   
   Try：预留资源
   Confirm：确认执行
   Cancel：取消预留
   
   示例（转账）：
   Try: 冻结转出金额
   Confirm: 扣款 + 入账
   Cancel: 解冻
   
   优点：无锁，高性能
   缺点：业务侵入性强

4. Saga
   
   - 将事务拆分为多个本地事务
   - 每个事务有对应的补偿操作
   - 失败时执行补偿
   
   正向：T1 → T2 → T3
   补偿：C1 ← C2 ← C3
   
   适用：长事务、跨服务

5. 消息队列最终一致性
   
   - 本地事务 + 消息发送
   - 消息消费 + 本地事务
   - 通过消息保证最终一致
   
   如：RocketMQ事务消息

选择建议：
- 强一致要求：2PC/3PC
- 高性能要求：TCC
- 长事务：Saga
- 最终一致：消息队列
```

## 4.4 如何设计分布式ID生成器？

**标准答案**：

```
分布式ID需求：
- 全局唯一
- 趋势递增
- 高性能
- 高可用

方案对比：

1. UUID
   - 本地生成，无依赖
   - 无序，不适合作为主键
   - 36个字符，存储空间大

2. 数据库自增
   - 简单，递增
   - 单点瓶颈
   - 可通过步长解决

   # 节点1: 1,3,5,7...
   # 节点2: 2,4,6,8...

3. 号段模式
   - 一次获取一批ID
   - 本地分发
   - 减少数据库访问

4. Redis
   - INCR命令生成
   - 高性能
   - 需要考虑持久化

5. Snowflake（雪花算法）
   
   64位结构：
   0 | 41位时间戳 | 10位机器ID | 12位序列号
   
   - 1位符号位（0）
   - 41位时间戳（69年）
   - 10位机器ID（1024节点）
   - 12位序列号（每毫秒4096个）
   
   优点：
   - 趋势递增
   - 高性能（本地生成）
   - 可排序
   
   问题：
   - 时钟回拨
   - 机器ID分配

6. Leaf（美团）
   - 号段模式 + Snowflake
   - 支持两种模式
   - 开源可用

7. UidGenerator（百度）
   - 基于Snowflake
   - 解决时钟回拨
```

## 4.5 如何设计秒杀系统？

**标准答案**：

```
秒杀系统挑战：
- 瞬时高并发
- 库存准确
- 防止超卖
- 用户体验

架构设计：

1. 流量入口层
   - CDN缓存静态资源
   - 按钮防抖
   - 验证码/答题

2. 接入层
   - 负载均衡
   - 限流（令牌桶）
   - 过滤无效请求

3. 应用层
   - 读写分离
   - 本地缓存
   - 异步处理

4. 缓存层
   - Redis预扣库存
   - 防止超卖
   - 请求排队

5. 数据层
   - 异步落库
   - 分库分表

核心流程：
1. 用户请求 → 限流过滤
2. 检查资格 → 过滤黄牛
3. Redis预扣库存 → 防止超卖
4. 生成订单 → 发送MQ
5. 异步处理 → 写入数据库
6. 返回结果 → 轮询/推送

库存扣减（Redis Lua）：
local stock = redis.call('get', KEYS[1])
if not stock or tonumber(stock) <= 0 then
    return 0
end
redis.call('decr', KEYS[1])
return 1

关键技术：
- 限流：令牌桶
- 缓存：Redis
- 异步：消息队列
- 分布式锁：防止并发
- 熔断降级：保护系统
```

## 4.6 微服务架构的挑战？

**标准答案**：

```
微服务带来的挑战：

1. 服务发现
   - 服务实例动态变化
   - 需要注册中心
   - Consul, Eureka, Nacos

2. 配置管理
   - 配置分散
   - 需要配置中心
   - Apollo, Nacos, Spring Cloud Config

3. 服务通信
   - RPC vs HTTP
   - 超时、重试、熔断
   - gRPC, HTTP/REST

4. 数据一致性
   - 分布式事务
   - 最终一致性
   - Saga, TCC

5. 链路追踪
   - 问题定位困难
   - 需要分布式追踪
   - Jaeger, Zipkin

6. 日志聚合
   - 日志分散
   - 需要集中收集
   - ELK, Loki

7. 部署复杂
   - 服务数量多
   - 依赖关系复杂
   - Kubernetes, Docker

8. 测试困难
   - 集成测试复杂
   - 需要Mock
   - 契约测试

9. 监控告警
   - 监控点增多
   - 告警关联
   - Prometheus + Grafana

10. 安全
    - 服务间认证
    - API Gateway
    - Service Mesh
```

## 总结

### 高频考点速查

| 主题 | 核心概念 | 关键技术 |
|------|----------|----------|
| 高可用 | 冗余/故障隔离/快速恢复 | 主从/集群 |
| 负载均衡 | 轮询/一致性哈希 | Nginx/LVS |
| 限流 | 令牌桶/漏桶 | Sentinel |
| 熔断 | 三态转换 | Hystrix |
| CAP | 一致性/可用性/分区容错 | CP/AP选择 |
| 分布式事务 | 2PC/TCC/Saga | Seata |
| 分布式ID | Snowflake | Leaf |
| 秒杀 | 限流/缓存/异步 | Redis/MQ |
