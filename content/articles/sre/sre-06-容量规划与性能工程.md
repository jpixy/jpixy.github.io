## 容量规划概述

### 什么是容量规划

容量规划是**预测未来资源需求，确保系统能够承载业务增长**的过程。

**核心问题**：
- 当前系统能承载多少流量？
- 业务增长后需要多少资源？
- 何时需要扩容？扩多少？
- 如何平衡性能与成本？

### 容量规划的意义

**太少容量**：
- 服务降级或不可用
- 用户体验差
- 业务损失

**太多容量**：
- 资源浪费
- 成本过高
- 投资回报率低

**目标**：在满足SLO的前提下，以最优成本运行系统。

## 需求预测

### 数据收集

**历史数据**：
- 过去12个月的流量趋势
- 峰值出现的时间和原因
- 增长率（日/周/月/年）

**业务输入**：
- 预计用户增长
- 新功能上线计划
- 营销活动安排
- 季节性因素（如电商大促）

### 预测方法

**线性预测**：
```
未来流量 = 当前流量 × (1 + 增长率)^时间
```
适用于稳定增长的业务。

**基于业务事件**：
```
大促期间流量 = 日常流量 × 历史峰值倍数
```
适用于有明确事件的场景。

**机器学习预测**：
- 时间序列分析（ARIMA、Prophet）
- 考虑多种因素的综合预测
- 适用于复杂场景

### 预测的不确定性

预测不可能100%准确，需要：
- 留出Buffer（通常20-30%）
- 定期修正预测
- 建立快速扩容能力

## 容量建模

### 资源与负载的关系

理解系统的扩展特性：

**线性扩展**：
- 2倍流量 → 2倍资源
- 理想情况，少数系统能做到

**亚线性扩展**：
- 2倍流量 → 1.5倍资源
- 存在共享资源的优化

**超线性扩展**：
- 2倍流量 → 3倍资源
- 存在瓶颈或争抢

### 容量模型

**基于资源的模型**：
```
所需实例数 = 峰值QPS / 单实例承载QPS × (1 + Buffer)
```

**基于SLO的模型**：
```
在目标延迟(P99 < 200ms)下，单实例能处理多少QPS？
通过压测确定这个值，再计算所需实例数
```

### 瓶颈识别

系统容量由最弱的环节决定：

```
请求 → Web层 → 应用层 → 缓存 → 数据库
        1000     800      5000    500
        QPS      QPS      QPS     QPS
                                  ↑
                               瓶颈在这里
```

先找瓶颈，再针对性优化或扩容。

## 压力测试

### 测试类型

| 类型 | 目的 | 方法 |
|------|------|------|
| **基准测试** | 确定单实例容量 | 固定负载，测量性能 |
| **负载测试** | 验证目标容量 | 逐步增加负载到目标值 |
| **压力测试** | 找到系统极限 | 持续增加直到系统崩溃 |
| **浸泡测试** | 发现长期问题 | 中等负载持续运行 |
| **峰值测试** | 验证突发承载 | 瞬间大流量冲击 |

### 压测环境

**生产环境压测**：
- 最真实的结果
- 风险：可能影响真实用户
- 方案：深夜进行、流量隔离、灰度压测

**独立压测环境**：
- 安全，不影响生产
- 风险：环境差异导致结果不准
- 方案：尽量模拟生产配置

### 压测指标

**性能指标**：
- 吞吐量（QPS/TPS）
- 延迟（P50/P90/P95/P99）
- 错误率

**资源指标**：
- CPU使用率
- 内存使用率
- 网络带宽
- 磁盘IO

**饱和度指标**：
- 线程池使用率
- 连接池使用率
- 队列长度

### 压测结果分析

**理想曲线**：
```
QPS ↑
    |      ____平台期
    |     /
    |    /
    |   /
    |  /
    | /
    |/____________→ 并发数
```

**关键点**：
- 拐点：性能开始下降的点
- 最大QPS：能达到的最高吞吐
- 崩溃点：系统不可用的点

## 性能优化

### 优化原则

1. **先测量，再优化**：没有数据就是瞎猜
2. **优化瓶颈**：解决最慢的环节
3. **避免过早优化**：先让系统工作，再让它快
4. **权衡取舍**：性能 vs 可维护性 vs 成本

### 常见优化方向

**应用层**：
- 算法优化
- 减少不必要的计算
- 异步处理
- 批量操作

**缓存优化**：
- 增加缓存层
- 提高缓存命中率
- 减少缓存穿透

**数据库优化**：
- 索引优化
- 查询优化
- 读写分离
- 分库分表

**网络优化**：
- 减少网络往返
- 压缩传输数据
- 使用CDN
- 连接复用

**基础设施**：
- 垂直扩展（更强的机器）
- 水平扩展（更多实例）
- 优化配置参数

### 性能分析工具

**应用层**：
- Profiler（CPU、内存分析）
- APM工具（链路追踪）
- 火焰图

**系统层**：
- top/htop
- vmstat/iostat
- perf
- eBPF工具

**数据库**：
- 慢查询日志
- EXPLAIN分析
- 数据库监控

## 扩展策略

### 垂直扩展（Scale Up）

增加单机资源：更多CPU、更大内存、更快磁盘

**优点**：
- 简单，无需改架构
- 无分布式复杂性

**缺点**：
- 有上限
- 单点故障风险
- 成本非线性增长

### 水平扩展（Scale Out）

增加实例数量

**优点**：
- 理论上无上限
- 更好的容错性
- 成本线性

**缺点**：
- 需要无状态设计
- 分布式复杂性
- 数据一致性挑战

### 自动扩缩容

根据负载动态调整容量：

**基于指标**：
```yaml
# Kubernetes HPA配置
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 3
  maxReplicas: 100
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

**预测性扩缩容**：
- 基于历史规律提前扩容
- 避免扩容延迟导致的性能问题

**挑战**：
- 扩容速度 vs 流量增长速度
- 缩容时避免影响用户
- 成本与性能的平衡

## 成本效率

### 资源利用率

**目标利用率**：
- CPU：60-70%（留出应对突发）
- 内存：70-80%
- 磁盘：70-80%

**过低利用率**：资源浪费
**过高利用率**：无法应对突发

### 成本优化手段

**右sizing**：
- 选择合适的实例规格
- 避免过度配置

**预留实例/Savings Plans**：
- 稳定负载使用预留资源
- 可节省30-60%成本

**Spot/抢占式实例**：
- 可容忍中断的负载
- 可节省60-90%成本

**按需扩缩容**：
- 非高峰期缩容
- 只在需要时付费

### 效率指标

**单位成本性能**：
```
效率 = QPS / 成本
```

**容量成本比**：
```
每1000 QPS的成本是多少？
```

持续跟踪这些指标，识别优化机会。

## 容量规划流程

### 定期Review

**月度Review**：
- 当前资源使用情况
- 与预测的偏差
- 近期是否需要扩容

**季度规划**：
- 下季度业务预测
- 资源需求预估
- 预算申请

**年度规划**：
- 年度业务目标
- 长期容量需求
- 大型架构升级计划

### 容量报告内容

```markdown
## 容量报告 - 2026年Q1

### 当前状态
- 峰值QPS：50,000
- 平均CPU使用率：45%
- 当前容量上限：80,000 QPS

### 预测
- Q2预计峰值：65,000 QPS（+30%）
- Q3预计峰值：85,000 QPS（+70%）

### 建议
- Q2前扩容20%
- Q3前进行架构优化，提升单实例性能

### 成本影响
- 扩容成本：$X/月
- 优化后预计节省：$Y/月
```

## 总结

| 环节 | 关键活动 |
|------|----------|
| 需求预测 | 收集数据、业务输入、模型预测 |
| 容量建模 | 理解扩展特性、识别瓶颈 |
| 压力测试 | 验证容量、找到极限 |
| 性能优化 | 测量、分析、优化瓶颈 |
| 扩展策略 | 垂直/水平扩展、自动扩缩容 |
| 成本效率 | 合理利用率、优化成本 |

容量规划是一个持续的过程，不是一次性工作。**宁可多一点，不要少一点**——容量不足导致的损失远大于多预留一些资源的成本。
