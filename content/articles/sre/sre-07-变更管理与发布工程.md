## 变更管理概述

### 变更是事故的主要来源

研究表明，**70-80%的生产事故与变更相关**：
- 代码发布
- 配置变更
- 基础设施变更
- 数据变更

### 变更管理目标

1. **降低变更风险**：减少变更导致的事故
2. **保持变更速度**：不能因为怕出问题就不变更
3. **快速恢复能力**：出问题能快速回滚
4. **可追溯性**：知道谁在什么时候改了什么

## 变更分类

### 按风险级别

| 级别 | 定义 | 审批要求 | 示例 |
|------|------|----------|------|
| **低风险** | 影响范围小，可快速回滚 | 自动审批 | 文案修改、小功能 |
| **中风险** | 影响核心功能，但有回滚方案 | Peer Review | 普通功能发布 |
| **高风险** | 影响核心系统，回滚困难 | 多人审批+评审会 | 数据库迁移、架构变更 |
| **紧急变更** | 修复生产事故 | 事后补审 | 紧急Hotfix |

### 按变更类型

**代码变更**：
- 功能发布
- Bug修复
- 性能优化

**配置变更**：
- 应用配置
- 基础设施配置
- 功能开关

**数据变更**：
- 数据库Schema变更
- 数据迁移
- 数据修复

**基础设施变更**：
- 服务器扩缩容
- 网络配置
- 存储变更

## 变更审批流程

### 变更请求（Change Request）

```markdown
## 变更请求

### 基本信息
- 变更标题：优化支付接口性能
- 变更类型：代码变更
- 风险级别：中
- 申请人：@alice
- 计划时间：2026-01-20 10:00

### 变更内容
- 优化数据库查询
- 增加缓存层

### 影响范围
- 支付服务
- 预计影响用户：0（性能优化，无功能变更）

### 回滚方案
- 回滚命令：kubectl rollout undo deployment/payment
- 预计回滚时间：5分钟

### 验证方案
- [ ] 金丝雀发布，观察30分钟
- [ ] 错误率无上升
- [ ] 延迟P99下降

### 审批
- [ ] Tech Lead: @bob
- [ ] SRE: @charlie
```

### 审批要点

**代码变更Review**：
- 逻辑正确性
- 性能影响
- 异常处理
- 回滚可行性

**配置变更Review**：
- 配置值合理性
- 影响范围
- 是否需要重启

**数据库变更Review**：
- Schema兼容性
- 锁表时间
- 数据迁移脚本

## 渐进式发布

### 金丝雀发布（Canary Release）

先发布到少量实例，观察无问题后全量发布。

```
发布流程：
1. 发布1%流量（金丝雀）
2. 观察15-30分钟
3. 扩大到10%
4. 观察15-30分钟
5. 扩大到50%
6. 全量发布
```

**金丝雀指标监控**：
- 错误率对比（新版本 vs 旧版本）
- 延迟对比
- 业务指标对比

**自动化金丝雀分析**：
- 自动对比新旧版本指标
- 异常时自动回滚
- 工具：Kayenta、Flagger

### 蓝绿部署（Blue-Green Deployment）

同时维护两套环境，通过切换流量实现发布。

```
Blue（当前版本）← 100%流量
Green（新版本）← 0%流量

验证Green后：
Blue（旧版本）← 0%流量
Green（新版本）← 100%流量
```

**优点**：
- 回滚快（切回Blue即可）
- 发布过程对用户无感知

**缺点**：
- 需要双倍资源
- 数据库Schema需要兼容

### 灰度发布（Gray Release）

按用户维度逐步发布：

```
阶段1：内部员工
阶段2：1%随机用户
阶段3：10%用户
阶段4：全量用户
```

**灰度维度**：
- 用户ID
- 地理位置
- 设备类型
- 用户标签

### Feature Flag

通过配置控制功能开关：

```python
if feature_flag.is_enabled("new_payment_flow", user_id):
    return new_payment_flow()
else:
    return old_payment_flow()
```

**优点**：
- 发布与上线分离
- 可针对用户群体开启
- 快速关闭问题功能

**管理要点**：
- 定期清理过期Flag
- Flag状态需要监控
- 避免Flag嵌套过深

## 回滚机制

### 回滚策略

**自动回滚**：
- 发布后监控指标异常，自动回滚
- 依赖完善的指标和阈值定义

**手动回滚**：
- 人工判断后触发回滚
- 适用于复杂场景

### 回滚方案设计

每次变更都需要有回滚方案：

**代码回滚**：
```bash
# Kubernetes回滚
kubectl rollout undo deployment/my-app

# 或回滚到指定版本
kubectl rollout undo deployment/my-app --to-revision=2
```

**配置回滚**：
- 配置版本管理
- 快速恢复到上一版本

**数据库回滚**：
- 需要提前考虑兼容性
- 有些变更难以回滚（如删除列）

### 不可回滚变更的处理

有些变更无法简单回滚：
- 数据库删除操作
- 外部API变更
- 状态机变更

**处理策略**：
- 更谨慎的审批
- 更长的灰度周期
- 前向修复（Fix Forward）准备

## 发布自动化

### CI/CD流水线

```
代码提交 → 构建 → 单元测试 → 集成测试 → 安全扫描
                                            ↓
监控告警 ← 金丝雀分析 ← 灰度发布 ← 部署到预发 ← 制品存储
```

### 发布检查清单

自动化检查（发布前）：
- [ ] 所有测试通过
- [ ] 代码Review完成
- [ ] 安全扫描无高危
- [ ] 依赖版本兼容
- [ ] 配置无误

自动化检查（发布中）：
- [ ] 服务健康检查通过
- [ ] 核心指标正常
- [ ] 无错误日志激增

### 发布窗口

**避免高风险时段**：
- 周五下午（影响周末On-Call）
- 大促前后
- 节假日前

**建议发布时间**：
- 工作日上午（有充足时间观察和处理）
- 团队人员齐全时

**发布冻结期**：
- 重大活动期间禁止变更
- 提前公告冻结时间

## 变更追踪

### 变更日志

记录所有变更：
```json
{
  "timestamp": "2026-01-19T10:00:00Z",
  "type": "deployment",
  "service": "payment-service",
  "version": "v1.2.3",
  "previous_version": "v1.2.2",
  "operator": "alice",
  "change_request": "CR-1234",
  "status": "success"
}
```

### 变更与事故关联

事故发生时，快速查询：
- 最近1小时有哪些变更？
- 这些变更涉及哪些服务？
- 变更操作人是谁？

### 变更审计

定期审计：
- 紧急变更比例是否过高？
- 变更导致的事故比例？
- 变更回滚率？

## 特殊变更处理

### 数据库变更

**Schema变更原则**：
- 向后兼容（新代码能读旧数据）
- 向前兼容（旧代码能读新数据）
- 分步执行（先加列再改代码再删列）

**大表变更**：
- 使用Online DDL工具（pt-online-schema-change、gh-ost）
- 低峰期执行
- 监控锁等待

### 配置变更

**配置管理原则**：
- 版本控制（Git）
- 环境隔离
- 变更审批
- 审计日志

**动态配置**：
- 支持热更新
- 配置中心（Apollo、Nacos）
- 变更推送+验证

### 基础设施变更

**IaC（Infrastructure as Code）**：
- Terraform/Pulumi管理基础设施
- 变更通过PR Review
- Plan后再Apply

**变更影响预估**：
```bash
# Terraform变更预览
terraform plan

# 显示将要创建/修改/删除的资源
```

## 总结

| 原则 | 实践 |
|------|------|
| 分类管理 | 不同风险等级不同流程 |
| 渐进发布 | 金丝雀→灰度→全量 |
| 可回滚 | 每次变更都有回滚方案 |
| 自动化 | CI/CD流水线，自动检查 |
| 可追溯 | 记录所有变更，关联事故 |

变更管理的核心是：**既要保持变更速度（业务需求），又要控制变更风险（系统稳定）**。通过渐进式发布、自动化检查、完善的回滚机制，可以在两者之间取得平衡。
