## 告警设计原则

### 好告警的标准

一个好的告警应该满足：

1. **可操作（Actionable）**
   - 收到告警后有明确的下一步行动
   - 如果只能"看看然后关掉"，这个告警不应该存在

2. **紧急（Urgent）**
   - 需要立即处理，不能等到明天
   - 非紧急问题应该进入工单系统

3. **真实（Real）**
   - 确实存在问题，不是误报
   - 误报率高的告警会被忽视

4. **唯一（Unique）**
   - 同一问题不会触发多个告警
   - 避免告警风暴

### 基于症状告警

**错误做法**：基于原因告警
```
CPU使用率 > 80% → 告警
内存使用率 > 90% → 告警
磁盘使用率 > 85% → 告警
```

这些可能是问题，也可能完全正常（如批处理任务）。

**正确做法**：基于症状告警
```
API错误率 > 1% → 告警
API延迟P99 > 2s → 告警
请求成功率 < 99.9% → 告警
```

用户受到影响才是真正的问题。

### 告警分级

| 级别 | 影响 | 响应时间 | 通知方式 |
|------|------|----------|----------|
| P0-Critical | 核心业务不可用 | 5分钟 | 电话+短信+IM |
| P1-High | 核心业务降级 | 30分钟 | 短信+IM |
| P2-Medium | 非核心功能受影响 | 4小时 | IM |
| P3-Low | 潜在问题 | 下个工作日 | 邮件 |

## 告警规则设计

### 基于SLO的告警

传统告警的问题：
- 阈值如何设定？
- 触发了意味着什么？
- 与业务目标的关系是什么？

**基于SLO的告警更有意义**：

```yaml
# 错误预算燃烧速率告警
# 如果继续以当前速率燃烧，会在X小时内耗尽预算

groups:
  - name: slo_alerts
    rules:
      # 1小时内耗尽1天预算 → Critical
      - alert: ErrorBudgetBurnRateCritical
        expr: |
          error_rate_1h > 14.4 * (1 - 0.999)
        labels:
          severity: critical
          
      # 6小时内耗尽1天预算 → Warning  
      - alert: ErrorBudgetBurnRateHigh
        expr: |
          error_rate_6h > 6 * (1 - 0.999)
        labels:
          severity: warning
```

### 多窗口告警

避免短暂抖动触发告警：

```yaml
# 需要同时满足短窗口和长窗口条件
- alert: HighErrorRate
  expr: |
    (
      # 短窗口：5分钟错误率高，快速检测
      rate(errors[5m]) / rate(requests[5m]) > 0.01
    ) and (
      # 长窗口：1小时错误率也偏高，确认趋势
      rate(errors[1h]) / rate(requests[1h]) > 0.005
    )
  for: 2m
```

### 告警抑制与分组

**抑制（Inhibition）**：高优先级告警触发时，抑制相关的低优先级告警

```yaml
# Alertmanager配置
inhibit_rules:
  # 服务完全不可用时，抑制延迟告警
  - source_match:
      severity: critical
      alertname: ServiceDown
    target_match:
      severity: warning
    equal: ['service']
```

**分组（Grouping）**：相关告警合并通知

```yaml
route:
  group_by: ['alertname', 'service']
  group_wait: 30s      # 等待30秒收集相关告警
  group_interval: 5m   # 分组内新告警等待5分钟
  repeat_interval: 4h  # 已发送告警4小时后重复
```

## 告警疲劳治理

### 告警疲劳的危害

- 重要告警被忽视
- On-Call人员倦怠
- 响应时间变长
- 团队士气下降

### 识别问题告警

**高噪音告警**：
- 频繁触发又自动恢复（Flapping）
- 每天触发多次但无需处理
- 总是被静默或忽略

**度量指标**：
```
告警噪音比 = 无需操作的告警 / 总告警数
告警有效率 = 触发事故响应的告警 / 总告警数
MTTA恶化 = 响应时间是否在变长
```

### 治理方法

**1. 定期Review**
```
每月告警分析：
- 触发次数Top 10的告警
- 触发后无操作的告警
- 重复静默的告警
```

**2. 优化或删除**

| 问题类型 | 解决方案 |
|----------|----------|
| 阈值不合理 | 基于历史数据调整 |
| 抖动频繁 | 增加for持续时间 |
| 不可操作 | 删除或转为日志 |
| 重复告警 | 合并或抑制 |

**3. 告警分流**

不是所有问题都需要On-Call响应：
- P0/P1 → 立即通知On-Call
- P2 → 工作时间处理
- P3 → 进入工单队列

## On-Call机制

### On-Call轮值设计

**轮值周期**：
- 常见：1周轮换
- 建议：至少3-4人参与轮值
- 避免：同一人连续值班超过1周

**轮值表示例**：
```
Week 1: Alice (Primary), Bob (Secondary)
Week 2: Bob (Primary), Charlie (Secondary)
Week 3: Charlie (Primary), Alice (Secondary)
```

**Primary vs Secondary**：
- Primary：首先响应，处理所有告警
- Secondary：Primary无法响应时接手
- 升级路径：Primary → Secondary → Manager

### On-Call职责

**值班期间**：
- 响应所有告警通知
- 初步诊断和处理
- 必要时升级或召集支援
- 记录事故和处理过程

**交接时**：
- 说明当前进行中的问题
- 交接待处理事项
- 分享值班期间的发现

### On-Call工具链

```
告警源 → Alertmanager → PagerDuty/Opsgenie → 手机通知
              ↓
          ChatOps → Slack/Teams通知
              ↓
          工单系统 → 事后跟踪
```

**必备功能**：
- 电话/短信通知（邮件不够紧急）
- 告警确认（Acknowledge）
- 升级路径（Escalation）
- 日程管理（Schedule）

## 事故响应流程

### 事故分级

| 级别 | 定义 | 响应 |
|------|------|------|
| SEV1 | 核心业务完全不可用 | 全员响应，15分钟内组建War Room |
| SEV2 | 核心业务严重降级 | On-Call响应，必要时升级 |
| SEV3 | 非核心功能受影响 | On-Call独立处理 |
| SEV4 | 潜在问题或小范围影响 | 记录后正常工作时间处理 |

### 响应流程

**1. 检测（Detection）**
- 收到告警或用户报告
- 确认问题存在

**2. 响应（Response）**
- 确认告警（Acknowledge）
- 初步评估影响范围和严重程度

**3. 沟通（Communication）**
- 通知相关人员
- SEV1/SEV2启动专用沟通频道
- 定期更新状态

**4. 缓解（Mitigation）**
- 第一优先级：恢复服务
- 临时方案优先（回滚、重启、切流量）
- 根因分析可以事后做

**5. 恢复（Recovery）**
- 确认服务恢复正常
- 监控是否有二次问题
- 解除告警状态

**6. 复盘（Post-mortem）**
- 48小时内完成复盘文档
- 识别根因和改进项
- 跟踪Action Items

### 事故指挥官（Incident Commander）

SEV1/SEV2事故需要指定IC：

**IC职责**：
- 协调响应工作
- 分配任务
- 对外沟通
- 决策是否升级

**IC不做**：
- 不亲自排查技术问题
- 不写代码
- 专注协调和沟通

## On-Call健康度

### 度量指标

**响应效率**：
- MTTA（Mean Time to Acknowledge）：平均确认时间
- MTTR（Mean Time to Resolve）：平均解决时间

**告警质量**：
- 每周告警数量
- 误报率
- 夜间告警比例

**人员健康**：
- On-Call工作时长
- 睡眠中断次数
- 值班人员满意度

### 改进措施

**减少On-Call负担**：
- 优化告警质量（减少噪音）
- 编写Runbook（加速诊断）
- 自动化常见操作
- 合理的轮值安排

**补偿机制**：
- On-Call津贴
- 调休制度
- 夜间值班后第二天弹性上班

**持续改进**：
- 每月On-Call回顾会
- 分析告警趋势
- 推动根因修复

## Runbook编写

### Runbook结构

```markdown
# 告警名称

## 概述
- 触发条件
- 影响范围
- 严重程度

## 诊断步骤
1. 检查Dashboard: [链接]
2. 查看相关日志: [命令/链接]
3. 确认上下游状态

## 处理步骤
### 场景A：XXX导致
1. 步骤1
2. 步骤2

### 场景B：YYY导致
1. 步骤1
2. 步骤2

## 升级条件
- 10分钟内无法定位
- 需要代码变更
- 影响范围扩大

## 相关联系人
- 服务Owner: @alice
- 相关团队: #channel

## 历史事故
- 2025-12-01: [事故链接]
```

### Runbook最佳实践

1. **保持更新**：每次事故后Review
2. **可执行**：命令可直接复制执行
3. **有链接**：Dashboard、日志、代码直接跳转
4. **有时限**：每步操作预期时间
5. **有判断点**：明确什么情况该升级

## 总结

| 维度 | 关键点 |
|------|--------|
| 告警设计 | 基于症状、可操作、分级分流 |
| 告警治理 | 定期Review、消除噪音 |
| On-Call机制 | 合理轮值、明确职责、充分补偿 |
| 事故响应 | 快速恢复优先、有序协调 |
| 持续改进 | 度量、分析、优化 |

好的On-Call体系让工程师能够**睡个好觉**，因为：
- 告警有意义，不会误报
- 有Runbook指导，不会手足无措
- 有升级机制，不会孤军奋战
- 有补偿制度，付出有回报
