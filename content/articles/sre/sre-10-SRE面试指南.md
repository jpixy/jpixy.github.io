## SRE面试概览

## 技术基础问题

### Linux系统

**进程与线程**：
- 进程和线程的区别？
- 僵尸进程是什么？如何处理？
- 如何查看系统负载？load average意味着什么？

**内存管理**：
- 虚拟内存是什么？
- OOM Killer的工作原理？
- 如何排查内存泄漏？

**文件系统**：
- inode是什么？
- 硬链接和软链接的区别？
- 磁盘满了如何排查？

**性能排查**：
```
问：服务器响应变慢，如何排查？

答：按照USE方法论系统排查：
1. CPU：top/htop查看CPU使用率和负载
2. 内存：free -m查看内存，检查swap使用
3. 磁盘：iostat -x查看IO等待
4. 网络：netstat/ss查看连接状态

结合业务指标和日志定位根因。
```

### 网络

**TCP/IP**：
- 三次握手和四次挥手？
- TIME_WAIT是什么？为什么需要？
- TCP和UDP的区别？

**HTTP**：
- HTTP状态码含义？
- HTTP/1.1和HTTP/2的区别？
- HTTPS如何保证安全？

**网络排查**：
```
问：用户反馈访问慢，如何排查？

答：分层排查：
1. 确认范围：是所有用户还是部分？
2. 客户端：ping/traceroute检查网络路径
3. DNS：nslookup/dig检查解析
4. 服务端：检查服务延迟指标
5. 后端：检查数据库、缓存延迟
```

### 编程

**语言选择**：通常Python或Go

**常见题型**：
- 日志分析：解析日志统计错误

## SRE核心概念

### SLI/SLO/SLA

```
问：解释SLI、SLO、SLA的区别？

答：
- SLI（指标）：量化服务质量的指标，如可用性、延迟
- SLO（目标）：SLI的目标值，如可用性>99.9%
- SLA（协议）：与客户的正式承诺，包含违约后果

关系：SLI是测量什么，SLO是目标是什么，SLA是承诺是什么。
```

```
问：如何设计一个服务的SLI？

答：以用户体验为中心：
1. 识别关键用户旅程
2. 定义每个旅程的成功标准
3. 选择可测量的指标
4. 确定测量位置（越靠近用户越好）

示例：支付服务
- 可用性SLI：支付成功率
- 延迟SLI：支付接口P99延迟
```

### 错误预算

```
问：什么是错误预算？如何使用？

答：
错误预算 = 1 - SLO目标
例如：99.9% SLO → 0.1%错误预算 → 每月43分钟停机时间

使用方式：
- 预算充足：可以接受更多风险（快速发布）
- 预算紧张：降低风险（谨慎变更）
- 预算耗尽：冻结变更，专注稳定性

价值：量化了可靠性和速度的权衡
```

### Toil

```
问：什么是Toil？如何处理？

答：
Toil是满足以下特征的工作：手动、重复、可自动化、无持久价值、随规模线性增长。

处理方法：
1. 识别和量化Toil（目标<50%）
2. 按ROI优先级自动化
3. 从根本上消除Toil来源
4. 定期Review和改进
```

## 系统设计题

### 设计高可用系统

```
问：设计一个99.99%可用的Web服务

答：
1. 多副本部署
   - 无状态应用，至少3个实例
   - 跨可用区部署

2. 负载均衡
   - 健康检查
   - 自动摘除故障节点

3. 数据层高可用
   - 数据库主从复制
   - 自动故障转移

4. 监控告警
   - 关键指标监控
   - 快速故障检测

5. 灾备方案
   - 定期备份
   - 跨区域容灾

6. 量化分析
   - 99.99% = 年停机52分钟
   - 需要自动化恢复（人工来不及）
```

### 设计监控系统

```
问：为微服务架构设计监控方案

答：
1. 指标体系
   - 基础设施：CPU、内存、网络、磁盘
   - 应用层：QPS、延迟、错误率（RED）
   - 业务层：订单数、支付成功率

2. 日志系统
   - 结构化日志
   - 统一采集（ELK/Loki）
   - 关联trace_id

3. 分布式追踪
   - 全链路追踪
   - 采样策略
   - 与日志关联

4. 告警设计
   - 基于症状而非原因
   - 分级分流
   - 避免告警疲劳

5. 可视化
   - 统一Dashboard
   - 关联跳转
```

### 设计On-Call系统

```
问：设计一个On-Call管理系统

答：
核心功能：
1. 排班管理
   - 支持周轮换
   - 支持请假覆盖
   - 日历同步

2. 告警路由
   - 按服务/级别路由
   - 主备On-Call
   - 升级机制

3. 通知渠道
   - 电话、短信、IM
   - 多次重试
   - 确认机制

4. 事故跟踪
   - 事故状态管理
   - 时间线记录
   - 关联复盘

5. 分析报表
   - On-Call负担统计
   - 告警趋势分析
   - MTTA/MTTR跟踪
```

## 场景问题

### 故障排查

```
问：线上服务CPU突然飙升到100%，如何排查？

答：
1. 确认影响
   - 服务是否正常响应？
   - 是否需要立即扩容或限流？

2. 初步定位
   - top查看哪个进程占用高
   - 是否有异常请求模式？

3. 深入分析
   - 如果是应用进程，使用profiler定位热点
   - 检查是否有慢查询、死循环
   - 对比最近是否有发布或配置变更

4. 缓解措施
   - 如果是发布导致：回滚
   - 如果是流量导致：扩容或限流
   - 如果是攻击：启用防护

5. 事后
   - 记录事故
   - 完成复盘
```

### 容量规划

```
问：预计明年用户增长3倍，如何做容量规划？

答：
1. 当前状态分析
   - 当前峰值负载
   - 各组件容量上限
   - 瓶颈在哪里

2. 需求预测
   - 3倍用户≠3倍请求（需要分析用户行为）
   - 考虑季节性因素
   - 新功能的额外负载

3. 扩展方案
   - 哪些可以水平扩展？
   - 哪些需要架构改造？
   - 数据库是否需要分片？

4. 成本分析
   - 扩容成本
   - 优化后可能的节省

5. 执行计划
   - 分阶段扩容时间表
   - 压测验证
   - 监控指标
```

### 发布故障

```
问：新版本发布后错误率上升，你会怎么做？

答：
1. 立即评估
   - 错误率多少？趋势如何？
   - 影响哪些用户？
   - 是否触发SLO告警？

2. 决策
   - 如果影响严重：立即回滚
   - 如果影响较小：可以先分析

3. 回滚执行
   - 触发回滚
   - 验证回滚成功
   - 确认指标恢复

4. 根因分析
   - 查看错误日志
   - 对比新旧版本代码
   - 复现问题

5. 改进措施
   - 修复代码问题
   - 加强测试覆盖
   - 优化发布流程（金丝雀比例）
```

## 行为问题

### 事故处理经验

```
问：描述一次你处理的严重事故

STAR框架：
Situation：什么情况下发生的？
Task：你的职责是什么？
Action：你采取了什么行动？
Result：结果如何？学到了什么？

示例回答：
S：核心支付服务因数据库连接池耗尽导致不可用
T：作为On-Call，需要快速恢复服务
A：
  1. 确认问题后立即通知相关人员
  2. 紧急扩大连接池配置
  3. 发现是慢查询导致，定位到具体SQL
  4. 添加索引后恢复
R：服务在30分钟内恢复，事后建立了数据库连接监控，
   并在代码Review中增加了SQL检查项
```

### 团队协作

```
问：如何与开发团队合作推动可靠性改进？

答：
1. 建立共同目标
   - 用SLO作为共同语言
   - 让开发理解可靠性影响业务

2. 数据驱动
   - 用事故数据说话
   - 展示改进的价值

3. 赋能而非控制
   - 提供工具和培训
   - 帮助而非阻挡

4. 建立反馈机制
   - 定期Review会议
   - 事故复盘共同参与

5. 共同承担责任
   - SRE不是唯一的可靠性守护者
   - 推动开发参与On-Call
```

### 压力管理

```
问：On-Call期间如何处理压力？

答：
1. 准备充分
   - 熟悉Runbook
   - 了解升级路径
   - 工具和权限提前准备好

2. 保持冷静
   - 遵循流程，不要慌
   - 不确定时及时求助

3. 团队支持
   - 知道可以找谁帮忙
   - 不要独自扛着

4. 事后恢复
   - 完成复盘，避免反复发生
   - 适当休息

5. 长期机制
   - 合理的轮值安排
   - 持续改进减少告警
```

## 总结

| 面试环节 | 准备重点 |
|----------|----------|
| 技术基础 | Linux、网络、编程实战 |
| SRE理念 | SLI/SLO、Toil、事故管理 |
| 系统设计 | 高可用、可扩展性设计 |
| 场景分析 | 故障排查思路、实际经验 |
| 行为问题 | STAR框架、真实案例 |

**面试技巧**：
1. 思考过程比答案更重要
2. 不会就说不会，不要编造
3. 结合实际经验回答
4. 主动沟通，确认问题
5. 展示解决问题的能力，而非背诵知识
