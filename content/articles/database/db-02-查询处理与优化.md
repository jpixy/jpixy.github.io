## SQL解析

### 词法分析

词法分析器将SQL文本拆分为Token序列。每个Token代表一个语法单元：关键字、标识符、字面量、运算符。

例如 `SELECT name FROM users WHERE id = 1` 被拆分为：

关键字SELECT、标识符name、关键字FROM、标识符users、关键字WHERE、标识符id、运算符=、数字1。

词法分析器通常使用有限状态机实现，可以用工具（如Flex、Lex）自动生成。

### 语法分析

语法分析器根据SQL语法规则将Token序列组织成抽象语法树（AST）。

SQL的语法可以用BNF（巴科斯-诺尔范式）描述。语法分析器验证SQL是否符合语法规则，并构建表示查询结构的树形结构。

常用的语法分析技术：LL解析、LR解析、递归下降。工具如Bison、ANTLR可以自动生成。

### 语义分析

语法正确的SQL还需要语义验证：

**名称解析**：表名、列名是否存在？列属于哪个表？如果有别名，解析别名引用。

**类型检查**：操作数类型是否兼容？字符串和数字能否比较？

**权限检查**：用户是否有权限访问这些表和列？

语义分析后，AST被转换为关系代数表达式或查询树，更适合优化器处理。

## 查询优化概述

### 为什么需要优化

SQL是声明式语言，描述"要什么"而非"怎么做"。同一个查询可能有多种执行方式，性能差异可能达到几个数量级。

优化器的任务是在众多可能的执行计划中选择最优（或足够好）的一个。

### 优化器类型

**基于规则的优化器（RBO）**：使用预定义的规则进行转换。规则基于经验，如"使用索引通常比全表扫描好"。简单但不考虑数据分布。

**基于代价的优化器（CBO）**：估算每个计划的执行代价，选择代价最低的。需要统计信息支持。现代数据库主流方法。

**自适应优化**：运行时根据实际执行情况调整计划。如Oracle的自适应游标共享、SQL Server的自适应查询处理。

## 逻辑优化

### 关系代数等价变换

查询可以表示为关系代数表达式，某些变换保持语义等价但可能改善性能。

**选择下推**：尽早过滤数据。将选择操作下推到连接操作之前，减少参与连接的数据量。这是最重要的优化之一。

**投影下推**：尽早去除不需要的列。减少数据传输和处理的开销。

**谓词合并**：将多个条件合并为一个，或拆分为更有利于索引利用的形式。

**子查询展开**：将子查询转换为连接。避免嵌套循环执行，让优化器有更多选择。

**视图合并**：将视图查询与外层查询合并，避免物化视图的中间结果。

### 连接消除

如果连接的结果可以保证不改变另一侧的行数（如通过外键约束），且连接列不在输出中，可以消除连接。

### 常量折叠

在编译时计算常量表达式。`WHERE date > '2024-01-01' + 7` 可以直接计算为具体日期。

## 物理优化

### 访问路径选择

对于每个表，选择如何获取数据：

**全表扫描**：读取所有页面。适用于需要大部分行的查询，或没有合适索引时。

**索引扫描**：通过索引定位数据。索引选择性高时效率远超全表扫描。

**索引覆盖**：所需数据都在索引中，无需回表。性能最佳。

**位图索引扫描**：对多个条件分别使用索引，用位图合并结果，再访问数据。适合多条件查询。

### 连接算法选择

**嵌套循环连接**：对于外表的每一行，扫描内表找匹配行。简单，适合小表。可以利用索引改进为索引嵌套循环。

**哈希连接**：用较小的表构建哈希表，扫描另一个表进行探测。适合等值连接和大表。需要足够内存存放哈希表。

**排序合并连接**：将两个表按连接列排序，然后合并。如果数据已排序（如利用索引），效率很高。

选择哪种算法取决于表大小、是否有索引、可用内存、连接条件类型。

### 连接顺序

多表连接时，连接顺序影响巨大。N个表有N!种连接顺序。优化器使用动态规划或贪心算法搜索最优顺序。

左深树：所有连接的外表都是基表或之前连接的结果。便于流水线执行。

Bushy树：允许任意形状的连接树。搜索空间更大，可能找到更优计划。

## 代价模型

### 代价组成

**I/O代价**：读取页面的数量。传统上是主要代价，因为磁盘I/O最慢。

**CPU代价**：比较、哈希、排序等操作。现代系统中比重增加，特别是内存数据库。

**网络代价**：分布式系统中，数据传输的代价。

### 统计信息

代价估算依赖统计信息：

**表大小**：行数、页面数。

**列统计**：不同值数量（NDV）、最小/最大值、空值比例。

**直方图**：值的分布。等宽直方图将值域分为等宽区间；等高直方图每个桶包含相同数量的值。

**索引统计**：索引高度、叶子页面数。

### 基数估计

估算每个操作的输出行数。这是代价估算最困难的部分。

**选择率**：条件过滤后保留的比例。等值条件假设均匀分布时，选择率 = 1/NDV。

**连接选择率**：连接后的行数与笛卡尔积的比值。

估计错误会导致计划选择错误。估计错误在多层连接中会放大。

## 执行计划

### 计划表示

执行计划是操作符树，描述如何执行查询。每个节点是一个操作（扫描、连接、排序、聚合）。

数据从叶子节点向上流动。每个节点处理来自子节点的数据，输出给父节点。

### 火山模型

经典的执行模型。每个操作符实现next()接口，每次返回一行。

优点：简单，内存占用低。缺点：每行都有函数调用开销，对CPU不友好。

### 向量化执行

每次处理一批数据（如1024行）而非一行。减少函数调用开销，利用CPU缓存和SIMD指令。

现代分析型数据库（如ClickHouse）普遍采用。

### 编译执行

将查询编译为机器码执行。消除解释开销，针对具体查询优化。

代表：HyPer、PostgreSQL的JIT。

---

## 执行计划分析

### EXPLAIN

查看优化器选择的执行计划。不同数据库输出格式不同，但核心信息类似：

- 操作类型（扫描、连接、排序）
- 访问方法（索引、全表）
- 估算行数
- 估算代价

### 实际执行 vs 估算

EXPLAIN ANALYZE（或类似功能）显示实际执行统计：真实行数、真实时间。

对比估算和实际值可以发现统计信息过时或估计算法问题。

### 计划偏差

优化器选择了糟糕计划的常见原因：

- 统计信息过时
- 基数估计错误
- 参数嗅探问题
- 缺少合适索引
- 数据倾斜

## 总结

| 阶段 | 职责 |
|------|------|
| 解析 | SQL → AST |
| 语义分析 | 验证、名称解析 |
| 逻辑优化 | 等价变换 |
| 物理优化 | 选择算法 |
| 代价估算 | 选择最优计划 |
| 执行 | 执行计划 |

查询优化是数据库的核心竞争力。好的优化器能让简单的SQL获得高效执行。
