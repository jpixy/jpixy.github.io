# 微服务架构设计原则

## 一、微服务概述

### 1.1 什么是微服务

微服务是一种将应用程序构建为一组小型、独立服务的架构风格。每个服务：
- 围绕特定业务能力构建
- 可独立部署
- 拥有自己的数据存储
- 通过轻量级协议通信

### 1.2 微服务 vs 单体

| 维度 | 单体应用 | 微服务 |
|------|----------|--------|
| 部署 | 整体部署 | 独立部署 |
| 扩展 | 整体扩展 | 按需扩展 |
| 技术栈 | 统一 | 可异构 |
| 数据 | 共享数据库 | 独立数据库 |
| 复杂度 | 代码复杂 | 运维复杂 |
| 故障影响 | 全局影响 | 局部影响 |

### 1.3 微服务的代价

**不要忽视成本**：
- 分布式系统复杂性
- 运维复杂度增加
- 网络调用开销
- 数据一致性挑战
- 服务治理需求

**适用场景**：
- 业务复杂度高
- 团队规模大
- 需要独立演进
- 有运维能力支撑

## 二、服务拆分

### 2.1 拆分原则

**单一职责**：
- 一个服务只做一件事
- 职责清晰，边界明确

**高内聚低耦合**：
- 相关功能聚合在一起
- 服务间依赖最小化

**业务驱动**：
- 按业务能力拆分
- 不是按技术层次拆分

### 2.2 拆分方法

**领域驱动设计（DDD）**：
- 识别限界上下文
- 上下文即服务边界
- 聚合根定义一致性边界

**业务能力分解**：
- 分析业务流程
- 识别核心业务能力
- 每个能力一个服务

**事件风暴**：
- 团队协作识别领域事件
- 根据事件划分服务
- 适合复杂业务

### 2.3 拆分粒度

**过细的问题**：
- 服务过多，运维困难
- 调用链过长
- 分布式事务复杂

**过粗的问题**：
- 失去微服务优势
- 独立部署困难
- 耦合度高

**判断标准**：
- 团队能独立开发维护
- 业务边界清晰
- 可独立扩展和部署

### 2.4 拆分示例

**电商系统**：

| 服务 | 职责 |
|------|------|
| 用户服务 | 用户注册、登录、信息管理 |
| 商品服务 | 商品管理、分类、搜索 |
| 订单服务 | 订单创建、状态管理 |
| 库存服务 | 库存扣减、查询 |
| 支付服务 | 支付流程、退款 |
| 通知服务 | 短信、邮件、推送 |

## 三、服务通信

### 3.1 同步通信

**HTTP/REST**：
- 简单直接
- 跨语言支持好
- 适合对外API

**RPC（gRPC）**：
- 高性能
- 强类型
- 适合内部服务

### 3.2 异步通信

**消息队列**：
- 解耦服务
- 削峰填谷
- 适合事件驱动

**事件驱动**：
- 发布订阅模式
- 服务间松耦合
- 最终一致性

### 3.3 选择依据

| 场景 | 推荐方式 |
|------|----------|
| 需要即时响应 | 同步（REST/RPC） |
| 可以延迟处理 | 异步（消息队列） |
| 一对多通知 | 事件发布 |
| 链路追踪要求高 | 同步 |
| 解耦要求高 | 异步 |

### 3.4 API设计

**RESTful原则**：
- 资源导向
- HTTP动词语义化
- 无状态
- 版本管理

**接口契约**：
- 明确定义请求/响应格式
- 向后兼容
- 文档化（OpenAPI/Swagger）

## 四、数据管理

### 4.1 数据库模式

**每服务独立数据库**：
- 数据隔离
- 独立演进
- 推荐方式

**共享数据库**（不推荐）：
- 破坏服务独立性
- 耦合度高
- 仅作为过渡方案

### 4.2 数据一致性

**挑战**：跨服务数据如何保持一致

**方案**：
- Saga模式：补偿事务
- 最终一致性：异步同步
- 避免分布式事务

### 4.3 数据共享

**查询需要其他服务数据**：
- API调用获取
- 数据冗余（异步同步）
- 事件驱动更新

**避免**：
- 直接访问其他服务的数据库
- 共享数据库

## 五、服务治理

### 5.1 服务注册发现

**作用**：服务实例动态注册和发现

**方案**：
- Eureka
- Consul
- Nacos
- Kubernetes Service

### 5.2 负载均衡

**客户端负载均衡**：
- 客户端获取服务列表
- 自行选择实例
- 如Ribbon

**服务端负载均衡**：
- 通过代理分发请求
- 如Nginx、Kubernetes Service

### 5.3 熔断降级

**熔断**：
- 失败率过高时断开调用
- 防止故障扩散
- 如Hystrix、Sentinel

**降级**：
- 核心功能保障
- 非核心功能关闭
- 返回兜底数据

### 5.4 限流

**目的**：保护系统不被过载

**算法**：令牌桶、漏桶、滑动窗口

**维度**：用户、IP、接口

### 5.5 配置中心

**作用**：集中管理配置

**方案**：
- Apollo
- Nacos
- Spring Cloud Config

## 六、可观测性

### 6.1 日志

**要求**：
- 统一格式
- 包含TraceID
- 集中收集

**工具**：ELK、Loki

### 6.2 指标

**要求**：
- RED指标（Rate、Error、Duration）
- 业务指标
- 资源指标

**工具**：Prometheus + Grafana

### 6.3 链路追踪

**作用**：追踪请求在服务间的流转

**工具**：Jaeger、Zipkin、SkyWalking

### 6.4 统一观测

三者结合：
- 从指标发现异常
- 从链路定位服务
- 从日志找到原因

## 七、演进策略

### 7.1 渐进式拆分

**不要**：
- 一步到位大规模拆分
- 没有基础设施就拆

**应该**：
- 从单体逐步抽离
- 先拆独立性强的
- 积累经验再扩大

### 7.2 拆分步骤

1. **评估现状**：识别边界和依赖
2. **基础设施准备**：注册中心、配置中心、监控
3. **选择突破口**：变化频繁或独立的模块
4. **拆分实施**：代码拆离、数据拆离
5. **验证稳定**：灰度发布、性能验证
6. **持续迭代**：逐步拆分其他服务

### 7.3 绞杀者模式

**原理**：
- 新功能用新服务实现
- 老功能逐步迁移
- 老系统最终下线

**优势**：
- 风险可控
- 可持续演进

## 八、反模式

### 8.1 常见反模式

**分布式单体**：
- 拆分了但高度耦合
- 必须一起部署
- 失去微服务意义

**过度拆分**：
- 服务过多过细
- 运维成本爆炸
- 调用链过长

**共享数据库**：
- 数据耦合
- 难以独立演进

**缺少治理**：
- 没有注册发现
- 没有监控告警
- 出问题难定位

### 8.2 避免方式

- 先做好基础设施
- 团队能力匹配
- 渐进式演进
- 持续关注复杂度

## 九、面试要点

### 9.1 常见追问

**Q：什么时候应该用微服务？**
A：业务复杂、团队规模大、需要独立部署和扩展、有足够的运维能力。小团队简单业务不建议。

**Q：如何划分服务边界？**
A：基于业务能力拆分，使用DDD识别限界上下文。保证高内聚低耦合，服务可独立开发部署。

**Q：微服务的主要挑战是什么？**
A：分布式系统复杂性、数据一致性、运维复杂度、服务治理。需要完善的基础设施支撑。

**Q：如何保证服务间数据一致性？**
A：使用Saga补偿事务；接受最终一致性；事件驱动同步；避免分布式事务。

### 9.2 核心要点

1. **业务驱动拆分**：按业务能力而非技术层次
2. **独立性是核心**：数据、部署、团队独立
3. **治理是基础**：没有治理的微服务是灾难
4. **渐进式演进**：不要一步到位
5. **权衡复杂度**：微服务不是银弹
