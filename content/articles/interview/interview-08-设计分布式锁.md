# 如何设计一个分布式锁

## 一、为什么需要分布式锁

### 1.1 单机锁的局限

在单机环境中，使用synchronized、ReentrantLock等即可保证互斥。但在分布式系统中：

- 多个服务实例部署在不同机器
- 每个JVM的锁只能控制本地线程
- 无法协调跨进程的并发访问

### 1.2 典型场景

| 场景 | 说明 | 要求 |
|------|------|------|
| 防止重复处理 | 定时任务多实例只执行一次 | 互斥性 |
| 资源抢占 | 抢购、秒杀库存扣减 | 互斥性、高性能 |
| 分布式事务 | 跨服务操作的串行化 | 互斥性、可重入 |
| 缓存重建 | 防止缓存击穿时重复加载 | 互斥性 |

### 1.3 分布式锁的要求

**基本要求**：
- **互斥性**：任意时刻只有一个客户端持有锁
- **无死锁**：持有锁的客户端崩溃后，锁能被释放
- **容错性**：锁服务高可用

**进阶要求**：
- **可重入**：同一客户端可多次获取同一把锁
- **公平性**：按请求顺序获取锁
- **阻塞/非阻塞**：支持等待或立即返回

## 二、基于Redis的分布式锁

### 2.1 基本实现

**加锁**：使用SET命令的NX和EX选项

```
SET lock_key unique_value NX EX 30
```

- NX：只有key不存在时才设置
- EX 30：过期时间30秒
- unique_value：唯一标识，用于释放时验证

**解锁**：验证value后删除

必须先验证value再删除，且需要原子操作（Lua脚本）。

### 2.2 关键问题与解决

**问题一：锁过期但业务未完成**

场景：客户端A获取锁，执行时间超过过期时间，锁自动释放。客户端B获取锁，此时A完成操作释放锁，实际释放的是B的锁。

**解决方案**：
- 使用唯一value标识锁的持有者
- 释放时验证value匹配才删除
- 引入锁续期机制（Watch Dog）

**问题二：锁续期（Watch Dog）**

原理：
- 获取锁后启动后台线程
- 定期检查锁是否仍被持有
- 若持有则延长过期时间
- 业务完成或客户端崩溃时停止续期

Redisson的实现：默认30秒过期，每10秒续期一次。

**问题三：Redis单点故障**

场景：主节点获取锁后崩溃，从节点升级为主但未同步锁数据，导致锁丢失。

**解决方案**：RedLock算法（后文详述）

### 2.3 可重入锁

**实现原理**：
- 使用Hash结构存储锁
- field为客户端标识
- value为重入次数
- 同一客户端重复加锁时次数+1
- 释放时次数-1，减到0时删除

### 2.4 RedLock算法

**目标**：解决Redis主从切换导致的锁丢失问题

**前提**：部署N个独立的Redis实例（建议5个）

**加锁流程**：
1. 获取当前时间T1
2. 依次向N个实例请求加锁（设置较短超时）
3. 计算获取锁总耗时
4. 当且仅当：
   - 在超过半数实例（N/2+1）上成功获取锁
   - 且总耗时小于锁的过期时间
   - 才认为加锁成功
5. 锁的有效时间 = 原过期时间 - 获取锁耗时

**解锁流程**：向所有实例发送释放请求

**争议**：
- Martin Kleppmann指出时钟漂移和GC停顿可能导致问题
- Antirez（Redis作者）进行了回应
- 实践中需根据场景评估是否使用

## 三、基于ZooKeeper的分布式锁

### 3.1 实现原理

利用ZooKeeper的特性：
- **临时节点**：客户端断开连接后自动删除
- **顺序节点**：节点名自动追加递增序号
- **Watch机制**：监听节点变化

### 3.2 实现流程

**加锁**：
1. 在锁节点下创建临时顺序节点
2. 获取锁节点下所有子节点
3. 判断自己是否是最小序号的节点
4. 如果是，获取锁成功
5. 如果不是，监听比自己小的前一个节点

**解锁**：
- 删除自己创建的临时节点
- 或客户端断开连接自动删除

### 3.3 特点分析

**优点**：
- 天然支持锁失效（临时节点）
- 支持公平锁（顺序节点）
- 支持阻塞等待（Watch机制）
- 可靠性高

**缺点**：
- 性能不如Redis
- 需要额外部署ZooKeeper集群
- 实现相对复杂

### 3.4 惊群效应

**问题**：如果所有等待者都监听锁节点，锁释放时所有人都被唤醒，只有一个能成功。

**解决**：每个节点只监听前一个节点（链式监听），避免惊群。

## 四、基于数据库的分布式锁

### 4.1 方案一：唯一索引

**原理**：利用唯一索引的排他性

**加锁**：INSERT一条记录
- 成功则获取锁
- 唯一索引冲突则失败

**解锁**：DELETE该记录

**问题**：
- 无锁过期机制，需要定时清理
- 非阻塞，需要轮询
- 数据库成为瓶颈

### 4.2 方案二：排他锁

**原理**：使用SELECT ... FOR UPDATE

**流程**：
1. 开启事务
2. SELECT ... FOR UPDATE获取锁
3. 执行业务逻辑
4. 提交事务释放锁

**问题**：
- 连接时间长
- 容易造成数据库连接池耗尽
- 死锁风险

### 4.3 方案三：乐观锁

**原理**：使用版本号控制

**流程**：
1. 查询当前版本号
2. 更新时带上版本号条件
3. 更新成功则获取锁
4. 失败则重试

**适用场景**：冲突较少的场景

### 4.4 数据库锁总结

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 唯一索引 | 简单 | 无过期、非阻塞 | 简单场景 |
| 排他锁 | 阻塞 | 连接占用、死锁 | 低并发 |
| 乐观锁 | 轻量 | 需要重试 | 低冲突 |

## 五、方案对比与选型

### 5.1 综合对比

| 维度 | Redis | ZooKeeper | 数据库 |
|------|-------|-----------|--------|
| 性能 | 高 | 中 | 低 |
| 可靠性 | 中（主从问题） | 高 | 高 |
| 实现复杂度 | 低 | 中 | 低 |
| 运维成本 | 低 | 高 | 低 |
| 锁失效 | 需设计 | 天然支持 | 需设计 |
| 公平性 | 不支持 | 支持 | 不支持 |

### 5.2 选型建议

**Redis分布式锁**：
- 性能要求高
- 已有Redis基础设施
- 对极端情况锁丢失可接受

**ZooKeeper分布式锁**：
- 对可靠性要求极高
- 需要公平锁
- 已有ZK基础设施

**数据库锁**：
- 并发量低
- 不想引入新组件
- 临时方案

## 六、生产实践要点

### 6.1 锁粒度

**粗粒度**：锁整个资源
- 简单，但并发度低

**细粒度**：锁具体数据
- 如：锁用户ID、锁订单ID
- 并发度高，但需要精心设计

### 6.2 锁超时设置

**过短**：业务未完成锁已释放，导致并发问题

**过长**：客户端崩溃后锁长时间无法释放

**建议**：
- 根据业务耗时设置，留有余量
- 使用锁续期机制
- 或使用更短超时 + 自动续期

### 6.3 异常处理

**获取锁失败**：
- 重试（限制次数和间隔）
- 快速失败
- 降级处理

**释放锁失败**：
- 记录日志
- 依赖过期自动释放
- 告警人工处理

### 6.4 监控告警

**监控指标**：
- 锁获取成功率
- 锁等待时间
- 锁持有时间
- 锁过期释放次数

**告警场景**：
- 锁等待超时频繁
- 锁持有时间过长
- 锁服务不可用

## 七、面试要点

### 7.1 常见追问

**Q：Redis分布式锁如何防止误删？**
A：使用唯一value（如UUID+线程ID）标识锁持有者；释放时用Lua脚本原子地验证value后再删除。

**Q：业务执行时间超过锁过期时间怎么办？**
A：引入锁续期机制（Watch Dog），后台线程定期延长过期时间；Redisson默认实现了该机制。

**Q：Redis主从切换导致锁丢失怎么办？**
A：使用RedLock算法，需要超过半数独立实例加锁成功；或接受小概率问题，通过业务幂等兜底。

**Q：ZooKeeper分布式锁为什么更可靠？**
A：基于ZAB协议保证数据一致性；临时节点在客户端断开后自动删除；不存在主从同步延迟导致的锁丢失。

### 7.2 设计要点总结

1. **互斥性是基础**：任意时刻只有一个持有者
2. **避免死锁**：必须有过期机制
3. **正确释放**：验证持有者身份后再释放
4. **续期机制**：长任务需要锁续期
5. **高可用**：锁服务本身要高可用
