# 如何设计一个高性能、高可用的订单系统

> 本文从系统设计面试角度，深入剖析企业级订单系统的完整架构设计，涵盖业务建模、技术选型、高性能优化、高可用保障、分布式事务等核心主题。

---

## 一、需求分析与业务建模

### 1.1 核心业务场景

| 场景 | 描述 | QPS 预估 |
| :--- | :--- | :--- |
| **下单** | 用户提交订单，扣减库存，创建订单记录 | 10,000+ |
| **支付** | 订单支付，对接支付网关 | 5,000+ |
| **查询** | 用户/商家查询订单列表和详情 | 50,000+ |
| **取消** | 用户/系统取消订单，释放库存 | 1,000+ |
| **退款** | 订单退款处理 | 500+ |
| **履约** | 发货、物流跟踪、签收 | 2,000+ |

### 1.2 非功能性需求

| 维度 | 要求 | 量化指标 |
| :--- | :--- | :--- |
| **性能** | 低延迟下单 | P99 < 200ms |
| **吞吐** | 支撑大促峰值 | 10万+ QPS |
| **可用性** | 核心链路高可用 | 99.99% |
| **一致性** | 订单与库存一致 | 最终一致 |
| **扩展性** | 支撑业务增长 | 水平扩展 |
| **数据量** | 海量订单存储 | 日增千万级 |

### 1.3 业务约束

| 约束 | 说明 |
| :--- | :--- |
| **超卖防控** | 库存扣减必须准确，不能超卖 |
| **订单唯一** | 防止重复下单 |
| **支付时效** | 未支付订单需自动取消 |
| **数据合规** | 订单数据需保留 N 年 |

### 2.2 服务划分原则

| 原则 | 说明 |
| :--- | :--- |
| **单一职责** | 每个服务只负责一个业务领域 |
| **高内聚低耦合** | 服务内部高度内聚，服务间松耦合 |
| **数据自治** | 每个服务拥有自己的数据库 |
| **独立部署** | 服务可独立开发、测试、部署 |
| **容错设计** | 服务间调用有熔断、降级、重试 |

### 2.3 核心服务职责

| 服务 | 职责 | 核心能力 |
| :--- | :--- | :--- |
| **Order Service** | 订单生命周期管理 | 创建、取消、状态流转 |
| **Inventory Service** | 库存管理 | 扣减、回滚、预占 |
| **Payment Service** | 支付处理 | 支付、退款、对账 |
| **Product Service** | 商品信息 | 商品详情、价格、SKU |
| **Cart Service** | 购物车 | 添加、删除、结算 |
| **User Service** | 用户信息 | 用户详情、地址 |
| **Coupon Service** | 优惠券 | 发放、核销、校验 |
| **Logistics Service** | 物流履约 | 发货、跟踪、签收 |

### 3.3 订单号生成策略

**要求**：
- 全局唯一
- 趋势递增（利于数据库索引）
- 信息安全（不可推测）
- 高性能生成

**推荐方案：改进版 Snowflake**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         订单号结构 (64 bits)                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  ┌───────┬────────────────────────┬────────────┬────────────┬────────────┐  │
│  │ Sign  │      Timestamp         │  Datacenter│  Machine   │  Sequence  │  │
│  │ 1 bit │        41 bits         │   5 bits   │   5 bits   │  12 bits   │  │
│  └───────┴────────────────────────┴────────────┴────────────┴────────────┘  │
│                                                                              │
│  • Sign: 固定为 0                                                            │
│  • Timestamp: 毫秒时间戳 (约 69 年)                                          │
│  • Datacenter: 数据中心 ID (0-31)                                            │
│  • Machine: 机器 ID (0-31)                                                   │
│  • Sequence: 序列号 (0-4095)                                                 │
│                                                                              │
│  理论 QPS: 4096 * 1000 = 400万/秒/节点                                       │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

**业务友好格式（可选）**：

```
格式: {业务标识}{时间}{机器}{序列号}
示例: OD20250107143052100001

OD         - 订单标识
20250107   - 日期
143052     - 时间
1          - 机器ID
00001      - 序列号
```


**分片键选择考量**：

| 分片键 | 优点 | 缺点 |
| :--- | :--- | :--- |
| **user_id** | 用户查询自己订单高效 | 商家查询需要聚合 |
| **order_no** | 订单查询高效 | 用户查询需要聚合 |
| **shop_id** | 商家查询高效 | 用户查询需要聚合 |

**最佳实践**：
- 主表使用 user_id 分片（C端场景为主）
- 建立 order_no → user_id 的映射（Redis）
- 商家视角通过 ES 异步索引解决

### 6.3 扣减方案对比

| 方案 | 实现方式 | 优点 | 缺点 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **数据库扣减** | UPDATE SET stock = stock - N WHERE stock >= N | 简单可靠 | 性能瓶颈 | 低并发 |
| **Redis 扣减** | DECRBY + Lua 脚本 | 高性能 | 需同步DB | 高并发 |
| **预扣+异步确认** | 先预扣，支付后确认 | 防止恶意锁库存 | 实现复杂 | 电商大促 |
| **分布式库存** | 库存分片，多节点扣减 | 极高性能 | 实现复杂 | 秒杀场景 |

### 6.4 Redis + Lua 扣减方案

**Lua 脚本**：

```lua
-- 库存扣减脚本
-- KEYS[1]: 库存key
-- ARGV[1]: 扣减数量
-- 返回: 1-成功, 0-库存不足

local stock = tonumber(redis.call('GET', KEYS[1]) or 0)
local num = tonumber(ARGV[1])

if stock >= num then
    redis.call('DECRBY', KEYS[1], num)
    return 1
else
    return 0
end
```

**流程**：

```
1. Redis 扣减库存 (Lua 原子操作)
2. 扣减成功 → 创建订单 → 异步同步 DB
3. 扣减失败 → 直接返回库存不足

补偿机制:
• 定时对账 Redis 与 DB 库存
• 订单取消/超时 → 释放 Redis 库存
```

## 八、幂等性设计

### 8.1 幂等场景

| 场景 | 原因 | 后果 |
| :--- | :--- | :--- |
| 用户重复点击 | 网络延迟、用户焦虑 | 重复下单 |
| 前端重试 | 超时重试 | 重复下单 |
| MQ 重复投递 | 消费失败重试 | 重复扣库存 |
| 支付回调重复 | 支付平台重试 | 重复记账 |

### 8.2 幂等实现方案

**方案一：唯一约束**

```
• 利用数据库唯一索引
• 适用于: 订单创建 (order_no 唯一)
```

**方案二：Token 机制**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          Token 防重机制                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  1. 获取 Token                                                               │
│     Client ─────> Server: GET /api/order/token                              │
│     Server ─────> Client: token = UUID                                      │
│     Server: Redis SET token:xxx 1 EX 600                                    │
│                                                                              │
│  2. 提交订单 (带 Token)                                                       │
│     Client ─────> Server: POST /api/order {token: xxx, ...}                 │
│                                                                              │
│  3. 验证并删除 Token (原子操作)                                               │
│     Server: Redis DEL token:xxx                                             │
│     • 删除成功 (返回1) → 首次请求，继续处理                                    │
│     • 删除失败 (返回0) → 重复请求，拒绝                                        │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

**方案三：请求去重表**

```sql
CREATE TABLE t_request_record (
    id BIGINT PRIMARY KEY,
    request_id VARCHAR(64) UNIQUE,  -- 请求唯一标识
    biz_type VARCHAR(32),           -- 业务类型
    status TINYINT,                 -- 处理状态
    result TEXT,                    -- 处理结果
    create_time DATETIME
);

-- 处理流程
1. INSERT INTO t_request_record (request_id, ...)
2. 如果插入成功 → 执行业务逻辑
3. 如果唯一键冲突 → 查询历史结果返回
```

**方案四：状态机幂等**

```
• 利用状态机前置状态校验
• UPDATE t_order SET status = 20 WHERE order_no = ? AND status = 10
• 只有状态正确才能更新，天然幂等
```

### 8.3 幂等方案选择

| 场景 | 推荐方案 |
| :--- | :--- |
| 创建订单 | Token + 唯一约束 |
| 支付回调 | 幂等表 + 状态机 |
| 库存扣减 | 请求ID + Redis 去重 |
| 消息消费 | 幂等表 (message_id) |

| **配置中心** | Nacos / Apollo | 动态配置、灰度发布 |
| **注册中心** | Nacos / Consul | 服务发现、健康检查 |
| **链路追踪** | SkyWalking / Jaeger | 无侵入、性能好 |
| **监控** | Prometheus + Grafana | 云原生标准 |
| **日志** | ELK / Loki | 全文搜索、可视化 |
| **容器编排** | Kubernetes | 事实标准 |

### 14.2 设计原则总结

| 原则 | 实践 |
| :--- | :--- |
| **分层架构** | 接入层 → 服务层 → 数据层 |
| **服务拆分** | 单一职责、领域驱动 |
| **数据分片** | 按用户分库分表 |
| **异步解耦** | 消息队列解耦非核心流程 |
| **缓存加速** | 多级缓存、热点数据特殊处理 |
| **容错设计** | 熔断、降级、限流、重试 |
| **幂等保证** | Token、去重表、状态机 |
| **最终一致** | 事务消息、补偿机制 |
| **可观测性** | Metrics、Logging、Tracing |
| **自动化运维** | CI/CD、自动扩缩容 |
