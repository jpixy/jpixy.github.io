# 分布式事务解决方案

## 一、分布式事务问题

### 1.1 问题来源

**单体应用**：
- 单一数据库
- 本地事务保证ACID
- 简单可靠

**微服务架构**：
- 多个数据库
- 跨服务操作
- 本地事务不够用

### 1.2 典型场景

**电商下单**：
- 订单服务：创建订单
- 库存服务：扣减库存
- 账户服务：扣减余额
- 需要保证全部成功或全部失败

### 1.3 一致性要求

**强一致性**：
- 操作完成时所有节点数据一致
- 难以实现，性能差

**最终一致性**：
- 允许短暂不一致
- 最终达到一致状态
- 主流选择

---

## 二、理论基础

### 2.1 CAP定理

**C（一致性）**：所有节点数据一致

**A（可用性）**：请求能得到响应

**P（分区容错）**：网络分区时系统能继续工作

**结论**：只能同时满足两个，分布式系统必须P，所以在C和A之间选择

### 2.2 BASE理论

**BA（Basically Available）**：基本可用

**S（Soft State）**：软状态，允许中间状态

**E（Eventually Consistent）**：最终一致性

**核心思想**：放弃强一致性，换取可用性

---

## 三、2PC（两阶段提交）

### 3.1 原理

**第一阶段（Prepare）**：
1. 协调者询问所有参与者是否可以提交
2. 参与者执行事务但不提交
3. 参与者回复Yes或No

**第二阶段（Commit）**：
1. 如果所有参与者都Yes，协调者发送Commit
2. 如果有任何No，协调者发送Rollback
3. 参与者执行提交或回滚

### 3.2 问题

**同步阻塞**：
- Prepare后资源锁定
- 等待Commit指令
- 阻塞时间长

**单点问题**：
- 协调者故障导致阻塞
- 参与者不知道是提交还是回滚

**数据不一致**：
- Commit阶段部分节点故障
- 可能导致不一致

### 3.3 适用场景

- 数据库层面的分布式事务
- XA规范实现
- 要求强一致但性能要求不高

## 四、TCC模式

### 4.1 原理

**Try**：
- 资源预留
- 不真正执行业务

**Confirm**：
- 确认执行
- 使用Try预留的资源

**Cancel**：
- 取消执行
- 释放Try预留的资源

### 4.2 示例

**扣减库存**：
- Try：冻结库存（可用库存-10，冻结库存+10）
- Confirm：扣减冻结库存（冻结库存-10）
- Cancel：解冻库存（冻结库存-10，可用库存+10）

**扣减余额**：
- Try：冻结余额
- Confirm：扣减冻结余额
- Cancel：解冻余额

### 4.3 特点

**优点**：
- 业务灵活
- 不锁定数据库资源

**缺点**：
- 代码侵入性强
- 需要实现三个接口
- 需要处理空回滚、幂等、悬挂

### 4.4 异常处理

**空回滚**：
- Try未执行，直接Cancel
- Cancel需要判断是否有Try记录

**幂等**：
- Confirm/Cancel可能重试
- 需要保证幂等性

**悬挂**：
- Cancel先于Try执行
- 需要拒绝后续的Try

### 4.5 适用场景

- 需要强一致性
- 对性能要求高
- 业务可以拆分为Try/Confirm/Cancel

## 五、Saga模式

### 5.1 原理

**正向操作**：
- 将长事务拆分为多个本地事务
- 依次执行T1 → T2 → T3

**补偿操作**：
- 每个本地事务有对应的补偿操作
- 失败时依次执行补偿C3 → C2 → C1

### 5.2 执行方式

**编排式（Orchestration）**：
- 有中央协调者
- 协调者控制流程
- 统一管理容易

**协同式（Choreography）**：
- 无中央协调者
- 通过事件驱动
- 服务间通过事件通信

### 5.3 示例

**下单流程**：

```
正向：创建订单 → 扣减库存 → 扣减余额 → 创建物流
补偿：取消物流 ← 回滚余额 ← 回滚库存 ← 取消订单
```

若扣减余额失败：
1. 执行回滚库存
2. 执行取消订单
3. 返回失败

### 5.4 特点

**优点**：
- 无全局锁
- 每步都是本地事务
- 简单易理解

**缺点**：
- 隔离性差
- 需要设计补偿逻辑
- 可能出现中间状态

### 5.5 适用场景

- 长事务
- 业务可设计补偿
- 对一致性要求不是极高

## 六、本地消息表

### 6.1 原理

1. 业务操作和消息写入在同一事务
2. 消息异步发送给消费者
3. 消费者处理成功后确认
4. 定时任务重试未确认的消息

### 6.2 流程

**生产者**：
1. 开启事务
2. 执行业务操作
3. 写入本地消息表
4. 提交事务
5. 异步发送消息

**消费者**：
1. 接收消息
2. 幂等处理业务
3. 确认消息

### 6.3 特点

**优点**：
- 实现相对简单
- 可靠性高

**缺点**：
- 需要轮询表
- 耦合本地存储

---

## 七、可靠消息最终一致

### 7.1 原理

利用消息队列保证消息可靠传递：
1. 预发送消息（不可消费）
2. 执行本地事务
3. 确认消息可消费
4. 消费者消费处理

### 7.2 RocketMQ事务消息

**流程**：
1. 发送半消息（暂不可消费）
2. 执行本地事务
3. 提交或回滚消息
4. 消费者消费

**回查机制**：
- 长时间未提交的消息
- MQ主动回查生产者
- 确认事务状态

### 7.3 特点

**优点**：
- 解耦好
- 可靠性有MQ保证

**缺点**：
- 依赖MQ
- 最终一致性

## 八、方案对比与选型

### 8.1 对比

| 方案 | 一致性 | 性能 | 侵入性 | 复杂度 |
|------|--------|------|--------|--------|
| 2PC | 强 | 低 | 低 | 低 |
| TCC | 强 | 高 | 高 | 高 |
| Saga | 最终 | 高 | 中 | 中 |
| 消息表 | 最终 | 中 | 中 | 低 |
| 事务消息 | 最终 | 高 | 低 | 中 |

### 8.2 选型建议

| 场景 | 推荐方案 |
|------|----------|
| 强一致性、性能要求不高 | 2PC/XA |
| 强一致性、高性能 | TCC |
| 长事务、可接受最终一致 | Saga |
| 异步场景、松耦合 | 消息最终一致 |
| 对账类业务 | 本地消息表 |

### 8.3 最佳实践

**优先避免分布式事务**：
- 合理设计服务边界
- 相关数据放在同一服务

**接受最终一致性**：
- 大多数业务可以接受
- 降低复杂度

**实现幂等**：
- 所有操作都要幂等
- 防止重试导致问题

**做好对账**：
- 定期数据对账
- 发现并修复不一致

## 九、Seata框架

### 9.1 简介

阿里开源的分布式事务解决方案，支持多种模式。

### 9.2 AT模式

**原理**：
- 基于本地事务的自动补偿
- 无代码侵入
- 自动生成回滚SQL

**流程**：
1. 解析SQL，记录前镜像
2. 执行SQL
3. 记录后镜像
4. 生成回滚日志
5. 提交或回滚时自动处理

### 9.3 其他模式

**TCC模式**：需要实现Try/Confirm/Cancel

**Saga模式**：状态机编排

**XA模式**：标准XA协议

## 十、面试要点

### 10.1 常见追问

**Q：2PC和TCC的区别？**
A：2PC在数据库层面，资源锁定时间长；TCC在业务层面，资源预留而非锁定，性能更好但侵入性强。

**Q：Saga如何保证隔离性？**
A：Saga隔离性差，可能看到中间状态。通过业务设计规避，如使用状态机、加业务锁。

**Q：如何处理TCC的空回滚？**
A：Cancel执行前检查是否有Try记录。有则回滚，无则记录Cancel已执行，拒绝后续Try。

**Q：如何选择分布式事务方案？**
A：首先考虑能否避免分布式事务；其次考虑业务是否接受最终一致性；最后根据性能、侵入性选择具体方案。

### 10.2 核心要点

1. **能不用就不用**：优先通过设计规避
2. **最终一致性为主**：强一致性代价高
3. **幂等是基础**：所有操作必须幂等
4. **补偿是兜底**：设计好补偿逻辑
5. **对账是保障**：发现并修复问题
