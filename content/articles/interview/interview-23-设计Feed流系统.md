# 如何设计一个Feed流系统

## 一、需求分析

### 1.1 什么是Feed流

Feed流是按时间线聚合的内容列表，常见于：
- 社交网络（微博、Twitter、朋友圈）
- 资讯应用（今日头条、知乎）
- 电商推荐

### 1.2 核心需求

- **发布内容**：用户发布的内容需要推送给粉丝
- **查看Feed**：用户看到关注人的最新内容
- **时间线排序**：按时间倒序或算法排序
- **实时性**：新内容尽快出现在粉丝Feed中

### 1.3 规模估算

假设1亿用户，日活3000万，每用户平均关注200人：

```
每日发布量：3000万 × 5条 = 1.5亿条
每日阅读量：3000万 × 50次 = 15亿次
Feed刷新QPS：15亿 / 86400 ≈ 17000 QPS
峰值QPS：约10万
```

## 二、推拉模式

Feed流最核心的设计决策是**推模式**还是**拉模式**。

### 2.1 推模式（Push / Write Fanout）

**原理**：用户发布内容时，主动推送到每个粉丝的收件箱。

**流程**：
1. 用户A发布内容
2. 查询A的所有粉丝列表
3. 将内容ID写入每个粉丝的收件箱
4. 粉丝读取时直接查自己的收件箱

**优点**：
- 读取极快，直接读收件箱
- 适合读多写少场景

**缺点**：
- 写放大严重（1条内容写N份）
- 大V发布延迟高
- 存储空间大

### 2.2 拉模式（Pull / Read Fanout）

**原理**：用户查看Feed时，实时拉取关注人的最新内容并合并。

**流程**：
1. 用户B请求Feed
2. 查询B关注的所有人
3. 从每个人的发件箱拉取最新内容
4. 合并排序后返回

**优点**：
- 写入简单，只写发件箱
- 存储空间小
- 无延迟问题

**缺点**：
- 读取慢，需要多次查询和合并
- 不适合关注数很多的用户

### 2.3 推拉结合

**实际系统通常采用推拉结合**：

**策略一：按用户类型区分**
- 普通用户（粉丝少）：推模式
- 大V（粉丝多）：拉模式或延迟推

**策略二：按粉丝活跃度区分**
- 活跃粉丝：推
- 不活跃粉丝：拉（登录时才拉）

**策略三：热度分层**
- 实时收件箱只保留最近N条
- 更早的内容走拉模式

## 三、系统架构

### 3.1 整体架构

```
客户端 → API Gateway → 负载均衡
                          │
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
    发布服务          Feed服务          用户服务
        │                 │                 │
        ↓                 ↓                 ↓
    消息队列 ←──────→ 推送服务          关系服务
        │                 │
        ↓                 ↓
    内容存储          收件箱（Redis）
        │
        ↓
    MySQL/MongoDB
```

### 3.2 核心组件

**发布服务**：
- 接收用户发布的内容
- 写入内容存储
- 发送消息到队列触发推送

**推送服务**：
- 消费发布消息
- 查询粉丝列表
- 写入粉丝收件箱

**Feed服务**：
- 读取用户收件箱
- 必要时拉取大V内容
- 合并排序返回

**收件箱存储**：
- 使用Redis Sorted Set
- score为时间戳
- value为内容ID

## 四、关键设计

### 4.1 收件箱设计

**使用Redis Sorted Set**：
- 每个用户一个key：`inbox:{user_id}`
- 按时间戳排序
- 支持分页获取

**限制大小**：
- 只保留最近N条（如1000条）
- 更早的走拉模式或归档

**过期策略**：
- 设置TTL，不活跃用户自动清理
- 活跃时重新构建

### 4.2 大V处理

**问题**：大V粉丝可能上千万，推送延迟高

**方案一：延迟推送**
- 发布后先入队列
- 后台异步分批推送
- 用户可能有短暂延迟

**方案二：拉模式**
- 大V的内容不推送
- 粉丝读取时实时拉取并合并

**方案三：活跃粉丝优先**
- 先推给活跃粉丝（如最近7天登录）
- 不活跃粉丝登录时再拉取

### 4.3 热点处理

**热门内容**：
- 识别热门内容（转发/点赞多）
- 缓存热门内容详情
- 减少DB查询

**热门用户**：
- 大V的粉丝列表缓存
- 分片存储减少单点压力

### 4.4 实时性保障

**发布到可见的延迟**：
- 推模式：取决于推送速度
- 拉模式：几乎无延迟

**优化手段**：
- 消息队列分区，并行消费
- 批量写入收件箱
- 异步处理非核心逻辑

## 五、Feed排序

### 5.1 时间排序

**纯时间倒序**：
- 最新的在最前
- 简单直接
- 可能错过重要内容

### 5.2 算法排序

**排序因素**：
- 时间衰减
- 互动量（点赞、评论、转发）
- 关系亲密度
- 内容质量
- 用户兴趣匹配

**实现方式**：
- 离线计算：定期批量计算排序分
- 在线计算：实时计算，但开销大
- 混合方式：粗排离线，精排在线

### 5.3 热门/推荐混合

- 关注的内容为主
- 穿插推荐内容
- 广告内容按规则插入

## 六、数据存储

### 6.1 内容存储

**MySQL**：
- 存储内容元数据
- 分库分表（按用户ID或时间）
- 主从分离

**MongoDB**：
- 适合文档型内容
- 支持灵活字段

**对象存储**：
- 图片、视频等媒体文件
- 通过CDN加速

### 6.2 关系存储

**关注关系**：
- MySQL存储双向关系
- 关注列表、粉丝列表分开存储
- 大V粉丝列表需要分页

**缓存**：
- 活跃用户的关注列表缓存到Redis
- 粉丝计数缓存

### 6.3 收件箱存储

**Redis**：
- 存储最近的内容ID列表
- Sorted Set按时间排序
- 支持分页和范围查询

**持久化**：
- Redis持久化保障
- 或使用HBase等持久存储

## 七、扩展功能

### 7.1 未读计数

- 记录用户上次阅读时间
- 计算之后的新内容数量
- 可以使用独立计数器

### 7.2 刷新与分页

**下拉刷新**：获取最新内容

**上滑加载更多**：
- 使用cursor/max_id分页
- 避免传统offset分页的问题

### 7.3 内容过滤

- 已读内容不再显示（可选）
- 屏蔽用户/关键词过滤
- 内容审核状态过滤

## 八、面试要点

### 8.1 常见追问

**Q：推模式和拉模式如何选择？**
A：读多写少选推，写多读少选拉。实际系统通常混合使用，普通用户推，大V拉，按粉丝活跃度分层。

**Q：大V发一条内容，百万粉丝如何处理？**
A：延迟推送分批处理；只推活跃粉丝；或采用拉模式，粉丝读取时实时拉取。

**Q：如何保证Feed不丢失不重复？**
A：使用消息队列保证推送不丢失；收件箱使用Set去重；幂等处理。

**Q：如何处理取关后的Feed？**
A：推模式下取关后收件箱已有的内容不删除（复杂且必要性低）；拉模式下自然过滤。

### 8.2 设计要点总结

1. **推拉模式**是核心决策，需根据读写比和用户分布选择
2. **大V处理**是难点，需要特殊优化
3. **收件箱设计**要考虑存储和性能平衡
4. **实时性**和**资源消耗**需要权衡
5. **排序策略**影响用户体验
