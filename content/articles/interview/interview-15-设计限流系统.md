# 如何设计一个限流系统

## 一、限流概述

### 1.1 为什么需要限流

- **保护系统**：防止过载导致服务不可用
- **公平使用**：避免少数用户占用过多资源
- **成本控制**：防止恶意调用产生高额费用
- **稳定性**：保障核心功能在高压下仍可用

### 1.2 限流维度

| 维度 | 说明 | 示例 |
|------|------|------|
| 用户 | 限制单用户请求量 | 每用户100次/分钟 |
| IP | 限制单IP请求量 | 每IP1000次/分钟 |
| 接口 | 限制单接口总量 | 该接口10000次/秒 |
| 服务 | 限制服务总量 | 服务最大5万QPS |

### 1.3 限流位置

- **客户端**：减少无效请求（不可靠，可绑过）
- **网关层**：统一入口限流
- **服务层**：服务自我保护
- **数据层**：数据库连接池限制

## 二、限流算法

### 2.1 固定窗口计数器

**原理**：将时间划分为固定窗口（如1秒），在每个窗口内计数。

**优点**：
- 实现简单
- 内存占用小

**缺点**：
- 临界问题：窗口边界可能出现2倍流量
- 例如：限制100次/秒，第1秒最后500ms有100次，第2秒最前500ms又有100次，1秒内实际200次

### 2.2 滑动窗口计数器

**原理**：将窗口细分为多个小窗口，统计最近N个小窗口的总数。

**示例**：1秒分为10个100ms的小窗口

**优点**：
- 平滑度比固定窗口好
- 实现相对简单

**缺点**：
- 仍有一定的临界问题
- 需要更多内存存储多个窗口

### 2.3 滑动日志

**原理**：记录每个请求的时间戳，统计时间窗口内的请求数。

**优点**：
- 精确限流
- 无临界问题

**缺点**：
- 内存占用大
- 性能开销高

### 2.4 漏桶算法（Leaky Bucket）

**原理**：
- 请求进入桶中排队
- 以固定速率从桶中流出处理
- 桶满则拒绝新请求

**特点**：
- 流出速率恒定
- 平滑流量
- 无法应对突发流量

**适用场景**：需要严格平滑流量的场景

### 2.5 令牌桶算法（Token Bucket）

**原理**：
- 以固定速率向桶中添加令牌
- 每个请求需要获取令牌才能执行
- 桶有最大容量
- 无令牌则拒绝或等待

**特点**：
- 允许一定程度的突发流量（桶中积累的令牌）
- 平均速率受控
- 最常用的限流算法

**参数**：
- 令牌生成速率（rate）
- 桶容量（burst）

**适用场景**：大多数限流场景

### 2.6 算法对比

| 算法 | 突发流量 | 精确度 | 实现复杂度 | 内存占用 |
|------|----------|--------|-----------|----------|
| 固定窗口 | 可能超限 | 低 | 低 | 低 |
| 滑动窗口 | 较好 | 中 | 中 | 中 |
| 漏桶 | 完全平滑 | 高 | 中 | 低 |
| 令牌桶 | 允许突发 | 高 | 中 | 低 |

## 三、单机限流

### 3.1 实现方式

**基于内存的计数器**：
- 使用ConcurrentHashMap存储计数
- 适合简单场景

**Guava RateLimiter**：
- 令牌桶实现
- 支持预热
- Java生态常用

**Sentinel**：
- 阿里开源
- 功能丰富
- 支持多种限流模式

### 3.2 限流粒度

**接口级限流**：针对单个接口

**用户级限流**：针对用户ID

**资源级限流**：针对特定资源（如商品ID）

### 3.3 限流响应

**拒绝请求**：返回429状态码

**排队等待**：请求进入队列

**降级处理**：返回兜底数据

## 四、分布式限流

### 4.1 为什么需要分布式限流

单机限流只能保护单个实例，无法实现：
- 全局统一限流（如用户全局100次/分钟）
- 多实例共享配额
- 精确的总量控制

### 4.2 基于Redis的实现

**方案一：简单计数器**

使用Redis的INCR命令，设置过期时间。

问题：固定窗口的临界问题

**方案二：滑动窗口**

使用Redis Sorted Set：
- 成员为请求ID
- 分数为时间戳
- 查询时统计时间窗口内的数量
- 删除过期数据

**方案三：令牌桶**

使用Lua脚本保证原子性：
1. 计算从上次到现在应该添加的令牌数
2. 更新令牌数（不超过桶容量）
3. 尝试获取令牌
4. 返回是否成功

### 4.3 性能优化

**本地缓存 + 远程同步**：
- 每个实例分配部分配额
- 本地消费配额
- 定期与Redis同步
- 减少Redis访问

**批量获取令牌**：
- 一次获取多个令牌
- 本地分配
- 减少网络往返

## 五、限流策略

### 5.1 静态限流

配置固定的限流阈值，如：每秒1000次

适用于负载稳定的场景。

### 5.2 动态限流

根据系统状态自动调整阈值。

**基于指标**：
- CPU使用率高时降低阈值
- 响应时间上升时降低阈值
- 错误率上升时降低阈值

**自适应限流**：
- BBR算法：根据RTT和带宽估算
- Sentinel的系统自适应保护

### 5.3 分级限流

不同级别的请求不同限流策略。

**VIP用户**：更高配额

**核心功能**：预留配额

**非核心功能**：优先限流

### 5.4 熔断降级

限流是预防性保护，熔断是故障时保护。

**熔断触发**：
- 错误率超过阈值
- 响应时间过长

**熔断状态**：
- 关闭：正常请求
- 打开：拒绝请求
- 半开：尝试恢复

## 六、架构设计

### 6.1 整体架构

```
           ┌─────────────────────────────┐
           │          客户端             │
           └──────────────┬──────────────┘
                          ↓
           ┌─────────────────────────────┐
           │     API Gateway / 网关       │
           │    （入口限流、黑白名单）     │
           └──────────────┬──────────────┘
                          ↓
           ┌─────────────────────────────┐
           │        业务服务层            │
           │    （服务级限流、熔断）       │
           └──────────────┬──────────────┘
                          ↓
           ┌─────────────────────────────┐
           │          数据层              │
           │    （连接池、队列限制）       │
           └─────────────────────────────┘
                          ↑
           ┌─────────────────────────────┐
           │      Redis / 配置中心        │
           │    （限流计数、规则配置）     │
           └─────────────────────────────┘
```

### 6.2 网关层限流

**优势**：
- 统一入口，覆盖所有请求
- 可以实现全局限流
- 对业务代码无侵入

**实现方式**：
- Nginx：limit_req模块
- Kong：rate-limiting插件
- 自研网关：集成限流组件

### 6.3 服务层限流

**优势**：
- 针对具体服务特点
- 更精细的控制
- 服务自我保护

**实现方式**：
- Sentinel
- Hystrix
- Resilience4j

## 七、生产实践

### 7.1 限流配置

**配置要素**：
- 限流维度（用户/IP/接口）
- 时间窗口（秒/分钟/小时）
- 阈值
- 处理方式（拒绝/排队/降级）

**配置管理**：
- 配置中心统一管理
- 支持动态调整
- 按环境区分

### 7.2 监控告警

**监控指标**：
- 限流触发次数
- 被拒绝请求数
- 当前QPS
- 配额使用率

**告警场景**：
- 限流频繁触发
- 配额即将用尽
- 异常流量激增

### 7.3 应急处理

**预案**：
- 紧急调整阈值
- 开启降级模式
- 黑名单处理

**操作**：
- 通过配置中心实时生效
- 无需重启服务

## 八、面试要点

### 8.1 常见追问

**Q：令牌桶和漏桶的区别？**
A：漏桶以恒定速率流出，无法处理突发；令牌桶允许积累令牌应对突发，但平均速率受控。

**Q：分布式限流如何保证精确？**
A：使用Redis + Lua脚本保证原子性；或使用本地缓存+远程同步的近似方案。

**Q：限流阈值如何确定？**
A：基于压测确定系统容量；预留20-30%余量；根据业务优先级分配。

**Q：如何处理被限流的请求？**
A：返回429状态码和Retry-After头；客户端实现退避重试；或进入队列异步处理。

### 8.2 设计要点总结

1. **算法选择**：令牌桶最通用
2. **维度设计**：根据业务选择合适的限流维度
3. **分布式方案**：Redis + Lua保证原子性
4. **动态调整**：支持运行时修改配置
5. **监控告警**：限流效果可观测
