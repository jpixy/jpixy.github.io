# 如何设计一个即时通讯系统

## 一、需求分析

### 1.1 核心需求

- **单聊**：一对一实时消息
- **群聊**：多人群组消息
- **消息送达**：确保消息不丢失
- **实时性**：消息延迟 < 1秒
- **历史消息**：支持查看聊天记录

### 1.2 扩展需求

- 已读回执
- 消息撤回
- 图片/视频/文件发送
- @提醒
- 消息搜索
- 多端同步

### 1.3 规模估算

假设1亿用户，日活3000万：

```
日消息量：3000万 × 50条 = 15亿条
消息QPS：15亿 / 86400 ≈ 17000 QPS
峰值QPS：约10万
长连接数：3000万同时在线 × 1.5 = 4500万连接
单机10万连接，需要450台连接服务器
```

## 二、通信方式

### 2.1 轮询

**短轮询**：客户端定时请求服务器

缺点：延迟高、服务器压力大、大量无效请求

**长轮询**：客户端请求后服务器hold住，有消息或超时才返回

优点：减少无效请求
缺点：服务器资源占用、不够实时

### 2.2 WebSocket

**特点**：
- 全双工通信
- 连接复用
- 真正的实时推送
- 是IM的首选方案

**工作流程**：
1. HTTP握手升级为WebSocket
2. 保持长连接
3. 服务器主动推送消息
4. 心跳保持连接活跃

### 2.3 移动端推送

**问题**：移动端App切后台后，WebSocket连接可能断开

**解决方案**：
- iOS：APNs（Apple Push Notification Service）
- Android：FCM/厂商推送通道
- 自建推送：保活服务（受系统限制）

**策略**：
- 前台使用WebSocket
- 后台使用厂商推送通道

## 三、系统架构

### 3.1 整体架构

```
           ┌──────────────────────────────────────────┐
           │                  客户端                   │
           │         iOS / Android / Web              │
           └─────────────────┬────────────────────────┘
                             │
                    ┌────────┴────────┐
                    │   接入层         │
                    │  （长连接网关）   │
                    └────────┬────────┘
                             │
        ┌────────────────────┼────────────────────┐
        ↓                    ↓                    ↓
   ┌─────────┐         ┌─────────┐         ┌─────────┐
   │  路由   │         │  消息   │         │  用户   │
   │  服务   │         │  服务   │         │  服务   │
   └────┬────┘         └────┬────┘         └────┬────┘
        │                   │                    │
        ↓                   ↓                    ↓
   ┌─────────┐         ┌─────────┐         ┌─────────┐
   │  路由   │         │  消息   │         │  用户   │
   │  缓存   │         │  队列   │         │  数据   │
   └─────────┘         └────┬────┘         └─────────┘
                            │
                       ┌────┴────┐
                       │  消息   │
                       │  存储   │
                       └─────────┘
```

### 3.2 核心组件

**接入层（Gateway）**：
- 管理客户端长连接
- 协议转换（WebSocket ↔ 内部协议）
- 消息上行/下行转发
- 心跳管理
- 连接鉴权

**路由服务**：
- 维护用户→连接服务器的映射
- 支持按用户ID查找连接位置
- 使用Redis存储路由信息

**消息服务**：
- 消息处理和转发
- 消息持久化
- 消息状态管理

## 四、消息投递

### 4.1 单聊消息流程

**在线投递**：
1. 发送方发消息到Gateway
2. Gateway转发到消息服务
3. 消息服务持久化消息
4. 查询接收方路由信息
5. 若在线，推送到接收方Gateway
6. Gateway推送给接收方客户端
7. 返回发送成功

**离线处理**：
1. 消息存入离线消息表
2. 若有推送渠道，发送推送通知
3. 接收方上线时拉取离线消息

### 4.2 消息可靠性

**确保不丢失**：
- 消息持久化到数据库
- 客户端发送需要服务器ACK
- 服务器推送需要客户端ACK
- 未ACK的消息重试

**消息ID与去重**：
- 每条消息有唯一ID
- 客户端本地去重
- 服务端幂等处理

### 4.3 消息顺序

**问题**：分布式系统消息可能乱序

**解决方案**：
- 使用单调递增的消息序号（per 会话）
- 客户端按序号排序展示
- 落后的消息到达后插入正确位置

**序号生成**：
- 每个会话独立序号
- 使用Redis INCR原子递增
- 或使用发送时间戳

## 五、群聊设计

### 5.1 群聊挑战

- 消息扩散：1条消息需送达N人
- 一致性：所有成员看到相同消息
- 性能：大群消息投递延迟

### 5.2 写扩散 vs 读扩散

**写扩散**：
- 消息写入每个成员的收件箱
- 读取快，直接读自己的消息
- 写放大严重（1条消息写N份）
- 适合小群

**读扩散**：
- 消息只写一份到群消息表
- 读取时从群消息表拉取
- 写入快，但读取可能慢
- 适合大群

**实际选择**：
- 小群（<200人）：写扩散
- 大群（>200人）：读扩散
- 或混合方式

### 5.3 群消息投递

**在线投递**：
1. 发送方发消息
2. 消息持久化到群消息表
3. 查询群在线成员及其路由
4. 并行推送给在线成员
5. 离线成员记录推送标记

**优化**：
- 分批推送，避免单次请求过大
- 使用消息队列异步处理
- 大群只推送活跃成员

## 六、扩展功能

### 6.1 已读回执

**单聊已读**：
- 接收方阅读后发送已读消息
- 标记消息ID已读
- 发送方显示"已读"

**群聊已读**：
- 每个成员发送已读回执
- 存储每条消息的已读列表
- 显示"X人已读"

**实现**：
- 已读状态存储在Redis（热数据）
- 定期同步到数据库

### 6.2 消息撤回

**流程**：
1. 发送方发撤回请求
2. 验证时间限制（如2分钟内）
3. 标记消息为撤回状态
4. 推送撤回通知给接收方
5. 客户端更新显示

**注意**：
- 已经同步的消息可能无法撤回
- 本地缓存需要处理

### 6.3 多端同步

**场景**：用户同时在手机和电脑登录

**同步策略**：
- 消息推送到所有在线终端
- 已读状态多端同步
- 消息序号保证一致性

**实现**：
- 路由表记录多终端连接
- 使用用户级别的消息序号

## 七、存储设计

### 7.1 消息存储

**MySQL**：
- 单聊消息表：按用户ID分表
- 群聊消息表：按群ID分表
- 适合持久化和查询

**HBase/Cassandra**：
- 适合海量消息存储
- 按时间范围查询友好

**存储策略**：
- 热数据：Redis缓存最近N条
- 温数据：MySQL
- 冷数据：归档到廉价存储

### 7.2 关系存储

**好友关系**：MySQL
**群成员**：MySQL + Redis缓存

### 7.3 在线状态

**存储**：Redis
**结构**：Hash存储用户在线信息
**更新**：心跳续期，超时清除

---

## 八、高可用设计

### 8.1 接入层高可用

- 多实例部署
- 客户端断线自动重连
- 切换到其他接入节点

### 8.2 消息不丢失

- 写入成功才返回ACK
- 使用可靠消息队列
- 重试机制

### 8.3 容灾

- 多机房部署
- 消息存储跨机房复制
- 路由信息多副本

## 九、面试要点

### 9.1 常见追问

**Q：如何保证消息不丢失？**
A：发送端ACK、服务端持久化、接收端ACK、离线消息存储。任一环节失败都有重试机制。

**Q：如何处理消息顺序？**
A：使用会话级别的单调递增序号，客户端按序号排序。服务端保证同一会话的消息序号递增。

**Q：群聊消息如何高效投递？**
A：小群写扩散，大群读扩散。使用消息队列异步推送，只推在线和活跃用户。

**Q：如何支持百万用户同时在线？**
A：多台Gateway服务器，每台支持10万+连接。使用路由服务管理用户到Gateway的映射。

### 9.2 设计要点总结

1. **长连接**是IM实时性的基础
2. **消息可靠投递**需要多层保障
3. **群聊设计**要根据群规模选择策略
4. **多端同步**需要统一的消息序号
5. **高可用**需要考虑接入层、存储层、推送通道
