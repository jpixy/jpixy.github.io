## 二、纯内存操作

### 2.1 内存 vs 磁盘速度对比

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        存储介质访问速度对比                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  存储介质              访问延迟              相对速度                         │
│  ─────────────────────────────────────────────────────────────               │
│  CPU L1 缓存           ~1 ns                 基准                            │
│  CPU L2 缓存           ~4 ns                 4x                              │
│  CPU L3 缓存           ~12 ns                12x                             │
│  主内存 (RAM)          ~100 ns               100x                            │
│  SSD 随机读            ~100 μs               100,000x                        │
│  HDD 随机读            ~10 ms                10,000,000x                     │
│                                                                              │
│  结论: 内存访问比 SSD 快 1000 倍，比 HDD 快 100,000 倍                       │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 Redis 内存管理

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        Redis 内存管理机制                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  内存分配器: jemalloc (默认)                                                 │
│  ───────────────────────────                                                 │
│  • 减少内存碎片                                                              │
│  • 多线程友好的内存分配                                                      │
│  • 内存使用统计精确                                                          │
│                                                                              │
│  内存优化策略:                                                               │
│  ───────────────────────────                                                 │
│  • 共享对象池: 0-9999 的整数对象复用                                         │
│  • SDS (Simple Dynamic String): 预分配减少 realloc                          │

│  • 惰性释放: 渐进式删除大 key                                                │
│                                                                              │
│  内存淘汰策略:                                                               │
│  ───────────────────────────                                                 │
│  • volatile-lru: 从设置过期时间的 key 中 LRU 淘汰                            │

│  • volatile-random: 随机淘汰有过期时间的 key                                 │

│  • noeviction: 不淘汰，写入报错                                              │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 SDS (Simple Dynamic String)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        SDS vs C字符串                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  C字符串问题:                                                                │
│  • 获取长度需要 O(n) 遍历                                                    │
│  • 容易缓冲区溢出                                                            │
│  • 修改时需要频繁重新分配内存                                                 │
│  • 不能存储二进制数据 (遇到 \0 截断)                                         │
│                                                                              │
│  SDS 结构:                                                                   │
│  ┌──────────┬──────────┬──────────┬─────────────────────────┐              │
│  │   len    │  alloc   │  flags   │         buf[]          │              │
│  │ (已用)   │ (总分配)  │ (类型)   │      (字符数组)         │              │
│  └──────────┴──────────┴──────────┴─────────────────────────┘              │
│                                                                              │
│  SDS 优势:                                                                   │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │ 特性           │ C字符串        │ SDS                              │   │
│  ├─────────────────────────────────────────────────────────────────────┤   │
│  │ 获取长度       │ O(n)           │ O(1) 直接读取 len               │   │
│  │ 缓冲区安全     │ 不安全         │ 自动扩容检查                     │   │
│  │ 内存分配       │ 每次修改都分配  │ 空间预分配 + 惰性释放            │   │
│  │ 二进制安全     │ 否 (\0结尾)    │ 是 (len 判断长度)                │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                              │
│  空间预分配策略:                                                             │
│  • len < 1MB: 分配 2 * len (翻倍)                                           │
│  • len >= 1MB: 分配 len + 1MB                                               │
│  • 减少 append 操作的内存重分配次数                                          │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.3 跳表 (Skip List)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        跳表结构 (ZSet 底层实现)                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  Level 3:  ────────────────────────────────────────────> 50 ────────> NULL  │
│                                                          │                  │
│  Level 2:  ────────> 20 ────────────────> 40 ──────────> 50 ────────> NULL  │
│                      │                    │              │                  │
│  Level 1:  ───> 10 ─> 20 ───> 30 ───────> 40 ──> 45 ──> 50 ──> 60 ─> NULL  │
│                 │     │       │           │      │      │      │           │
│  Level 0:  ──> 10 ─> 20 ──> 30 ──> 35 ─> 40 ─> 45 ──> 50 ──> 60 ──> NULL   │
│                                                                              │
│  查找过程 (查找 45):                                                         │
│  1. 从最高层开始，50 > 45，下降                                              │
│  2. Level 2: 20 < 45, 40 < 45, 50 > 45，下降                                │
│  3. Level 1: 40 < 45, 45 = 45，找到!                                        │
│                                                                              │
│  时间复杂度: O(log n)                                                        │
│  空间复杂度: O(n)                                                            │
│                                                                              │
│  为什么用跳表而不用红黑树?                                                   │
│  ───────────────────────────                                                 │
│  1. 实现简单: 跳表代码量约 200 行，红黑树约 500 行                           │
│  2. 范围查询友好: 跳表天然有序，范围查询只需遍历链表                         │
│  3. 并发友好: 局部锁即可，红黑树旋转需要更大范围锁                           │
│  4. 内存局部性: 跳表节点连续分配，缓存命中率高                               │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.4 压缩列表 (ziplist)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        压缩列表结构                                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  ┌────────┬────────┬────────┬────────┬────────┬────────┬────────┐          │
│  │zlbytes │ zltail │ zllen  │ entry1 │ entry2 │  ...   │ zlend  │          │
│  │ 4字节  │ 4字节  │ 2字节  │        │        │        │ 1字节  │          │
│  └────────┴────────┴────────┴────────┴────────┴────────┴────────┘          │
│                                                                              │
│  • zlbytes: 整个 ziplist 占用字节数                                         │
│  • zltail: 最后一个 entry 的偏移量 (支持反向遍历)                            │
│  • zllen: entry 数量                                                        │
│  • zlend: 结束标记 (0xFF)                                                   │
│                                                                              │
│  entry 结构:                                                                 │
│  ┌──────────────┬────────────┬────────────┐                                 │
│  │ prevlen      │ encoding   │ content    │                                 │
│  │ (前项长度)   │ (类型+长度)│ (实际数据) │                                 │
│  └──────────────┴────────────┴────────────┘                                 │
│                                                                              │
│  优势:                                                                       │
│  • 连续内存，CPU 缓存友好                                                    │
│  • 紧凑存储，节省内存                                                        │
│  • 小数据量时遍历也很快                                                      │
│                                                                              │
│  使用场景 (自动编码转换):                                                    │
│  • Hash: 元素数 < 512 且 value < 64字节 → ziplist                           │
│  • List: 元素数 < 512 且 value < 64字节 → quicklist (ziplist链表)           │
│  • ZSet: 元素数 < 128 且 value < 64字节 → ziplist                           │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.5 数据结构时间复杂度

| 数据结构 | 操作 | 时间复杂度 | 说明 |
| :--- | :--- | :--- | :--- |
| **String** | GET/SET | O(1) | 直接内存访问 |
| **Hash** | HGET/HSET | O(1) | 哈希表查找 |
| **List** | LPUSH/RPUSH | O(1) | 头尾插入 |
| | LINDEX | O(n) | 按索引查找 |
| **Set** | SADD/SISMEMBER | O(1) | 哈希表实现 |
| **ZSet** | ZADD/ZSCORE | O(log n) | 跳表实现 |
| | ZRANGE | O(log n + m) | m 为返回元素数 |

## 四、单线程模型

### 4.1 为什么单线程也很快

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        单线程模型优势                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  误区: "单线程一定比多线程慢"                                                │
│                                                                              │
│  事实: Redis 单线程足够快，因为:                                             │
│                                                                              │
│  1. 避免锁竞争                                                               │
│     ─────────────                                                            │
│     多线程访问共享数据需要加锁                                               │
│     锁竞争 = 线程阻塞 + 上下文切换 = 性能损耗                                │
│     Redis 单线程完全无锁                                                     │
│                                                                              │
│  2. 避免上下文切换                                                           │
│     ─────────────                                                            │
│     线程切换开销: 保存/恢复寄存器、缓存失效                                  │
│     单次切换成本: 1-10 μs                                                   │
│     高并发时切换频繁，累计开销巨大                                           │
│                                                                              │
│  3. 瓶颈不在 CPU                                                            │
│     ─────────────                                                            │
│     Redis 操作大多是内存操作，耗时极短 (纳秒级)                              │
│     瓶颈在网络 I/O 和内存带宽，不在 CPU                                     │
│     单核 CPU 足以处理 10万+ QPS                                             │
│                                                                              │
│  4. 代码简单可维护                                                           │
│     ─────────────                                                            │
│     无需考虑并发安全，逻辑清晰                                               │
│     bug 更少，更容易优化                                                     │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 五、I/O 多路复用

### 5.1 I/O 模型演进

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        I/O 模型对比                                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  1. 阻塞 I/O (BIO)                                                          │
│     ────────────────                                                         │
│     问题: 一个连接阻塞，所有连接等待                                         │
│     方案: 一个连接一个线程 → 线程开销大                                      │
│                                                                              │
│  2. 非阻塞 I/O (NIO)                                                        │
│     ────────────────                                                         │
│     改进: read 立即返回                                                      │
│     问题: 需要轮询检查所有连接 → CPU 空转                                    │
│                                                                              │
│  3. I/O 多路复用 (select/poll/epoll)                                        │
│     ────────────────────────────────                                         │
│     改进: 一次系统调用监控多个连接                                           │
│     优势: 有事件才处理，无空转                                               │
│                                                                              │
│  ┌───────────────────────────────────────────────────────────────────┐      │
│  │                                                                    │      │
│  │  select:                                                          │      │
│  │  • fd 数量限制 (通常 1024)                                        │      │
│  │  • 每次调用需要拷贝 fd 集合                                       │      │
│  │  • O(n) 遍历检查就绪状态                                          │      │
│  │                                                                    │      │
│  │  poll:                                                            │      │
│  │  • 无 fd 数量限制                                                 │      │
│  │  • 仍需拷贝和遍历                                                 │      │
│  │                                                                    │      │
│  │  epoll (Redis 在 Linux 上使用):                                   │      │
│  │  • 无 fd 数量限制                                                 │      │
│  │  • 事件驱动，O(1) 获取就绪事件                                    │      │
│  │  • 使用 mmap 减少数据拷贝                                         │      │
│  │                                                                    │      │
│  └───────────────────────────────────────────────────────────────────┘      │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 5.2 epoll 工作原理

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        epoll 工作流程                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  1. epoll_create(): 创建 epoll 实例                                         │
│     ─────────────────────────────────                                        │
│     内核创建一个 eventpoll 对象                                              │
│     包含: 红黑树 (存储监控的 fd) + 就绪链表                                  │
│                                                                              │
│  2. epoll_ctl(): 注册/修改/删除监控的 fd                                    │
│     ─────────────────────────────────                                        │
│     EPOLL_CTL_ADD: 添加 fd 到红黑树                                         │
│     EPOLL_CTL_MOD: 修改监控事件                                             │
│     EPOLL_CTL_DEL: 从红黑树删除                                             │
│                                                                              │
│  3. epoll_wait(): 等待事件发生                                              │
│     ─────────────────────────────────                                        │
│     检查就绪链表，有事件则返回                                               │
```

## 附录：面试常见问题

### Q1: Redis 是单线程还是多线程？

**答**: Redis 的**命令执行是单线程的**，但整个进程包含多个线程：
- 主线程：处理客户端请求、执行命令
- 后台线程：AOF 持久化、惰性删除等
- Redis 6.0+：可选的 I/O 多线程（读写网络数据）

### Q2: Redis 单线程为什么还能这么快？

**答**: 
1. **内存操作**：数据在内存中，访问速度极快
2. **高效数据结构**：专门优化的底层实现
3. **无锁设计**：避免锁竞争和上下文切换
4. **I/O 多路复用**：单线程高效处理大量连接
5. **瓶颈不在 CPU**：主要瓶颈在网络和内存带宽

### Q3: Redis 6.0 的多线程是怎么回事？

**答**: Redis 6.0 引入了 **I/O 多线程**：
- 网络读写可以多线程并行
- 命令执行仍然是单线程（保持原子性和简单性）
- 适合大 Value、高并发读写场景
- 配置 `io-threads` 开启

### Q4: 为什么 Redis 用跳表而不用红黑树？

**答**:
1. **实现简单**：跳表代码量是红黑树的 1/3
2. **范围查询高效**：跳表天然有序，直接遍历
3. **并发友好**：局部锁即可，红黑树需要更大范围锁
4. **内存局部性好**：缓存命中率更高
