# 如何设计一个支付系统

## 一、支付系统概述

### 1.1 核心要求

**资金安全**：钱不能多也不能少

**高可用**：支付服务不能中断

**一致性**：交易状态必须准确

**合规性**：满足监管要求

### 1.2 核心流程

```
用户下单 → 收银台 → 支付渠道 → 支付结果 → 通知商户
              ↓
          内部记账
```

### 1.3 关键概念

| 概念 | 说明 |
|------|------|
| 支付订单 | 用户发起的支付请求 |
| 渠道订单 | 发给第三方的支付请求 |
| 交易流水 | 资金变动记录 |
| 对账 | 与渠道核对交易 |
| 清算 | 资金归集和分配 |

---

## 二、系统架构

### 2.1 整体架构

```
┌─────────────────────────────────────────┐
│              接入层                      │
│   收银台 │ 商户API │ 管理后台            │
└─────────────────┬───────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│              交易核心                    │
│   订单服务 │ 支付服务 │ 退款服务         │
└─────────────────┬───────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│              渠道层                      │
│   微信 │ 支付宝 │ 银联 │ 银行           │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│              清算层                      │
│   对账服务 │ 清算服务 │ 结算服务         │
└─────────────────────────────────────────┘
```

### 2.2 核心服务

**订单服务**：
- 创建和管理支付订单
- 订单状态流转
- 订单查询

**支付服务**：
- 调用支付渠道
- 处理支付结果
- 异步通知

**渠道网关**：
- 统一渠道接口
- 路由选择
- 失败重试

**对账服务**：
- 下载渠道对账单
- 对账差异处理
- 异常订单处理

## 三、支付流程

### 3.1 支付流程

**同步流程**：
1. 用户发起支付请求
2. 创建支付订单
3. 调用支付渠道
4. 返回支付链接或二维码
5. 用户完成支付

**异步回调**：
1. 渠道异步通知支付结果
2. 验证通知签名
3. 更新订单状态
4. 通知业务系统

### 3.2 订单状态

```
待支付 → 支付中 → 支付成功
   ↓         ↓
  取消      失败
           
支付成功 → 部分退款 → 全额退款
```

**关键状态**：
- PENDING：待支付
- PAYING：支付中
- SUCCESS：支付成功
- FAILED：支付失败
- CLOSED：已关闭
- REFUNDING：退款中
- REFUNDED：已退款

### 3.3 超时处理

**支付超时**：
- 设置支付有效期（如30分钟）
- 超时自动关闭订单
- 释放库存等资源

**查询补偿**：
- 定时查询未完成订单
- 主动向渠道查询结果
- 更新订单状态

## 四、资金安全

### 4.1 幂等性

**问题**：重复请求导致重复扣款

**解决方案**：
- 使用业务订单号作为唯一键
- 数据库唯一约束
- 先查询后操作

**渠道幂等**：
- 使用商户订单号
- 渠道保证同一订单号只扣一次

### 4.2 事务一致性

**问题**：多步操作需要保证一致性

**解决方案**：
- 本地事务保证单库一致
- 最终一致性保证跨库
- 对账发现并修复差异

### 4.3 资金对账

**为什么对账**：
- 渠道通知可能丢失
- 系统可能出错
- 确保资金准确

**对账流程**：
1. 下载渠道对账单
2. 与本地订单比对
3. 处理差异：
   - 本地有渠道无：查询渠道确认
   - 本地无渠道有：补单
   - 金额不一致：人工处理

### 4.4 防重复支付

**同一订单多次支付**：
- 支付前检查订单状态
- 已支付则拒绝
- 渠道层面保证幂等

**掉单处理**：
- 定时任务查询未完成订单
- 向渠道确认真实状态
- 更新本地状态

## 五、渠道对接

### 5.1 渠道抽象

**统一接口**：
- 发起支付
- 查询订单
- 关闭订单
- 发起退款
- 查询退款

**渠道实现**：
- 微信支付实现
- 支付宝实现
- 银联实现
- 各银行实现

### 5.2 渠道路由

**路由策略**：
- 成本最优
- 成功率最优
- 限额规避
- 渠道状态

**渠道降级**：
- 渠道故障时切换
- 限额用完时切换

### 5.3 渠道安全

**签名验证**：
- 请求签名
- 回调验签
- 防止篡改

**证书管理**：
- 安全存储证书
- 定期更新
- 证书过期监控

## 六、退款设计

### 6.1 退款流程

1. 商户发起退款请求
2. 校验原订单状态
3. 创建退款单
4. 调用渠道退款
5. 异步通知退款结果

### 6.2 退款规则

**金额限制**：
- 退款金额不超过支付金额
- 支持部分退款
- 累计退款不超过原支付

**时间限制**：
- 退款时效（如1年内）
- 渠道限制

### 6.3 退款状态

- PENDING：待处理
- PROCESSING：处理中
- SUCCESS：退款成功
- FAILED：退款失败

---

## 七、清算结算

### 7.1 清算

**目的**：计算各方应收应付

**内容**：
- 商户应结金额
- 平台手续费
- 渠道成本

### 7.2 结算

**结算周期**：
- T+0：当日结算
- T+1：次日结算
- T+N：N日后结算

**结算方式**：
- 自动打款
- 手动提现
- 余额抵扣

### 7.3 分账

**场景**：多方分成

**实现**：
- 支付成功后分账
- 按比例或固定金额
- 延迟分账

## 十、面试要点

### 10.1 常见追问

**Q：如何保证支付不重复扣款？**
A：幂等设计——使用业务订单号作为唯一键；渠道层面通过商户订单号保证幂等；支付前检查订单状态。

**Q：支付掉单如何处理？**
A：定时任务查询未完成订单；主动向渠道查询真实状态；根据结果更新订单；对账发现并补单。

**Q：退款失败如何处理？**
A：记录失败原因；自动或手动重试；超过重试次数人工处理；通知商户。

**Q：如何保证资金准确？**
A：日终对账核对所有交易；差异自动或人工处理；多层校验（订单、流水、账户）。

### 10.2 设计要点总结

1. **幂等性**：防止重复支付
2. **最终一致性**：对账发现和修复问题
3. **渠道抽象**：统一接口，灵活切换
4. **安全第一**：宁可拒绝不可出错
5. **可观测性**：完整的日志和监控
