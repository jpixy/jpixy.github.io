# 如何设计一个通知推送系统

## 一、需求分析

### 1.1 核心需求

- **多渠道推送**：支持App推送、短信、邮件、站内信等
- **高送达率**：消息可靠送达用户
- **大规模**：支持亿级用户的推送
- **实时性**：消息及时送达

### 1.2 推送渠道

| 渠道 | 特点 | 适用场景 |
|------|------|----------|
| App Push | 即时、免费、需安装 | 日常通知 |
| 短信 | 触达率高、有成本 | 重要通知、验证码 |
| 邮件 | 内容丰富、可能进垃圾箱 | 营销、报告 |
| 站内信 | 持久化、用户主动查看 | 系统公告 |
| 微信/钉钉 | 依赖第三方、用户覆盖广 | 企业通知 |

### 1.3 规模估算

假设1亿用户，日活3000万：

```
日通知量：3000万 × 5条 = 1.5亿条
峰值QPS：约5万
多渠道：单条通知可能触发多渠道推送
```

## 二、系统架构

### 2.1 整体架构

```
┌─────────────────────────────────────────┐
│              业务系统                    │
│   订单服务 │ 营销服务 │ 用户服务        │
└─────────────────┬───────────────────────┘
                  ↓ 通知请求
┌─────────────────────────────────────────┐
│              通知平台                    │
│   ┌──────────────────────────────────┐  │
│   │          接入层                   │  │
│   │   API网关 │ 参数校验 │ 限流      │  │
│   └──────────────┬───────────────────┘  │
│                  ↓                       │
│   ┌──────────────────────────────────┐  │
│   │          核心层                   │  │
│   │   模板渲染 │ 路由决策 │ 去重     │  │
│   └──────────────┬───────────────────┘  │
│                  ↓                       │
│   ┌──────────────────────────────────┐  │
│   │          渠道层                   │  │
│   │   Push │ 短信 │ 邮件 │ 站内信   │  │
│   └──────────────────────────────────┘  │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│              第三方服务                  │
│   APNs │ FCM │ 短信网关 │ 邮件服务     │
└─────────────────────────────────────────┘
```

### 2.2 核心组件

**接入层**：
- 接收业务系统的通知请求
- 参数校验和限流
- 异步化处理

**核心层**：
- 模板渲染：将模板和变量组装成最终内容
- 路由决策：决定使用哪些渠道
- 去重过滤：避免重复打扰用户

**渠道层**：
- 每个渠道独立的适配器
- 封装第三方API调用
- 处理渠道特定逻辑

## 三、消息流程

### 3.1 推送流程

**同步阶段**：
1. 业务系统调用通知API
2. 参数校验
3. 写入消息队列
4. 返回请求ID

**异步阶段**：
1. 消费队列消息
2. 用户偏好检查
3. 渠道路由决策
4. 模板渲染
5. 渠道发送
6. 结果记录

### 3.2 消息状态

```
待发送 → 发送中 → 发送成功/失败
              ↓
           重试中 → 最终失败
```

**状态定义**：
- PENDING：待处理
- SENDING：发送中
- SUCCESS：发送成功
- FAILED：发送失败
- DELIVERED：已送达（有回执的渠道）
- READ：已读（支持的渠道）

## 四、渠道管理

### 4.1 App推送

**iOS（APNs）**：
- 需要Apple开发者证书
- 支持静默推送和通知推送
- 有反馈机制告知无效Token

**Android**：
- 厂商通道：华为、小米、OPPO、vivo等
- FCM：Google官方，国内可用性差
- 自建通道：App长连接

**推送策略**：
- 优先使用厂商通道（到达率高）
- 厂商通道失败走自建通道
- 自建通道需要App保活

### 4.2 短信

**多网关**：
- 接入多个短信服务商
- 负载均衡和故障切换
- 成本优化

**模板审核**：
- 短信模板需要运营商审核
- 提前准备常用模板

**发送限制**：
- 同一号码频率限制
- 防止骚扰和刷短信

### 4.3 邮件

**发送方式**：
- SMTP直发
- 第三方服务（SendGrid、AWS SES）

**送达率优化**：
- SPF、DKIM、DMARC配置
- IP预热
- 退订机制

**内容注意**：
- 避免垃圾邮件关键词
- 合理的图文比例

### 4.4 站内信

**存储**：
- 用户消息表
- 支持已读/未读状态

**查询**：
- 分页拉取
- 未读数统计

## 五、路由与策略

### 5.1 渠道选择

**基于消息类型**：
- 验证码：短信优先
- 交易通知：App推送 + 短信
- 营销活动：App推送 + 邮件
- 系统公告：站内信

**基于用户状态**：
- 在线用户：App推送
- 离线用户：短信或等待上线

**基于渠道状态**：
- 渠道故障时降级
- 渠道拥堵时切换

### 5.2 用户偏好

**偏好维度**：
- 接收渠道偏好
- 接收时间偏好（免打扰时段）
- 消息类型偏好

**偏好来源**：
- 用户主动设置
- 系统默认配置
- 法规要求（营销需用户同意）

### 5.3 防骚扰策略

**频率限制**：
- 单用户单渠道频率上限
- 如：每天最多5条短信

**去重**：
- 相同内容短时间内不重复发送
- 基于内容哈希判断

**时间控制**：
- 夜间不发送（22:00-8:00）
- 遵守用户免打扰设置

## 六、可靠性保障

### 6.1 消息不丢失

**发送端**：
- 异步发送，消息入队确认
- 消息持久化

**处理端**：
- 消费后处理完再确认
- 失败重试

**渠道端**：
- 调用失败重试
- 多渠道备份

### 6.2 重试机制

**重试策略**：
- 指数退避：1s, 2s, 4s, 8s...
- 最大重试次数限制
- 不同渠道不同策略

**重试场景**：
- 网络超时
- 渠道限流
- 临时故障

**不重试场景**：
- 参数错误
- 用户不存在
- 用户拒收

### 6.3 幂等处理

**消息去重**：
- 使用消息ID去重
- 避免重复发送

**接口幂等**：
- 业务方重复调用不会重复发送

## 七、大规模推送

### 7.1 场景特点

全量推送、活动通知等场景：
- 用户量大（百万到亿级）
- 时间窗口有限
- 对系统冲击大

### 7.2 设计要点

**异步处理**：
- 接收请求后立即返回
- 后台异步处理

**分批发送**：
- 将用户分批
- 控制发送速率
- 避免渠道限流

**优先级队列**：
- 大规模推送低优先级
- 不影响实时通知

**进度追踪**：
- 记录发送进度
- 支持暂停/恢复
- 实时统计

### 7.3 性能优化

**批量操作**：
- 批量查询用户信息
- 批量调用渠道API

**并行发送**：
- 多渠道并行
- 分片并行处理

## 八、统计与监控

### 8.1 核心指标

**发送指标**：
- 发送量：总量、分渠道
- 成功率：发送成功/总量
- 送达率：实际送达/发送成功

**用户指标**：
- 打开率：打开数/送达数
- 点击率：点击数/打开数
- 退订率

### 8.2 监控告警

**系统监控**：
- 队列积压
- 处理延迟
- 错误率

**渠道监控**：
- 渠道可用性
- 渠道成功率
- 渠道延迟

**告警规则**：
- 成功率低于阈值
- 队列积压超限
- 渠道故障

## 九、用户体验

### 9.1 消息质量

**内容相关性**：
- 推送用户感兴趣的内容
- 避免无关信息打扰

**发送时机**：
- 选择合适的时间发送
- 考虑用户时区

**频率控制**：
- 避免过度推送
- 合理的推送节奏

### 9.2 退订机制

**法规要求**：
- 营销类必须提供退订
- 一键退订

**实现方式**：
- 邮件底部退订链接
- 短信回复TD退订
- App内设置中心

## 十、面试要点

### 10.1 常见追问

**Q：如何保证消息不丢失？**
A：消息队列持久化；处理完成才确认消费；发送失败重试；多渠道备份；记录发送日志可追溯。

**Q：如何处理大规模推送？**
A：异步处理、分批发送、控制速率、优先级隔离。将用户分片，多实例并行处理，监控进度。

**Q：如何提高送达率？**
A：多渠道配合（推送失败走短信）；App推送优先厂商通道；短信多网关备份；用户偏好管理。

**Q：如何防止骚扰用户？**
A：频率限制、去重过滤、免打扰时段、用户偏好、退订机制。

### 10.2 设计要点总结

1. **多渠道**：不同场景用不同渠道
2. **异步化**：高吞吐、削峰填谷
3. **可靠性**：消息不丢失、失败重试
4. **用户体验**：防骚扰、可退订
5. **可观测**：完善的统计和监控
