# Redis高可用架构

## 一、高可用需求

### 1.1 单机Redis的问题

**可用性风险**：
- 单点故障：机器宕机服务中断
- 容量受限：单机内存有限

**数据安全**：
- 数据丢失风险
- 持久化不能完全保证

### 1.2 高可用目标

- 服务持续可用
- 数据不丢失
- 故障自动恢复
- 可水平扩展

---

## 二、主从复制

### 2.1 基本原理

**架构**：一主多从

**数据流向**：主节点写入，从节点复制

**作用**：
- 数据备份
- 读写分离
- 故障恢复的基础

### 2.2 复制过程

**全量复制**：
1. 从节点发送PSYNC命令
2. 主节点执行BGSAVE生成RDB
3. 主节点发送RDB给从节点
4. 从节点加载RDB
5. 主节点发送复制期间的增量命令

**增量复制**：
1. 从节点发送PSYNC + offset
2. 主节点检查复制积压缓冲区
3. 若offset在缓冲区内，发送增量数据
4. 否则触发全量复制

### 2.3 复制缓冲区

**作用**：保存最近的写命令，支持断线重连的增量复制

**配置**：repl-backlog-size（默认1MB，建议增大）

**重要性**：缓冲区太小会导致频繁全量复制

### 2.4 主从延迟

**产生原因**：
- 网络延迟
- 从节点处理能力
- 复制积压

**影响**：
- 读从节点可能读到旧数据
- 主节点故障可能丢失数据

**监控**：INFO replication 查看复制偏移量

## 三、哨兵模式（Sentinel）

### 3.1 哨兵的作用

- **监控**：监控主从节点运行状态
- **通知**：状态变化时通知管理员
- **自动故障转移**：主节点故障时自动切换
- **配置中心**：客户端通过哨兵获取主节点地址

### 3.2 部署架构

```
┌─────────┐  ┌─────────┐  ┌─────────┐
│Sentinel1│  │Sentinel2│  │Sentinel3│
└────┬────┘  └────┬────┘  └────┬────┘
     │           │           │
     └───────────┼───────────┘
                 ↓ 监控
┌─────────────────────────────────────┐
│                                     │
│    ┌────────┐                       │
│    │ Master │←──复制───┬─────┬─────│
│    └────────┘          │     │     │
│                   ┌────┴──┐ ┌┴────┐│
│                   │Slave 1│ │Slave2││
│                   └───────┘ └─────┘│
└─────────────────────────────────────┘
```

**建议**：至少3个Sentinel实例，奇数个

### 3.3 故障检测

**主观下线（SDOWN）**：
- 单个Sentinel认为节点不可用
- 依据：ping超时

**客观下线（ODOWN）**：
- 多数Sentinel都认为主节点不可用
- 触发故障转移

**配置**：
- sentinel down-after-milliseconds：判断下线的超时时间
- sentinel quorum：确认客观下线的Sentinel数量

### 3.4 故障转移

**选举流程**：
1. Sentinel们选举一个leader
2. Leader负责故障转移

**从节点选择**：
1. 过滤不健康的从节点
2. 选择优先级最高的
3. 选择复制偏移量最大的
4. 选择runid最小的

**切换步骤**：
1. 选中的从节点执行SLAVEOF NO ONE
2. 其他从节点指向新主节点
3. 更新Sentinel配置
4. 通知客户端

### 3.5 客户端连接

**连接方式**：
- 客户端连接Sentinel获取主节点地址
- 订阅Sentinel的频道接收故障转移通知
- 自动切换连接到新主节点

## 四、集群模式（Cluster）

### 4.1 集群特点

- **去中心化**：无需额外组件
- **数据分片**：16384个哈希槽
- **高可用**：节点故障自动切换
- **线性扩展**：可在线增删节点

### 4.2 数据分片

**哈希槽（Slot）**：
- 固定16384个槽
- 每个Key通过CRC16(key) % 16384计算槽
- 每个节点负责一部分槽

**示例**：3个主节点
- 节点A：0-5460
- 节点B：5461-10922
- 节点C：10923-16383

### 4.3 节点通信

**Gossip协议**：
- 节点间定期交换信息
- 传播节点状态
- 无中心节点

**通信内容**：
- 槽分配信息
- 节点状态
- 故障检测

### 4.4 请求路由

**MOVED重定向**：
- 客户端请求错误节点
- 返回MOVED + 正确节点地址
- 客户端重定向并更新缓存

**ASK重定向**：
- 槽正在迁移中
- 返回ASK + 目标节点
- 客户端只临时重定向

**Smart客户端**：
- 缓存槽与节点的映射
- 直接请求正确节点
- 减少重定向次数

### 4.5 故障转移

**故障检测**：
- 节点通过Gossip检测其他节点
- 超过半数认为某节点故障则标记为FAIL

**自动切换**：
- 故障节点的从节点发起选举
- 获得多数主节点投票后成为新主
- 接管原主节点的槽

### 4.6 集群限制

**不支持的操作**：
- 跨槽的多Key操作（除非使用HashTag）
- 跨槽的事务
- 部分命令受限（如KEYS）

**HashTag**：
- 使用{}指定槽计算的部分
- 如：{user:1000}.name 和 {user:1000}.age 在同一槽

## 五、方案对比

| 维度 | 主从复制 | 哨兵模式 | 集群模式 |
|------|----------|----------|----------|
| 高可用 | 手动切换 | 自动切换 | 自动切换 |
| 数据分片 | 不支持 | 不支持 | 支持 |
| 扩展性 | 低 | 低 | 高 |
| 复杂度 | 低 | 中 | 高 |
| 适用场景 | 备份/读分离 | 中小规模HA | 大规模/分片 |

## 六、最佳实践

### 6.1 部署建议

**哨兵模式**：
- 至少3个Sentinel
- 与Redis节点分开部署
- 跨机房/机架部署

**集群模式**：
- 至少6个节点（3主3从）
- 主从节点分开机架
- 预留扩容空间

### 6.2 配置优化

**复制相关**：
- repl-backlog-size：增大到100MB以上
- repl-timeout：根据网络调整

**持久化**：
- 主节点开启AOF
- 从节点可以做RDB备份

### 6.3 监控告警

**关键指标**：
- 主从延迟
- 内存使用
- 连接数
- 命令执行延迟

**告警场景**：
- 主从复制断开
- 内存使用过高
- 主节点故障

## 七、面试要点

### 7.1 常见追问

**Q：哨兵如何判断主节点故障？**
A：主观下线（单个Sentinel认为）+ 客观下线（quorum个Sentinel确认）。客观下线后触发故障转移。

**Q：集群模式为什么是16384个槽？**
A：槽信息需要节点间传播，16384个槽的bitmap只需2KB。作者认为1000个节点以上不推荐集群模式，16384对于1000节点足够。

**Q：Redis集群脑裂如何处理？**
A：配置min-replicas-to-write，主节点连接的从节点少于配置值时拒绝写入，防止网络分区时两个主都接受写入。

**Q：哨兵和集群如何选择？**
A：数据量单机可承载选哨兵，更简单；需要分片扩展选集群。两者都提供高可用。

### 7.2 核心要点

1. **主从复制是基础**：所有高可用方案都依赖
2. **哨兵解决故障自动切换**：适合不需要分片的场景
3. **集群解决分片和扩展**：适合大规模场景
4. **脑裂需要关注**：通过配置降低影响
5. **监控是保障**：及时发现问题
