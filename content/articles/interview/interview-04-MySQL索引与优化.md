# MySQL索引原理与查询优化

## 一、索引基础

### 1.1 什么是索引

索引是帮助MySQL高效获取数据的**数据结构**。类比书籍的目录，通过目录可以快速定位到需要的内容，而不用逐页翻阅。

### 1.2 索引的代价

**空间代价**：索引需要额外存储空间

**时间代价**：插入、更新、删除时需要维护索引

**权衡**：索引不是越多越好，需要根据查询模式合理设计

---

## 二、B+树索引

### 2.1 为什么选择B+树

**对比其他数据结构**：

| 数据结构 | 查找复杂度 | 问题 |
|----------|-----------|------|
| 哈希表 | O(1) | 不支持范围查询 |
| 二叉搜索树 | O(logN) | 可能退化为链表 |
| 平衡二叉树 | O(logN) | 树高较大，IO次数多 |
| B树 | O(logN) | 非叶子节点存数据，范围查询效率低 |
| B+树 | O(logN) | 适合磁盘存储和范围查询 |

### 2.2 B+树特点

**结构特点**：
- 非叶子节点只存储键值（索引）
- 所有数据都存储在叶子节点
- 叶子节点通过指针连接成有序链表
- 每个节点可存储多个键值

**优势**：
- 树高很低（3-4层可存储千万级数据）
- 非叶子节点可存储更多键值，减少IO
- 叶子节点链表支持高效范围查询
- 查询性能稳定（都需要到叶子节点）

### 2.3 InnoDB中的B+树

**聚簇索引（主键索引）**：
- 叶子节点存储完整数据行
- 数据按主键顺序存储
- 一张表只能有一个聚簇索引

**二级索引（辅助索引）**：
- 叶子节点存储主键值
- 查询需要回表（通过主键再查一次）
- 可以有多个二级索引

---

## 三、索引类型

### 3.1 按功能分类

**主键索引**：
- 唯一且不能为NULL
- 一张表只能有一个
- InnoDB中即聚簇索引

**唯一索引**：
- 值唯一，允许NULL
- 可以有多个

**普通索引**：
- 最基本的索引
- 无唯一性约束

**全文索引**：
- 用于全文搜索
- 适用于大文本字段

### 3.2 按结构分类

**单列索引**：一个索引只包含一列

**联合索引（复合索引）**：一个索引包含多列

### 3.3 联合索引

**最左前缀原则**：
- 联合索引(a, b, c)可用于查询：a、a+b、a+b+c
- 不能跳过左边的列直接使用右边的列

**示例**：索引(name, age, city)

| 查询条件 | 是否使用索引 |
|----------|-------------|
| name = 'Tom' | ✓ 使用 |
| name = 'Tom' AND age = 20 | ✓ 使用 |
| name = 'Tom' AND age = 20 AND city = 'BJ' | ✓ 使用 |
| age = 20 | ✗ 不使用 |
| city = 'BJ' | ✗ 不使用 |
| name = 'Tom' AND city = 'BJ' | ✓ 使用name |

## 四、索引优化

### 4.1 覆盖索引

**定义**：查询的列都在索引中，无需回表

**示例**：
- 索引：(name, age)
- 查询：SELECT name, age FROM user WHERE name = 'Tom'
- 只需访问索引，不需要回表查数据

**优势**：减少IO，性能显著提升

### 4.2 索引下推（ICP）

**定义**：将WHERE条件下推到存储引擎层过滤

**示例**：
- 索引：(name, age)
- 查询：SELECT * FROM user WHERE name LIKE 'T%' AND age = 20

**传统方式**：存储引擎返回所有name以T开头的行，MySQL层再过滤age

**索引下推**：存储引擎在索引层就过滤age，减少回表次数

### 4.3 索引选择性

**定义**：不重复的索引值与总记录数的比值

**计算**：选择性 = COUNT(DISTINCT column) / COUNT(*)

**原则**：
- 选择性越高，索引效果越好
- 性别（男/女）选择性低，不适合单独建索引
- 身份证号选择性高，适合建索引

### 4.4 索引设计原则

**建议建索引**：
- 经常用于WHERE条件的列
- 经常用于JOIN的列
- 经常用于ORDER BY的列
- 选择性高的列

**不建议建索引**：
- 表数据量很小
- 频繁更新的列
- 选择性很低的列
- 很少用于查询的列

## 五、查询优化

### 5.1 EXPLAIN分析

使用EXPLAIN查看执行计划：

**关键字段**：

| 字段 | 说明 |
|------|------|
| type | 访问类型（性能：const > ref > range > index > ALL） |
| key | 实际使用的索引 |
| rows | 预估扫描行数 |
| Extra | 额外信息 |

**type值含义**：
- **const**：通过主键或唯一索引查询，最多一条
- **ref**：非唯一索引查询
- **range**：索引范围扫描
- **index**：索引全扫描
- **ALL**：全表扫描（需要优化）

### 5.2 常见优化场景

**避免索引失效**：

| 情况 | 说明 |
|------|------|
| 函数操作 | WHERE YEAR(create_time) = 2025 |
| 隐式转换 | WHERE phone = 13800138000（phone是varchar） |
| 不等于 | WHERE status != 1（可能不走索引） |
| OR条件 | WHERE a = 1 OR b = 2（需要两列都有索引） |
| LIKE左模糊 | WHERE name LIKE '%Tom' |
| 联合索引未遵循最左前缀 | 跳过左边的列 |

**优化技巧**：
- 只查询需要的列，避免SELECT *
- 小表驱动大表
- 分页优化：使用延迟关联
- 避免在索引列上进行运算

### 5.3 分页优化

**问题**：LIMIT 1000000, 10 需要扫描100万行

**优化方案**：

**延迟关联**：
- 先查主键ID
- 再通过ID查完整数据

**游标分页**：
- 使用上一页最后一条的ID作为条件
- WHERE id > last_id LIMIT 10

## 六、索引维护

### 6.1 索引统计

MySQL使用统计信息优化查询计划：
- 索引基数（Cardinality）
- 数据分布

**更新统计信息**：
- ANALYZE TABLE table_name

### 6.2 索引碎片

**产生原因**：
- 频繁删除和更新
- 页分裂

**解决方案**：
- OPTIMIZE TABLE table_name
- 重建表

### 6.3 监控索引使用

**查看未使用的索引**：
- 通过performance_schema
- 定期清理无用索引

## 七、面试要点

### 7.1 常见追问

**Q：为什么InnoDB使用B+树而不是B树？**
A：B+树非叶子节点不存数据，可以存更多键值，树更矮；叶子节点链表支持高效范围查询；查询性能更稳定。

**Q：什么是回表？如何避免？**
A：二级索引查询需要先查索引得到主键，再查聚簇索引得到数据，这个过程叫回表。使用覆盖索引可以避免回表。

**Q：联合索引的最左前缀原则是什么？**
A：联合索引(a,b,c)的B+树按a、b、c的顺序排序。查询必须从最左列开始，不能跳过中间列。

**Q：如何定位慢查询？**
A：开启慢查询日志；使用EXPLAIN分析执行计划；关注type、key、rows、Extra字段。

### 7.2 核心要点

1. **B+树是核心**：理解其结构和优势
2. **聚簇索引与二级索引**：区分存储内容和回表
3. **最左前缀**：联合索引设计的关键
4. **覆盖索引**：避免回表的重要优化
5. **EXPLAIN**：查询优化的必备工具
