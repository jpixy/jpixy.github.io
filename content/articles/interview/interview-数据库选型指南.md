# 数据库选型指南

## 一、数据库分类

### 1.1 关系型数据库（RDBMS）

**代表**：MySQL、PostgreSQL、Oracle、SQL Server

**特点**：
- 结构化数据，表和关系
- SQL查询语言
- ACID事务
- 成熟稳定

### 1.2 NoSQL数据库

**分类**：

| 类型 | 代表 | 特点 |
|------|------|------|
| 键值型 | Redis、Memcached | 简单快速 |
| 文档型 | MongoDB、CouchDB | 灵活模式 |
| 列族型 | HBase、Cassandra | 海量数据 |
| 图数据库 | Neo4j、JanusGraph | 关系分析 |

### 1.3 NewSQL数据库

**代表**：TiDB、CockroachDB、Google Spanner

**特点**：
- 兼具SQL和NoSQL优点
- 分布式架构
- 水平扩展
- 强一致性事务

## 二、主流数据库对比

### 2.1 MySQL

**优势**：
- 开源免费
- 生态成熟
- 运维经验丰富
- 性能优秀

**劣势**：
- 分布式支持有限
- 大表DDL困难
- JSON支持一般

**适用场景**：
- OLTP业务
- 中小规模数据
- 传统Web应用

### 2.2 PostgreSQL

**优势**：
- 功能丰富
- 扩展性强
- JSON支持好
- 地理信息支持

**劣势**：
- 运维复杂度较高
- 高并发性能略逊MySQL

**适用场景**：
- 复杂查询
- 地理信息系统
- 数据仓库
- 需要高级特性

### 2.3 MongoDB

**优势**：
- 灵活的文档模型
- 水平扩展能力
- 开发效率高
- 地理位置查询

**劣势**：
- 事务支持有限（4.0后改善）
- 存储空间较大
- 不擅长复杂关联

**适用场景**：
- 内容管理
- 日志存储
- 快速迭代的应用
- 半结构化数据

### 2.4 Redis

**优势**：
- 极高性能
- 丰富数据结构
- 原子操作

**劣势**：
- 数据量受内存限制
- 持久化有性能开销

**适用场景**：
- 缓存
- 会话存储
- 计数器
- 排行榜

### 2.5 TiDB

**优势**：
- MySQL兼容
- 水平扩展
- 分布式事务
- HTAP能力

**劣势**：
- 运维复杂度高
- 资源消耗大
- 社区相对较小

**适用场景**：
- 大规模OLTP
- 需要分布式事务
- MySQL替代方案

## 三、选型维度

### 3.1 数据特征

| 特征 | 推荐选择 |
|------|----------|
| 结构化/关系明确 | 关系型数据库 |
| 半结构化/灵活模式 | MongoDB等文档库 |
| 高频读写/简单查询 | Redis等键值库 |
| 海量日志/时序数据 | HBase、InfluxDB |
| 复杂关系/图结构 | Neo4j等图数据库 |

### 3.2 业务需求

| 需求 | 推荐选择 |
|------|----------|
| 强一致性事务 | 关系型/NewSQL |
| 最终一致性可接受 | NoSQL |
| 复杂SQL查询 | 关系型 |
| 高吞吐写入 | NoSQL |
| 实时分析 | ClickHouse、TiDB |

### 3.3 规模与扩展

| 规模 | 推荐选择 |
|------|----------|
| 数据量 < 10TB | MySQL/PostgreSQL |
| 数据量 > 10TB | 分库分表/NewSQL/NoSQL |
| 需要线性扩展 | NewSQL/NoSQL |

### 3.4 团队因素

| 因素 | 考虑点 |
|------|--------|
| 技术栈 | 优先选熟悉的技术 |
| 运维能力 | 复杂系统需要相应能力 |
| 社区生态 | 资料、工具、人才 |

## 四、组合使用

### 4.1 多数据库架构

现实中往往需要多种数据库配合：

```
用户请求
    ↓
┌─────────────────────────────────────┐
│              应用层                  │
└────────────────┬────────────────────┘
                 ↓
    ┌────────────┼────────────┐
    ↓            ↓            ↓
┌───────┐   ┌───────┐   ┌───────┐
│ Redis │   │ MySQL │   │ ES    │
│ 缓存   │   │ 主数据 │   │ 搜索  │
└───────┘   └───────┘   └───────┘
```

### 4.2 典型组合

**电商系统**：
- MySQL：订单、用户
- Redis：缓存、会话、购物车
- ES：商品搜索
- MongoDB：商品详情

**社交系统**：
- MySQL：用户、关系
- Redis：信息流、计数
- HBase：消息存储
- Neo4j：社交图谱

### 4.3 数据同步

多数据库需要保持数据一致：
- Binlog同步（MySQL → ES/Redis）
- 消息队列异步同步
- 双写（需处理一致性）

## 五、选型流程

### 5.1 决策流程

```
明确需求 → 评估选项 → 概念验证 → 做出决策 → 持续优化
```

### 5.2 评估清单

**功能评估**：
- 是否满足功能需求
- 查询能力
- 事务支持

**性能评估**：
- 读写吞吐
- 延迟
- 并发能力

**可靠性评估**：
- 高可用方案
- 数据持久性
- 备份恢复

**运维评估**：
- 监控工具
- 运维复杂度
- 文档和社区

**成本评估**：
- 授权费用
- 硬件成本
- 人力成本

### 5.3 避免误区

**不要**：
- 盲目追新技术
- 过早分库分表
- 忽视团队能力
- 忽视运维成本

**应该**：
- 从业务需求出发
- 优先选择熟悉的技术
- 预留扩展空间
- 做好技术储备

## 六、案例分析

### 6.1 案例一：电商订单

**需求**：
- 订单数据，结构化
- 强一致性事务
- 日订单100万，年数据量10亿

**选型**：MySQL分库分表 或 TiDB

**理由**：
- 事务要求高
- 结构化数据
- 分库分表可控制成本
- TiDB简化分片但运维复杂

### 6.2 案例二：用户行为日志

**需求**：
- 每天10亿条日志
- 写多读少
- 7天保留

**选型**：HBase 或 ClickHouse

**理由**：
- 写吞吐要求高
- 时间范围查询
- 成本可控

### 6.3 案例三：内容管理

**需求**：
- 内容字段不固定
- 快速迭代
- 中等规模

**选型**：MongoDB

**理由**：
- 灵活模式
- 开发效率高
- 支持复杂文档

## 七、面试要点

### 7.1 常见追问

**Q：MySQL和MongoDB怎么选？**
A：结构化数据、需要事务、复杂关联选MySQL；半结构化、灵活模式、文档存储选MongoDB。也要考虑团队熟悉度。

**Q：什么时候用Redis替代数据库？**
A：Redis适合缓存和临时数据，不适合作为主数据库。可作为MySQL的前置缓存，加速热点数据访问。

**Q：TiDB能完全替代MySQL吗？**
A：兼容大部分MySQL语法，但有细微差异。单机性能不如MySQL，优势在分布式。中小规模MySQL更简单。

**Q：如何做数据库技术选型？**
A：明确需求（数据模型、规模、一致性）→ 评估候选方案 → POC验证 → 结合团队能力决策。

### 7.2 核心要点

1. **没有银弹**：每种数据库有其适用场景
2. **从需求出发**：先明确需求再选型
3. **组合使用**：复杂系统往往需要多种数据库
4. **团队因素**：技术能力是重要考量
5. **持续演进**：随业务发展调整架构
