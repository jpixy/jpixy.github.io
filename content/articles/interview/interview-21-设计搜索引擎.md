# 如何设计一个搜索引擎

## 一、需求分析

### 1.1 核心需求

- **文档索引**：将文档内容建立索引，支持快速检索
- **关键词搜索**：根据关键词找到相关文档
- **相关性排序**：按相关度排序搜索结果
- **高性能**：毫秒级响应，支持高并发

### 1.2 扩展需求

- 支持短语搜索、模糊搜索、通配符
- 支持过滤和聚合
- 支持高亮显示命中词
- 支持拼写纠错、同义词
- 支持多语言

### 1.3 规模估算

假设索引10亿文档，每天1000万次搜索：

```
文档数：10亿
平均文档大小：1KB，总数据量约1TB
索引大小：通常是原始数据的10-30%，约100-300GB
搜索QPS：峰值约1000 QPS
响应时间：< 100ms
```

## 二、核心概念

### 2.1 倒排索引

**正排索引 vs 倒排索引**：

- 正排索引：文档ID → 文档内容（存储用）
- 倒排索引：词项 → 文档ID列表（检索用）

**倒排索引结构**：

```
词项 → [文档ID, 位置信息, 词频]

示例：
"搜索" → [(doc1, [5,20], 2), (doc3, [8], 1), (doc7, [3,15,28], 3)]
"引擎" → [(doc1, [6], 1), (doc2, [12], 1)]
```

**组成部分**：
- **词典（Dictionary）**：所有不重复的词项
- **倒排列表（Posting List）**：每个词项对应的文档列表

### 2.2 分词（Tokenization）

**分词任务**：
- 将文本切分成词项（Token）
- 去除停用词（的、是、a、the等）
- 词形还原（running → run）
- 大小写统一

**中文分词挑战**：
- 无天然分隔符
- 歧义："结婚的和尚未结婚的"
- 新词识别

**分词方法**：
- **基于词典**：最大匹配、最短路径
- **基于统计**：HMM、CRF
- **混合方法**：词典 + 统计

## 三、索引构建

### 3.1 索引流程

```
原始文档 → 解析提取 → 分词处理 → 构建倒排 → 持久化存储
```

**详细步骤**：
1. **文档采集**：爬虫抓取或数据导入
2. **内容提取**：从HTML/PDF等格式提取文本
3. **分词分析**：切词、过滤、标准化
4. **构建索引**：生成倒排索引结构
5. **索引存储**：写入磁盘，可选压缩

### 3.2 索引优化

**词典优化**：
- 使用Trie树或FST（有限状态转换器）
- 支持快速前缀查询
- 压缩存储空间

**倒排列表压缩**：
- 文档ID用差值编码（Delta Encoding）
- 使用VInt变长整数
- 分块压缩，支持跳跃查询

**跳跃表（Skip List）**：
- 在长倒排列表中建立跳跃指针
- 加速多条件求交集

### 3.3 增量索引

**实时索引**：
- 新文档先写入内存索引
- 定期与磁盘索引合并
- 保证实时可搜索

**索引段合并**：
- 多个小段合并成大段
- 删除的文档真正清理
- 后台异步执行

## 四、检索流程

### 4.1 查询处理

```
用户查询 → 查询解析 → 查询分词 → 查询改写 → 检索执行 → 结果排序 → 返回结果
```

**查询解析**：
- 布尔查询：AND、OR、NOT
- 短语查询："distributed system"
- 范围查询：price:[100 TO 200]
- 通配符：sear*

**查询改写**：
- 同义词扩展：car → car OR automobile
- 拼写纠错：seach → search
- 停用词处理

### 4.2 检索执行

**单词查询**：直接查找倒排列表

**多词查询**：
- AND：取多个倒排列表的交集
- OR：取多个倒排列表的并集

**交集优化**：
- 从最短的列表开始
- 使用跳跃表加速
- 双指针归并

### 4.3 相关性排序

**TF-IDF**：
- **TF（词频）**：词在文档中出现的频率
- **IDF（逆文档频率）**：词的稀有程度
- 得分 = TF × IDF

**BM25**：
- TF-IDF的改进版本
- 考虑文档长度归一化
- 是现代搜索引擎的标准算法

**影响排序的因素**：
- 关键词匹配度
- 文档重要性（类似PageRank）
- 新鲜度（时间权重）
- 用户行为（点击率）

## 五、分布式架构

### 5.1 数据分片

**分片策略**：
- 按文档ID哈希分片
- 每个分片是独立的索引单元
- 分片数在创建索引时确定

**副本策略**：
- 每个分片有多个副本
- 主分片负责写入
- 副本参与查询，提高吞吐

### 5.2 分布式检索

**两阶段查询**：

**第一阶段（Query）**：
1. 协调节点接收查询
2. 将查询发送到所有分片
3. 每个分片返回Top N的文档ID和得分

**第二阶段（Fetch）**：
1. 协调节点合并所有分片结果
2. 全局排序取Top N
3. 根据文档ID获取完整内容

**优化**：
- 请求只发到每个分片的一个副本
- 使用scroll/search_after处理深度分页
- routing参数指定分片，减少查询范围

### 5.3 集群管理

**节点角色**：
- Master节点：管理集群状态
- Data节点：存储数据和执行查询
- Coordinating节点：路由请求

**故障处理**：
- 主分片故障：副本提升为主分片
- 节点故障：分片重新分配
- 自动rebalance

## 六、性能优化

### 6.1 索引优化

- 合理设置分片数（通常每个分片10-50GB）
- 使用合适的分词器
- 只索引需要搜索的字段
- 使用doc_values优化排序和聚合

### 6.2 查询优化

- 使用filter缓存（不计算得分的条件）
- 避免通配符在词首（leading wildcard）
- 合理使用分页，避免深度分页
- 预热常用查询

### 6.3 缓存策略

**查询缓存**：
- 缓存filter查询结果
- 段级别的位图缓存

**字段数据缓存**：
- 用于排序和聚合
- 加载到内存，首次较慢

## 七、实际系统参考

### 7.1 Elasticsearch架构

Elasticsearch是最流行的开源搜索引擎：

- 基于Lucene构建
- RESTful API，JSON文档
- 支持全文搜索、结构化搜索、分析
- 分布式、高可用

**核心概念映射**：
- Index（索引）≈ 数据库
- Type（类型，已废弃）≈ 表
- Document（文档）≈ 行
- Field（字段）≈ 列

### 7.2 其他方案

- **Solr**：老牌搜索引擎，功能丰富
- **Sphinx**：轻量级，适合小规模
- **MeiliSearch**：简单易用，适合产品搜索
- **自研**：适合特定场景优化

## 八、面试要点

### 8.1 常见追问

**Q：为什么用倒排索引而不是正排索引？**
A：正排索引需要遍历所有文档查找关键词，时间复杂度O(N)。倒排索引直接定位包含关键词的文档，时间复杂度O(1)查找 + O(M)遍历结果。

**Q：分词的作用是什么？**
A：将连续文本切分成可索引的词项，是建立倒排索引的前提。中文分词尤其重要，直接影响搜索效果。

**Q：如何处理搜索热词？**
A：使用filter缓存热门查询结果；预热热门词的倒排列表到内存；对热门词分片均衡。

**Q：深度分页为什么慢？**
A：需要从每个分片获取from+size条结果，协调节点要汇总排序所有结果。from越大，开销越大。解决方案是使用scroll API或search_after。

### 8.2 设计要点总结

1. **倒排索引**是搜索引擎的核心数据结构
2. **分词质量**直接影响搜索效果
3. **相关性排序**需要综合多种因素
4. **分布式设计**解决容量和性能问题
5. **缓存和预热**是性能优化关键
