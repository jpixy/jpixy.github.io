## 系统设计的目标

### 核心指标

| 指标 | 定义 | 衡量方式 |
|------|------|----------|
| **可用性** | 系统正常运行的时间比例 | 99.9% = 8.76小时/年故障 |
| **可靠性** | 系统正确执行功能的能力 | MTBF（平均故障间隔） |
| **可扩展性** | 系统处理增长负载的能力 | 水平/垂直扩展 |
| **性能** | 系统响应速度 | 延迟、吞吐量 |
| **可维护性** | 系统修改和维护的难度 | 代码复杂度、文档 |

### 可用性等级

| 等级 | 年故障时间 | 场景 |
|------|------------|------|
| 99% | 3.65天 | 内部工具 |
| 99.9% | 8.76小时 | 一般业务 |
| 99.99% | 52.6分钟 | 核心业务 |
| 99.999% | 5.26分钟 | 金融/医疗 |

## 设计原则

### 单一职责

每个组件只负责一件事，便于理解、测试、维护。

### 关注点分离

- **表现层**：用户界面
- **业务层**：业务逻辑
- **数据层**：数据存储

### 无状态设计

服务实例不保存会话状态，状态存储在外部（Redis、数据库），便于水平扩展。

### 幂等性

同一操作执行多次，结果与执行一次相同。

```
GET  /users/1      # 天然幂等
PUT  /users/1      # 幂等（完整替换）
POST /users        # 非幂等（需要处理）
DELETE /users/1    # 幂等
```

### 最终一致性

分布式系统中，允许短暂不一致，但最终会达成一致。

## 扩展策略

### 垂直扩展（Scale Up）

增强单机能力：更多CPU、内存、更快存储。

**优点**：简单，无需改代码
**缺点**：有上限，单点故障

### 水平扩展（Scale Out）

增加机器数量，负载分散。

**优点**：理论上无上限，高可用
**缺点**：需要处理分布式问题

### 扩展维度

| 维度 | 方式 | 示例 |
|------|------|------|
| X轴 | 克隆 | 多实例 + 负载均衡 |
| Y轴 | 功能分解 | 微服务拆分 |
| Z轴 | 数据分片 | 按用户ID分库 |

## 核心组件

### 负载均衡

**作用**：分发请求到多个服务实例

**层次**：
- L4：基于IP/端口（LVS、HAProxy）
- L7：基于HTTP内容（Nginx、Envoy）

**算法**：
- 轮询（Round Robin）
- 加权轮询
- 最少连接
- IP哈希
- 一致性哈希

### 缓存

**作用**：加速读取，减少数据库压力

**层次**：
- 客户端缓存（浏览器）
- CDN缓存
- 应用层缓存（Redis）
- 数据库缓存

**策略**：
- Cache Aside：读时填充
- Read Through：自动填充
- Write Through：同步写
- Write Behind：异步写

### 消息队列

**作用**：解耦、削峰、异步

**模式**：
- 点对点（队列）
- 发布订阅（主题）

**产品**：Kafka、RabbitMQ、RocketMQ

### 数据库

**类型选择**：
- 关系型：事务、复杂查询
- NoSQL：高吞吐、灵活Schema
- 时序数据库：监控数据
- 图数据库：关系网络

## 数据分区

### 分区策略

**水平分区（Sharding）**：
按某个键将数据分散到多个节点

**分区键选择原则**：
- 分布均匀
- 查询友好
- 避免热点

### 分区方案

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| 范围分区 | 按范围划分 | 简单，可能不均 |
| 哈希分区 | Hash(key) % N | 均匀，扩容复杂 |
| 一致性哈希 | 环形哈希 | 扩容友好 |

### 分区问题

- **跨分区查询**：需要聚合多个分区
- **跨分区事务**：需要分布式事务
- **数据倾斜**：热点分区

---

## 数据复制

### 复制模式

**主从复制**：
- 主节点处理写
- 从节点复制数据，处理读
- 主节点故障需要选举

**多主复制**：
- 多个节点都可写
- 需要处理冲突

**无主复制**：
- 任意节点读写
- 使用Quorum保证一致性

### 一致性级别

| 级别 | 描述 | 场景 |
|------|------|------|
| 强一致 | 读到最新写入 | 金融 |
| 会话一致 | 同一会话读到自己的写入 | 用户操作 |
| 最终一致 | 延迟后一致 | 社交动态 |

## 常见模式

### 读写分离

```
写请求 → 主库
读请求 → 从库
```

适用：读多写少

### CQRS

命令查询责任分离：
- 写操作（Command）→ 写模型
- 读操作（Query）→ 读模型（可优化为宽表）

### 事件溯源

存储事件而非状态，状态由事件回放得出。

### 熔断器

防止故障扩散：
- 关闭状态：正常调用
- 打开状态：快速失败
- 半开状态：尝试恢复

### 限流

保护系统不被压垮：
- 令牌桶：平滑限流
- 漏桶：恒定速率
- 滑动窗口：精确控制

## 设计流程

### 1. 需求澄清

- 功能需求是什么？
- 非功能需求：QPS、延迟、可用性？
- 数据规模：多少用户、多少数据？
- 读写比例？

### 2. 容量估算

```
DAU = 1000万
每用户每天10次请求
QPS = 10M × 10 / 86400 ≈ 1157
峰值QPS = 平均 × 3 ≈ 3500
```

### 3. 高层设计

画出核心组件和数据流。

### 4. 详细设计

深入关键组件：
- API设计
- 数据模型
- 扩展方案

### 5. 瓶颈与权衡

- 识别瓶颈
- 讨论权衡
- 提出优化方案

## 总结

| 概念 | 要点 |
|------|------|
| 核心指标 | 可用性、可靠性、可扩展性、性能 |
| 扩展策略 | 垂直扩展、水平扩展 |
| 核心组件 | 负载均衡、缓存、消息队列、数据库 |
| 数据分区 | 范围、哈希、一致性哈希 |
| 数据复制 | 主从、多主、无主 |
| 设计流程 | 需求→估算→高层→详细→权衡 |

系统设计没有标准答案，关键是理解权衡，根据场景做出合理选择。
