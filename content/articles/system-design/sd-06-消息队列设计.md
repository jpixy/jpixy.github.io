## 消息队列作用

### 解耦

```
传统：订单服务 → 库存服务 → 积分服务 → 通知服务

队列：订单服务 → MQ → 库存服务
                   → 积分服务
                   → 通知服务
```

各服务独立演进，互不影响。

### 异步

```
同步：下单 → 扣库存 → 加积分 → 发通知 → 返回（耗时长）

异步：下单 → 发消息 → 返回（快速）
      后台消费处理其他逻辑
```

### 削峰

```
流量高峰 → 消息堆积 → 按能力消费

避免后端服务被压垮
```

## 核心概念

### 基本模型

```
生产者 → Broker → 消费者

Producer → Topic/Queue → Consumer
```

### 消费模式

**点对点（Queue）**：
```
消息只被一个消费者处理
用于任务分发
```

**发布订阅（Topic）**：
```
消息被所有订阅者处理
用于事件广播
```

### 消费者组

```
Topic → Consumer Group A → Consumer 1
                        → Consumer 2
     → Consumer Group B → Consumer 3
```

- 组内竞争消费（负载均衡）
- 组间广播消费

## 消息可靠性

### 生产端可靠

**确认机制**：
```
Producer → Broker
Broker → ACK
Producer收到ACK才算成功
```

**Kafka ACK级别**：
- acks=0：不等待确认（可能丢失）
- acks=1：Leader确认
- acks=all：所有副本确认

**重试**：
```
发送失败 → 重试N次 → 记录失败消息
```

### Broker可靠

**持久化**：
```
消息写入磁盘
刷盘策略：同步/异步
```

**副本**：
```
多副本存储
Leader故障后Follower接管
```

**Kafka副本**：
```
Partition 0: Leader(Broker1), Follower(Broker2, Broker3)
ISR(In-Sync Replicas): 同步的副本集合
```

### 消费端可靠

**手动确认**：
```
消费成功后才ACK
失败则重新消费
```

**幂等消费**：
```
同一消息消费多次，结果相同
通过唯一ID去重
```

## 消息顺序

### 问题

```
消息发送顺序：A → B → C
消费顺序可能：B → A → C
```

### 全局顺序

**方案**：单分区
```
所有消息发送到同一个分区
一个消费者消费
```

**代价**：吞吐量受限

### 分区顺序

**方案**：按Key分区
```
相同Key的消息发到同一分区
分区内顺序消费
```

**示例**：
```
订单消息按order_id分区
同一订单的消息顺序处理
```

### 消费端保证

```
单线程消费
或按Key分发到同一线程
```

## 延迟消息

### 场景

- 订单30分钟未支付取消
- 预约提醒
- 延迟重试

### 实现方式

**时间轮**：
```
多级时间轮
到期触发投递
```

**延迟队列**：
```
RocketMQ：18个延迟级别
RabbitMQ：TTL + 死信队列
```

**数据库轮询**：
```
定时任务扫描到期消息
投递到正常队列
```

### RocketMQ延迟级别

```
1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
```

## 事务消息

### 场景

```
业务操作 + 发送消息 需要原子性
```

### RocketMQ事务消息

```
1. 发送Half消息（暂不可见）
2. 执行本地事务
3. 成功则Commit，失败则Rollback
4. 超时未确认，Broker回查本地事务状态
```

### 本地消息表

```
1. 业务操作 + 写消息表（本地事务）
2. 定时任务扫描未发送的消息
3. 发送到MQ
4. 标记已发送
```

## 死信队列

### 概念

无法正常消费的消息进入死信队列。

### 产生原因

- 消费失败达到最大重试次数
- 消息过期
- 队列满

### 处理

```
死信队列 → 人工处理
        → 修复后重新投递
        → 记录日志告警
```

---

## 消息积压

### 原因

- 消费者能力不足
- 消费者故障
- 突发流量

### 处理

**临时扩容**：
```
增加消费者实例
增加分区（Kafka）
```

**跳过处理**：
```
丢弃非重要消息
记录日志后续补偿
```

**分流消费**：
```
新建临时Topic
将积压消息转移
增加消费者处理
```

### 监控

- 消息堆积量
- 消费延迟
- 消费者Lag

## Kafka实践

### 生产者配置

```properties
# 可靠性
acks=all
retries=3
enable.idempotence=true

# 性能
batch.size=16384
linger.ms=10
compression.type=lz4
```

### 消费者配置

```properties
# 消费
group.id=my-group
auto.offset.reset=earliest
enable.auto.commit=false

# 性能
max.poll.records=500
fetch.min.bytes=1024
```

### 最佳实践

- 合理设置分区数
- 批量发送提高吞吐
- 手动提交Offset
- 幂等消费
- 监控Lag

## 总结

| 问题 | 方案 |
|------|------|
| 消息丢失 | ACK确认、持久化、副本 |
| 重复消费 | 幂等、去重 |
| 顺序消费 | 单分区、按Key分区 |
| 延迟消息 | 时间轮、延迟级别 |
| 事务消息 | 两阶段、本地消息表 |
| 消息积压 | 扩容、分流、降级 |

消息队列是分布式系统的核心基础设施，需要根据场景权衡可靠性和性能。
