## 高可用概述

### 可用性计算

```
可用性 = MTBF / (MTBF + MTTR)

MTBF = 平均故障间隔时间
MTTR = 平均修复时间
```

**提高可用性的途径**：
- 减少故障频率（提高MTBF）
- 缩短恢复时间（降低MTTR）

### 故障类型

| 类型 | 示例 | 应对 |
|------|------|------|
| 硬件故障 | 磁盘损坏、网络故障 | 冗余 |
| 软件Bug | 代码缺陷、配置错误 | 测试、灰度 |
| 过载 | 流量激增 | 限流、扩容 |
| 依赖故障 | 第三方服务不可用 | 熔断、降级 |
| 人为错误 | 误操作 | 审批、回滚 |
| 安全事件 | DDoS攻击 | 防护、清洗 |

## 冗余设计

### 服务冗余

**多实例部署**：
```
用户 → 负载均衡 → 实例1
                → 实例2
                → 实例3
```

**跨可用区部署**：
```
可用区A: 实例1, 实例2
可用区B: 实例3, 实例4
可用区C: 实例5, 实例6
```

### 数据冗余

**数据库主从复制**：
- 同步复制：强一致，性能低
- 异步复制：高性能，可能丢数据
- 半同步复制：折中

**多副本存储**：
- RAID：单机多盘冗余
- 分布式存储：跨机器多副本

### 网络冗余

- 多网卡Bonding
- 多运营商接入
- 多数据中心

## 故障检测

### 健康检查

**主动检查**：
```
负载均衡 → 定期探测 → 服务实例
                     ↓
                 健康/不健康
```

**检查类型**：
- TCP检查：端口连通性
- HTTP检查：返回200
- 脚本检查：自定义逻辑

### 心跳机制

```
服务实例 → 定期心跳 → 注册中心
              ↓
         超时则下线
```

### 故障判定

**避免误判**：
- 多次检查失败才判定故障
- 考虑网络抖动
- 使用Gossip协议传播状态

## 故障转移

### 自动故障转移

**负载均衡层**：
- 检测到实例故障
- 自动将流量切走

**数据库层**：
- 主库故障
- 自动选举新主
- 应用切换到新主

### 故障转移策略

| 策略 | 描述 | 适用 |
|------|------|------|
| 热备 | 备用节点实时同步，随时接管 | 数据库 |
| 温备 | 备用节点定期同步，需要追数据 | 成本敏感 |
| 冷备 | 备用节点不运行，需要启动 | 灾备 |

### Failover流程

```
1. 检测故障
2. 确认故障（避免脑裂）
3. 选举新主
4. 切换流量
5. 通知相关方
6. 修复旧节点
```

## 多活架构

### 同城双活

```
数据中心A ←→ 数据中心B
   ↓             ↓
  用户A         用户B
```

**特点**：
- 两个机房都服务流量
- 数据双向同步
- 延迟低（同城）

### 异地多活

```
北京机房 ←→ 上海机房 ←→ 广州机房
   ↓            ↓            ↓
 北方用户     中部用户     南方用户
```

**挑战**：
- 数据同步延迟
- 一致性问题
- 流量调度

### 单元化架构

将用户按某种规则划分到不同单元：

```
用户ID % 100 < 50 → 单元A
用户ID % 100 >= 50 → 单元B
```

**优点**：
- 故障隔离
- 降低跨单元调用

## 限流

### 限流算法

**令牌桶**：
- 以固定速率生成令牌
- 请求消耗令牌
- 允许突发流量

**漏桶**：
- 请求进入桶中排队
- 以固定速率处理
- 平滑输出

**滑动窗口**：
- 统计窗口内请求数
- 精确控制

### 限流层次

| 层次 | 方式 |
|------|------|
| 接入层 | Nginx limit_req |
| 网关层 | API Gateway限流 |
| 服务层 | 应用内限流 |
| 分布式 | Redis + Lua |

### 限流维度

- 全局限流：总QPS
- 用户限流：每用户QPS
- IP限流：每IP QPS
- 接口限流：每接口QPS

## 熔断

### 熔断器状态

```
     失败率超阈值
关闭 ─────────────→ 打开
 ↑                    │
 │    成功            │ 超时
 │                    ↓
 └──────────────── 半开
      失败则回到打开
```

### 熔断配置

```yaml
circuitBreaker:
  failureThreshold: 5      # 失败次数阈值
  successThreshold: 3      # 恢复成功次数
  timeout: 30s             # 熔断持续时间
  failureRateThreshold: 50% # 失败率阈值
```

### 熔断后处理

- 返回缓存数据
- 返回默认值
- 返回友好错误
- 走降级逻辑

## 降级

### 降级策略

| 类型 | 描述 | 示例 |
|------|------|------|
| 功能降级 | 关闭非核心功能 | 关闭推荐模块 |
| 数据降级 | 返回缓存/静态数据 | 库存显示"有货" |
| 体验降级 | 降低服务质量 | 图片降低清晰度 |
| 接口降级 | 直接返回错误 | 返回"系统繁忙" |

### 降级开关

```yaml
switches:
  recommendation: false  # 关闭推荐
  comment: false         # 关闭评论
  inventory_realtime: false  # 库存走缓存
```

### 自动降级

根据系统负载自动触发：
- CPU > 80%：降级非核心功能
- 响应时间 > 1s：降级慢接口
- 依赖超时：熔断+降级

## 容灾演练

### 故障注入

**类型**：
- 服务故障：杀进程、返回错误
- 网络故障：延迟、丢包、分区
- 资源故障：CPU满载、磁盘满

### 演练方式

**混沌工程**：
```
1. 定义稳态假设
2. 注入故障
3. 观察系统行为
4. 验证假设
5. 修复问题
```

**工具**：
- Chaos Monkey（Netflix）
- ChaosBlade（阿里）
- Litmus（Kubernetes）

### 演练原则

- 从小规模开始
- 有回滚能力
- 在生产环境演练
- 逐步扩大范围

## 监控告警

### 监控维度

- **基础设施**：CPU、内存、磁盘、网络
- **中间件**：Redis、MySQL、Kafka
- **应用**：QPS、延迟、错误率
- **业务**：订单量、支付成功率

### 告警设计

**分级**：
- P0：立即处理，电话通知
- P1：尽快处理，短信通知
- P2：工作时间处理，IM通知

**避免告警疲劳**：
- 合并同类告警
- 设置合理阈值
- 告警收敛

## 总结

| 维度 | 手段 |
|------|------|
| 冗余 | 多实例、多副本、多机房 |
| 检测 | 健康检查、心跳、监控 |
| 转移 | 自动故障转移、选举 |
| 限流 | 令牌桶、漏桶、滑动窗口 |
| 熔断 | 断路器模式 |
| 降级 | 功能/数据/体验降级 |
| 验证 | 混沌工程、故障演练 |

高可用不是一次性工作，需要持续投入和演练。
