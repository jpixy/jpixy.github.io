## 面试流程

### 典型时间分配（45分钟）

| 阶段 | 时间 | 内容 |
|------|------|------|
| 需求澄清 | 5分钟 | 功能、规模、约束 |
| 高层设计 | 10分钟 | 核心组件、数据流 |
| 详细设计 | 20分钟 | 关键组件深入 |
| 扩展讨论 | 10分钟 | 瓶颈、优化、权衡 |

### 答题框架

```
1. 需求澄清
2. 容量估算
3. API设计
4. 数据模型
5. 高层架构
6. 详细设计
7. 扩展与优化
```

## 需求澄清

### 功能需求

- 核心功能是什么？
- 用户如何使用？
- 哪些功能优先级高？

### 非功能需求

- 用户规模多大？DAU/MAU？
- 读写比例如何？
- 延迟要求？可用性要求？
- 数据规模和增长？

### 约束条件

- 是否需要跨地域？
- 是否有特殊安全要求？
- 预算限制？

### 示例对话

```
面试官：设计一个短链服务

候选人：
- 每天生成多少短链？（10亿）
- 短链长度有要求吗？（尽量短）
- 需要支持自定义短链吗？（可选）
- 短链是否过期？（可选过期时间）
- 需要统计点击吗？（需要）
- 读写比例？（读为主，100:1）
```

## 容量估算

### 估算公式

```
QPS = DAU × 每用户操作数 / 86400
峰值QPS = 平均QPS × 3

存储 = 每条记录大小 × 记录数 × 保留时间

带宽 = QPS × 响应大小
```

### 示例：短链服务

```
DAU = 1亿
每用户每天创建0.1条短链
每天创建1000万条

写QPS = 1000万 / 86400 ≈ 115
峰值写QPS ≈ 350

读QPS = 写 × 100 = 11500
峰值读QPS ≈ 35000

每条记录：
- 短链：7字节
- 长链：500字节
- 元数据：100字节
总计：~600字节

5年存储 = 600B × 1000万 × 365 × 5 ≈ 11TB
```

## 经典案例

### 短链服务

**核心设计**：
```
长链 → Hash/发号器 → 短链
短链 → 查找 → 长链 → 302重定向
```

**关键点**：
- ID生成：分布式ID、Base62编码
- 存储：KV存储（Redis/Cassandra）
- 缓存：热门短链缓存
- 统计：异步写入

### URL爬虫

**核心设计**：
```
种子URL → 调度器 → 下载器 → 解析器 → 存储
                             ↓
                         新URL入队
```

**关键点**：
- 去重：布隆过滤器
- 调度：优先级队列
- 礼貌策略：限制单站频率
- 分布式：多节点协调

### 新闻Feed

**核心设计**：
```
发布：写入 → 推送到粉丝Feed
读取：聚合Feed → 排序 → 返回
```

**推拉模式**：
- 推模式：写放大，读快
- 拉模式：读放大，写快
- 混合：大V用拉，普通用户用推

### 即时通讯

**核心设计**：
```
用户A → WebSocket → 服务器 → WebSocket → 用户B
```

**关键点**：
- 长连接：WebSocket
- 在线状态：心跳、Redis存储
- 离线消息：消息队列、数据库
- 群聊：扇出到成员

### 搜索引擎

**核心设计**：
```
爬虫 → 索引构建 → 倒排索引
查询 → 分词 → 索引检索 → 排序 → 返回
```

**关键点**：
- 倒排索引：词 → 文档列表
- 分布式索引：按文档分片
- 相关性：TF-IDF、BM25
- 缓存：热门查询缓存

### 分布式缓存

**核心设计**：
```
客户端 → 一致性哈希 → 缓存节点
```

**关键点**：
- 分片：一致性哈希
- 复制：主从复制
- 故障转移：自动切换
- 热点：本地缓存

## 常见问题

### 如何处理单点故障？

```
- 冗余：多实例、多副本
- 自动故障转移
- 无状态设计
```

### 如何扩展到10倍流量？

```
- 水平扩展：加机器
- 缓存：减少数据库压力
- 异步：消息队列削峰
- 分片：数据库分库分表
```

### 如何保证数据一致性？

```
- 强一致：分布式事务（代价高）
- 最终一致：事件驱动、补偿
- 业务层面：幂等、去重
```

### 如何处理热点数据？

```
- 本地缓存
- 多副本分散
- 限流保护
```

### 如何监控和调试？

```
- 指标：Prometheus
- 日志：ELK
- 追踪：Jaeger
- 告警：PagerDuty
```

## 面试技巧

### DO

- **主导对话**：不要等面试官问
- **先画图**：用图表达架构
- **量化估算**：用数字支撑设计
- **讨论权衡**：说明为什么选择这个方案
- **承认不知道**：诚实比乱猜好
- **考虑边界情况**：故障、高峰、异常

### DON'T

- **一上来就画架构**：先澄清需求
- **过度设计**：满足需求即可
- **忽视非功能需求**：可用性、扩展性很重要
- **只说方案不说原因**：面试官想了解思路
- **陷入细节**：保持适当抽象层次

### 沟通技巧

```
"让我确认一下需求..."
"我的设计思路是这样的..."
"这里有几个方案，我倾向于X，因为..."
"这个设计的瓶颈在于..."
"如果流量增长10倍，我会..."
```

## 参考回答模板

### 开场

```
"感谢这个问题。在开始设计之前，我想先澄清几个需求..."
```

### 转换

```
"基于这些需求，让我来估算一下容量..."
"现在让我画一个高层架构..."
"接下来我想深入讨论X组件..."
```

### 权衡

```
"这里我选择方案A而非方案B，原因是..."
"这个设计的trade-off是..."
"如果需求变化，我可能会调整..."
```

### 总结

```
"总结一下，这个系统的核心设计是..."
"主要的挑战和解决方案是..."
"还有一些可以优化的点..."
```

## 总结

| 阶段 | 关键动作 |
|------|----------|
| 需求 | 问清楚，不假设 |
| 估算 | 用数字说话 |
| 高层 | 先画图，主要组件 |
| 详细 | 深入关键点 |
| 扩展 | 讨论瓶颈和优化 |

系统设计面试考察的是思维过程，而非标准答案。展示清晰的思路比完美的方案更重要。
