## 微服务概述

### 单体 vs 微服务

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 部署 | 整体部署 | 独立部署 |
| 技术栈 | 统一 | 可异构 |
| 扩展 | 整体扩展 | 按服务扩展 |
| 故障 | 全局影响 | 局部影响 |
| 复杂度 | 代码复杂 | 运维复杂 |

### 微服务特征

- **服务组件化**：通过服务而非库组织
- **围绕业务能力**：按业务划分团队
- **智能端点和哑管道**：REST、消息队列
- **去中心化治理**：各服务独立决策
- **去中心化数据**：每个服务管理自己的数据
- **基础设施自动化**：CI/CD、容器化
- **容错设计**：Design for Failure

## 服务拆分

### 拆分原则

**单一职责**：
一个服务只做一件事。

**高内聚低耦合**：
相关功能聚合，服务间松耦合。

**基于业务能力**：
```
电商系统：
用户服务 → 订单服务 → 商品服务 → 支付服务 → 物流服务
```

### 拆分方法

**领域驱动设计（DDD）**：
```
限界上下文（Bounded Context）= 微服务边界

电商领域：
- 用户上下文：注册、登录、权限
- 商品上下文：商品、分类、库存
- 订单上下文：下单、支付、履约
```

**按业务能力**：
```
核心业务 → 核心服务
支撑业务 → 支撑服务
通用功能 → 公共服务
```

### 拆分粒度

**太粗**：
- 部署耦合
- 扩展受限

**太细**：
- 运维复杂
- 网络开销大
- 分布式事务复杂

**建议**：
- 起步不要太细
- 随着理解加深逐步拆分
- 团队规模匹配服务数量

## 服务通信

### 同步通信

**REST**：
```
GET /users/123
POST /orders
```

**gRPC**：
```
service UserService {
    rpc GetUser(GetUserRequest) returns (User);
}
```

| 协议 | 特点 | 适用 |
|------|------|------|
| REST | 简单、通用 | 对外API |
| gRPC | 高性能、强类型 | 内部服务 |

### 异步通信

**消息队列**：
```
服务A → MQ → 服务B
```

**事件驱动**：
```
订单服务 → 订单创建事件 → 库存服务
                       → 积分服务
                       → 通知服务
```

### 通信模式

| 模式 | 描述 | 场景 |
|------|------|------|
| 请求-响应 | 同步调用 | 查询、即时操作 |
| 事件驱动 | 发布-订阅 | 解耦、通知 |
| 命令模式 | 点对点 | 任务分发 |

## 服务治理

### 服务注册与发现

```
服务启动 → 注册到注册中心
服务调用 → 从注册中心获取地址
服务下线 → 从注册中心注销
```

**产品**：Consul、Eureka、Nacos、etcd

### 负载均衡

**客户端负载均衡**：
```
客户端获取服务列表，自行选择实例
```

**算法**：
- 轮询
- 加权轮询
- 随机
- 最少连接

### 熔断降级

**Hystrix/Resilience4j/Sentinel**：
```
调用失败率超过阈值 → 熔断
返回降级响应
```

### 限流

```
每秒最多处理N个请求
超过则排队或拒绝
```

### 重试

```
失败后重试
设置最大重试次数
指数退避
```

## API网关

### 功能

- **路由**：根据路径转发到不同服务
- **认证**：统一认证
- **限流**：保护后端服务
- **监控**：请求日志、指标
- **协议转换**：HTTP ↔ gRPC
- **聚合**：合并多个服务调用

### 架构

```
客户端 → API网关 → 服务A
                → 服务B
                → 服务C
```

### 产品

| 产品 | 特点 |
|------|------|
| Kong | Nginx+Lua，插件丰富 |
| Envoy | 云原生，服务网格 |
| APISIX | 高性能，国产 |
| Spring Cloud Gateway | Java生态 |

## 服务网格

### 概念

基础设施层，处理服务间通信。

```
服务A ←→ Sidecar Proxy ←→ Sidecar Proxy ←→ 服务B
```

### 功能

- 流量管理
- 安全（mTLS）
- 可观测性

### Istio架构

```
控制平面（istiod）：
- 配置管理
- 证书管理
- 服务发现

数据平面（Envoy）：
- 代理所有流量
- 执行策略
```

## 数据管理

### 每服务一数据库

```
服务A → 数据库A
服务B → 数据库B
```

**优点**：松耦合、独立演进
**挑战**：跨服务查询、数据一致性

### 跨服务查询

**API组合**：
```
聚合服务调用多个服务的API
组合结果返回
```

**CQRS**：
```
写模型：各服务独立
读模型：专门的查询服务，存储聚合数据
```

### 数据一致性

**Saga模式**：
```
本地事务 → 事件/命令 → 下一个本地事务
失败则执行补偿事务
```

**最终一致性**：
```
通过事件驱动
允许短暂不一致
最终达成一致
```

## 部署模式

### 每服务一容器

```dockerfile
FROM openjdk:17
COPY app.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

### Kubernetes部署

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: user-service
  template:
    spec:
      containers:
      - name: user-service
        image: user-service:1.0
        ports:
        - containerPort: 8080
```

### 蓝绿部署

```
蓝环境（当前）← 流量
绿环境（新版）

验证OK后切换：
绿环境（新版）← 流量
```

### 金丝雀部署

```
90%流量 → 旧版本
10%流量 → 新版本

逐步调整比例
```

## 可观测性

### 指标（Metrics）

```
请求量、错误率、延迟
Prometheus + Grafana
```

### 日志（Logs）

```
统一日志格式
集中收集：ELK/Loki
关联trace_id
```

### 追踪（Traces）

```
分布式追踪：Jaeger、Zipkin
请求在各服务的调用链
```

### 关联

```
同一个请求：
trace_id贯穿所有服务
指标、日志、追踪关联
```

## 演进策略

### 绞杀者模式

```
逐步将单体功能迁移到微服务
新功能用微服务
老功能逐步迁移
最终废弃单体
```

### 分支抽象

```
1. 创建抽象层
2. 实现新版本
3. 切换到新版本
4. 删除旧版本
```

### 迁移步骤

```
1. 构建基础设施（CI/CD、监控）
2. 识别边界服务
3. 抽取第一个服务
4. 验证、调整
5. 继续迁移
```

## 总结

| 领域 | 关键点 |
|------|--------|
| 拆分 | DDD、业务能力、适当粒度 |
| 通信 | REST/gRPC、事件驱动 |
| 治理 | 注册发现、熔断限流 |
| 网关 | 统一入口、路由认证 |
| 数据 | 独立数据库、Saga |
| 部署 | 容器化、K8s |
| 观测 | 指标、日志、追踪 |

微服务不是银弹，需要团队能力和基础设施支撑。从简单开始，逐步演进。
