## 缓存架构

### 多级缓存

```
请求 → 浏览器缓存
     → CDN缓存
     → 网关缓存
     → 本地缓存
     → 分布式缓存
     → 数据库
```

### 各级特点

| 层级 | 延迟 | 容量 | 一致性 |
|------|------|------|--------|
| 浏览器 | 最低 | 小 | 客户端控制 |
| CDN | 低 | 大 | TTL过期 |
| 本地缓存 | 极低 | 小 | 进程内 |
| 分布式缓存 | 毫秒级 | 大 | 需要策略 |

### 本地缓存

**实现**：
- Java：Caffeine、Guava Cache
- Go：bigcache、freecache

**适用**：
- 热点数据
- 不常变化的数据
- 允许短暂不一致

### 分布式缓存

**产品**：
- Redis：功能丰富
- Memcached：纯缓存、简单

## 缓存模式

### Cache Aside

**读**：
```
1. 查缓存
2. 命中则返回
3. 未命中则查数据库
4. 写入缓存
5. 返回
```

**写**：
```
1. 更新数据库
2. 删除缓存（而非更新）
```

**为什么删除而非更新**：
- 避免并发写导致脏数据
- 懒加载，按需填充

### Read Through

```
应用 → 缓存层
缓存层：
  命中 → 返回
  未命中 → 查数据库 → 填充缓存 → 返回
```

缓存层封装了数据库访问。

### Write Through

```
应用 → 缓存层 → 数据库
缓存和数据库同步更新
```

### Write Behind

```
应用 → 缓存
缓存 → 异步批量 → 数据库
```

**优点**：写性能高
**缺点**：可能丢数据

## 淘汰策略

### LRU（最近最少使用）

淘汰最久未访问的数据。

**实现**：哈希表 + 双向链表

```
访问时：移动到链表头部
淘汰时：删除链表尾部
```

### LFU（最少频率使用）

淘汰访问频率最低的数据。

**实现**：哈希表 + 频率链表

### FIFO（先进先出）

淘汰最早进入的数据。

### Random（随机）

随机淘汰。

### Redis淘汰策略

| 策略 | 描述 |
|------|------|
| noeviction | 不淘汰，内存满返回错误 |
| allkeys-lru | 所有key中LRU淘汰 |
| volatile-lru | 有过期时间的key中LRU淘汰 |
| allkeys-random | 所有key随机淘汰 |
| volatile-random | 有过期时间的key随机淘汰 |
| volatile-ttl | 淘汰TTL最短的key |
| allkeys-lfu | 所有key中LFU淘汰 |
| volatile-lfu | 有过期时间的key中LFU淘汰 |

## 缓存一致性

### 问题场景

```
线程A：更新数据库
线程B：读取数据库（旧值）
线程B：写入缓存（旧值）
线程A：删除缓存
结果：缓存中是旧值
```

### 延迟双删

```
1. 删除缓存
2. 更新数据库
3. 延迟N毫秒
4. 再次删除缓存
```

### 消息队列保证

```
1. 更新数据库
2. 发送删除缓存消息
3. 消费者删除缓存
4. 失败则重试
```

### 订阅binlog

```
数据库 → binlog → Canal → 删除缓存
```

**优点**：解耦、可靠
**产品**：Canal、Debezium

## 缓存问题

### 缓存穿透

**问题**：查询不存在的数据，每次都打到数据库

**方案1：缓存空值**
```
key不存在 → 缓存null值，设置短TTL
```

**方案2：布隆过滤器**
```
查询前先过布隆过滤器
不存在则直接返回
```

### 缓存击穿

**问题**：热点key过期，大量请求同时打到数据库

**方案1：互斥锁**
```
缓存未命中 → 获取锁
获取成功 → 查数据库 → 写缓存 → 释放锁
获取失败 → 等待重试
```

**方案2：逻辑过期**
```
不设置TTL，value中存储过期时间
发现逻辑过期 → 异步更新
同时返回旧值
```

### 缓存雪崩

**问题**：大量key同时过期，或缓存服务宕机

**方案1：过期时间加随机值**
```
TTL = 基础时间 + random(0, 300)
```

**方案2：缓存预热**
```
系统启动时加载热点数据
```

**方案3：多级缓存**
```
本地缓存兜底
```

**方案4：高可用**
```
Redis集群、主从
```

## 热点Key

### 识别

**客户端统计**：
```go
var hotKeyCounter sync.Map

func Get(key string) {
    count, _ := hotKeyCounter.LoadOrStore(key, 0)
    hotKeyCounter.Store(key, count.(int)+1)
}
```

**Redis监控**：
```bash
redis-cli --hotkeys
redis-cli MONITOR | grep "GET"
```

### 处理

**本地缓存**：
```
热点key存储在本地缓存
减少Redis访问
```

**读写分离**：
```
热点key复制到多个从节点
随机读取分散压力
```

**Key分片**：
```
原key：hot_product_123
分片key：hot_product_123_0, hot_product_123_1, ...
随机选择一个读取
```

## Redis实战

### 数据类型选择

| 场景 | 类型 | 示例 |
|------|------|------|
| 简单缓存 | String | 用户信息JSON |
| 计数器 | String | 访问次数 |
| 对象属性 | Hash | 用户多字段 |
| 排行榜 | ZSet | 分数排名 |
| 队列 | List | 消息队列 |
| 标签/关注 | Set | 用户标签 |
| 位图 | Bitmap | 签到记录 |

### 大Key问题

**识别**：
```bash
redis-cli --bigkeys
```

**拆分**：
```
大Hash → 分多个小Hash
user:1:profile, user:1:settings

大List → 分段
list:0, list:1, list:2
```

### 批量操作

```
-- Pipeline
MGET key1 key2 key3

-- Lua脚本
EVAL "return redis.call('get', KEYS[1])" 1 mykey
```

### 过期策略

**惰性删除**：访问时检查是否过期
**定期删除**：定时扫描删除过期key

**最佳实践**：
- 设置合理的TTL
- 避免大量key同时过期
- 监控内存使用

## 总结

| 问题 | 方案 |
|------|------|
| 穿透 | 空值缓存、布隆过滤器 |
| 击穿 | 互斥锁、逻辑过期 |
| 雪崩 | 随机TTL、多级缓存 |
