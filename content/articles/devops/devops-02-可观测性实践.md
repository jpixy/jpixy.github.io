# 可观测性实践

## 一、可观测性概述

### 1.1 什么是可观测性

可观测性（Observability）是指通过系统的外部输出来推断系统内部状态的能力。它回答的问题是："系统现在怎么样？为什么会这样？"

**监控 vs 可观测性**：
- 监控：告诉你系统是否正常（已知问题的检测）
- 可观测性：帮助你理解系统为什么不正常（未知问题的诊断）

### 1.2 三大支柱

**Metrics（指标）**：
- 可聚合的数值数据
- 如：CPU使用率、请求延迟、错误数
- 用于告警和趋势分析

**Logs（日志）**：
- 离散的事件记录
- 如：错误信息、请求详情、业务操作
- 用于问题排查和审计

**Traces（链路追踪）**：
- 请求在分布式系统中的完整路径
- 如：一次请求经过的所有服务和耗时
- 用于性能分析和故障定位

### 1.3 三者关系

```
Metrics：系统出问题了吗？哪个指标异常？
   ↓
Logs：具体发生了什么错误？
   ↓
Traces：这个请求经过了哪些服务？哪里慢了？
```

三者相互关联：
- 从异常指标定位到相关日志
- 从日志中的TraceID找到完整链路
- 从链路追踪关联到具体服务的日志

## 二、Metrics（指标）

### 2.1 指标类型

**Counter（计数器）**：
- 单调递增的值
- 如：请求总数、错误总数、处理的消息数
- 通过rate()计算速率

**Gauge（仪表盘）**：
- 可增可减的值
- 如：当前连接数、队列长度、CPU使用率
- 反映瞬时状态

**Histogram（直方图）**：
- 数据分布统计
- 如：请求延迟分布、响应体大小分布
- 可计算分位数（P50、P95、P99）

**Summary（摘要）**：
- 客户端计算的分位数
- 类似Histogram，但分位数在客户端计算
- 不可聚合

### 2.2 关键指标

**RED方法**（适用于服务）：
- **R**ate：请求速率
- **E**rror：错误率
- **D**uration：请求延迟

**USE方法**（适用于资源）：
- **U**tilization：使用率
- **S**aturation：饱和度
- **E**rrors：错误数

**四大黄金指标**（Google SRE）：
- 延迟（Latency）
- 流量（Traffic）
- 错误（Errors）
- 饱和度（Saturation）

### 2.3 指标设计原则

**命名规范**：
- 使用下划线分隔
- 包含单位后缀（bytes、seconds、total）
- 遵循{namespace}_{subsystem}_{name}_{unit}格式

**标签设计**：
- 使用有意义的标签
- 控制标签基数（避免高基数）
- 不要把请求ID作为标签

**避免的问题**：
- 标签基数爆炸（如：用户ID作为标签）
- 过多指标（难以维护）
- 指标含义不清

### 2.4 告警设计

**告警原则**：
- 只对需要人工干预的情况告警
- 告警应该是可操作的
- 避免告警疲劳

**告警分级**：
- P0/Critical：立即处理，影响核心功能
- P1/Warning：需要关注，可能恶化
- P2/Info：信息类，无需立即处理

**告警配置要点**：
- 设置合适的阈值（基于历史数据）
- 配置等待时间（避免瞬时抖动）
- 多条件聚合告警

## 三、Logs（日志）

### 3.1 日志级别

| 级别 | 用途 | 生产环境 |
|------|------|----------|
| ERROR | 错误，需要关注 | 必须记录 |
| WARN | 警告，可能有问题 | 记录 |
| INFO | 业务关键信息 | 记录 |
| DEBUG | 调试信息 | 通常关闭 |
| TRACE | 详细跟踪 | 仅调试时开启 |

### 3.2 结构化日志

**为什么需要结构化日志**：
- 便于机器解析
- 支持字段查询
- 便于聚合分析

**JSON日志格式**：
```
{
  "timestamp": "2025-01-16T10:30:00Z",
  "level": "ERROR",
  "service": "order-service",
  "trace_id": "abc123",
  "user_id": "user456",
  "message": "Failed to create order",
  "error": "insufficient inventory",
  "duration_ms": 125
}
```

**关键字段**：
- 时间戳
- 日志级别
- 服务名
- TraceID（用于关联）
- 请求相关信息
- 错误详情

### 3.3 日志采集架构

**ELK Stack**：
- Elasticsearch：存储和查询
- Logstash/Filebeat：采集和转发
- Kibana：可视化

**Loki Stack**：
- Loki：存储和查询（只索引标签）
- Promtail：采集
- Grafana：可视化

**采集方式**：
- Sidecar模式：每个Pod一个采集器
- DaemonSet模式：每个Node一个采集器
- 直接推送：应用直接发送到日志服务

### 3.4 日志最佳实践

**应该记录**：
- 请求的开始和结束
- 关键业务操作
- 错误和异常
- 外部服务调用
- 性能相关信息

**不应该记录**：
- 敏感信息（密码、密钥）
- 个人隐私数据（需脱敏）
- 大量重复的调试信息
- 高频循环内的日志

**日志保留策略**：
- 热数据：7-14天，快速查询
- 温数据：30-90天，可查询
- 冷数据：归档存储，备查

## 四、Traces（链路追踪）

### 4.1 核心概念

**Trace**：一次完整的请求链路

**Span**：链路中的一个操作单元
- SpanID：当前操作的唯一标识
- ParentSpanID：父操作的标识
- 操作名、开始时间、持续时间
- 标签和日志

**Context传播**：
- 将TraceID和SpanID传递到下游
- 通过HTTP Header或消息头
- 标准：W3C Trace Context

### 4.2 追踪实现

**自动埋点**：
- Agent自动注入（Java Agent等）
- 框架集成（Spring、gRPC等）
- 对代码侵入小

**手动埋点**：
- 关键业务逻辑
- 自定义Span
- 添加业务标签

**采样策略**：
- 全量采样：适合低流量
- 概率采样：如1%的请求
- 速率限制：每秒N条
- 自适应采样：基于负载调整

### 4.3 追踪工具

**Jaeger**：
- CNCF项目
- 支持多种存储后端
- 功能完善

**Zipkin**：
- Twitter开源
- 简单易用
- 社区成熟

**OpenTelemetry**：
- 统一的可观测性框架
- 同时支持Metrics、Logs、Traces
- 未来的标准

### 4.4 追踪分析

**延迟分析**：
- 找到耗时最长的Span
- 分析调用链瓶颈
- 识别串行可并行的调用

**错误分析**：
- 找到失败的Span
- 查看错误详情
- 定位根因服务

**依赖分析**：
- 服务拓扑图
- 调用关系
- 识别关键路径

## 五、统一可观测性

### 5.1 关联三支柱

**TraceID贯穿**：
- 日志中包含TraceID
- 指标中可查TraceID样本
- 从任一支柱可跳转到其他

**统一平台**：
- Grafana：统一可视化
- OpenTelemetry：统一采集
- 统一存储或联邦查询

### 5.2 典型排查流程

```
1. 收到告警：某服务P99延迟升高

2. 查看指标：
   - 确认延迟上升的时间点
   - 查看是否有错误率上升
   - 查看依赖服务的指标

3. 查看链路：
   - 找到慢请求的Trace
   - 分析哪个Span耗时异常
   - 定位到具体服务

4. 查看日志：
   - 根据TraceID查找日志
   - 查看错误详情
   - 定位具体代码

5. 解决问题并验证
```

### 5.3 工具选型

**中小规模**：
- Prometheus + Grafana（指标）
- Loki + Grafana（日志）
- Jaeger（链路）

**大规模/企业**：
- Prometheus/Thanos/Cortex（指标）
- Elasticsearch/Loki（日志）
- Jaeger/Tempo（链路）
- 或商业方案（Datadog、New Relic）

## 六、SLI/SLO/SLA

### 6.1 核心概念

**SLI（服务级别指标）**：
- 服务质量的量化度量
- 如：成功率、延迟P99

**SLO（服务级别目标）**：
- SLI的目标值
- 如：成功率>99.9%、P99延迟<200ms

**SLA（服务级别协议）**：
- 对外的承诺
- 包含SLO和违约条款
- 如：月可用性99.9%，违约赔偿

### 6.2 SLI选择

**可用性SLI**：
- 成功请求数 / 总请求数
- 正常运行时间 / 总时间

**延迟SLI**：
- P50、P95、P99延迟
- 延迟<Xms的请求占比

**质量SLI**：
- 数据新鲜度
- 正确性

### 6.3 错误预算

**概念**：允许的不可用时间

**计算**：
- SLO=99.9%，则错误预算=0.1%
- 一个月约43分钟

**使用**：
- 预算充足：可以发布新功能
- 预算紧张：聚焦稳定性
- 预算耗尽：停止发布

## 七、最佳实践

### 7.1 设计原则

**采集与存储分离**：
- 统一采集Agent
- 灵活的存储后端
- 便于扩展和替换

**渐进式实施**：
- 先解决有无问题
- 再优化细节
- 持续迭代

**成本意识**：
- 合理的采样率
- 适当的保留期
- 分层存储

### 7.2 常见问题

**数据量过大**：
- 调整采样率
- 减少日志级别
- 聚合存储

**告警过多**：
- 提高阈值
- 增加等待时间
- 合并相关告警

**关联困难**：
- 统一TraceID
- 统一时间戳
- 统一服务标识

### 7.3 团队实践

**On-Call文化**：
- 轮值制度
- 明确升级路径
- 事后复盘

**Runbook**：
- 告警对应的处理步骤
- 常见问题FAQ
- 联系人信息

**持续改进**：
- 定期回顾告警
- 优化SLO
- 更新监控覆盖

## 八、总结

### 8.1 可观测性成熟度

**Level 1 - 基础**：
- 基本的指标监控
- 日志收集
- 人工排查

**Level 2 - 进阶**：
- 结构化日志
- 分布式追踪
- 告警体系

**Level 3 - 成熟**：
- 三支柱关联
- SLO驱动
- 自动化诊断

### 8.2 核心要点

1. **三支柱缺一不可**，各有用途
2. **关联是关键**，TraceID贯穿
3. **SLO驱动**，明确目标
4. **持续改进**，从实践中学习
