# CI/CD最佳实践

## 一、CI/CD概述

### 1.1 核心概念

**持续集成（CI）**：开发人员频繁地将代码集成到主干，每次集成都通过自动化构建和测试验证。

**持续交付（CD - Delivery）**：在CI基础上，确保代码随时可以部署到生产环境，但部署需要手动触发。

**持续部署（CD - Deployment）**：自动将通过测试的代码部署到生产环境，无需人工干预。

### 1.2 核心价值

- **快速反馈**：问题在几分钟内发现，而非几天后
- **降低风险**：小批量频繁发布，单次变更影响可控
- **提高效率**：自动化减少重复劳动和人为错误
- **加速交付**：从代码提交到上线的周期大幅缩短

## 二、流水线设计

### 2.1 标准流水线阶段

```
代码提交 → 代码检查 → 构建 → 单元测试 → 集成测试 → 制品存储 → 部署测试环境 → 部署生产
```

**各阶段说明**：

| 阶段 | 目的 | 典型耗时 | 失败处理 |
|------|------|----------|----------|
| 代码检查 | 静态分析、代码规范 | 1-2分钟 | 阻断流水线 |
| 构建 | 编译、打包 | 2-10分钟 | 阻断流水线 |
| 单元测试 | 验证代码逻辑 | 2-5分钟 | 阻断流水线 |
| 集成测试 | 验证模块交互 | 5-15分钟 | 阻断流水线 |
| 制品存储 | 保存可部署包 | 1分钟 | 阻断流水线 |
| 部署测试 | 环境验证 | 5-10分钟 | 阻断流水线 |
| 部署生产 | 最终上线 | 5-30分钟 | 自动回滚 |

### 2.2 流水线设计原则

**快速失败**：
- 耗时短的检查放在前面
- 一旦失败立即终止，不浪费资源
- 代码检查 → 编译 → 快速测试 → 慢速测试

**并行执行**：
- 无依赖的任务并行运行
- 如：单元测试与静态分析并行
- 不同模块的测试并行

**环境一致性**：
- 使用容器保证环境一致
- 同一制品部署到所有环境
- 只有配置不同，代码相同

**可追溯性**：
- 每次构建有唯一标识
- 制品与代码版本关联
- 记录完整的构建日志

### 2.3 分支流水线策略

**主干分支（main/master）**：
- 完整的CI/CD流水线
- 自动部署到测试环境
- 生产部署需审批或手动触发

**功能分支（feature）**：
- 仅运行CI流水线
- 不部署到共享环境
- PR合并时触发完整检查

**发布分支（release）**：
- 完整测试
- 可部署到预发布环境
- 用于版本发布准备

## 三、分支策略

### 3.1 常见分支模型

**Git Flow**：
- 主要分支：main、develop
- 辅助分支：feature、release、hotfix
- 适合版本发布周期较长的项目
- 复杂度较高

**GitHub Flow**：
- 只有main分支长期存在
- 功能开发在feature分支
- 通过PR合并到main
- 合并即部署
- 适合持续部署的项目

**Trunk Based Development**：
- 所有人直接在主干开发
- 使用特性开关控制功能发布
- 需要强大的自动化测试
- 适合成熟的CI/CD体系

### 3.2 分支策略选择

| 团队情况 | 推荐策略 |
|----------|----------|
| 小团队、快速迭代 | GitHub Flow |
| 需要版本管理 | Git Flow |
| 成熟CI/CD、高频发布 | Trunk Based |
| 大团队协作 | Git Flow或Trunk Based |

### 3.3 分支保护

**主干分支保护规则**：
- 禁止直接推送，必须通过PR
- 要求Code Review通过
- 要求CI检查通过
- 要求最新代码（无冲突）

## 四、自动化测试

### 4.1 测试金字塔

```
        ┌─────────┐
        │  E2E    │  少量，验证关键流程
        │  测试   │  运行慢，维护成本高
       ┌┴─────────┴┐
       │  集成测试  │  适量，验证模块交互
       │           │  中等速度和成本
      ┌┴───────────┴┐
      │   单元测试   │  大量，验证代码逻辑
      │             │  运行快，维护成本低
      └─────────────┘
```

### 4.2 各层测试策略

**单元测试**：
- 覆盖率目标：70-80%以上
- 每次提交必须运行
- 失败即阻断流水线
- 执行时间控制在5分钟内

**集成测试**：
- 验证模块间接口
- 可使用Mock或真实依赖
- 关键路径必须覆盖
- 执行时间控制在15分钟内

**E2E测试**：
- 覆盖核心用户场景
- 在类生产环境运行
- 可以在部署后运行
- 接受较长执行时间

### 4.3 测试最佳实践

**测试独立性**：
- 测试之间互不依赖
- 每个测试可独立运行
- 便于并行执行

**测试数据管理**：
- 使用工厂模式创建测试数据
- 测试前准备、测试后清理
- 避免依赖共享数据

**失败测试处理**：
- 失败测试必须立即修复
- 不允许"已知失败"长期存在
- 定期清理不稳定测试

## 五、制品管理

### 5.1 制品类型

- **容器镜像**：Docker镜像，推送到Registry
- **二进制包**：JAR、WAR、DEB、RPM等
- **前端资源**：打包后的静态文件
- **配置文件**：环境相关配置

### 5.2 制品版本策略

**语义化版本**：
- 格式：MAJOR.MINOR.PATCH
- 如：1.2.3
- 适合对外发布的产品

**时间戳版本**：
- 格式：YYYYMMDD.HHMMSS
- 如：20250116.143022
- 适合内部持续部署

**Git SHA版本**：
- 使用Git commit SHA作为版本
- 如：abc123def
- 便于追溯代码

**混合版本**：
- 如：1.2.3-abc123def
- 兼顾可读性和追溯性

### 5.3 制品仓库

**常用制品仓库**：
- Docker Registry（Harbor、Docker Hub）
- Maven仓库（Nexus、Artifactory）
- NPM仓库
- Python仓库（PyPI、私有仓库）

**制品保留策略**：
- 保留最近N个版本
- 保留发布到生产的版本
- 定期清理旧版本

## 六、部署策略

### 6.1 常见部署策略

**滚动部署（Rolling）**：
- 逐步替换旧版本实例
- 保持服务可用
- 回滚需要时间

**蓝绿部署（Blue-Green）**：
- 维护两套环境
- 流量整体切换
- 快速回滚
- 资源成本翻倍

**金丝雀部署（Canary）**：
- 先发布小部分实例
- 观察验证后逐步扩大
- 风险可控
- 需要流量控制能力

**A/B测试部署**：
- 不同用户看到不同版本
- 用于功能验证
- 需要流量分流能力

### 6.2 策略选择

| 场景 | 推荐策略 |
|------|----------|
| 普通更新 | 滚动部署 |
| 重大变更 | 金丝雀部署 |
| 需要快速回滚 | 蓝绿部署 |
| 功能实验 | A/B测试 |
| 资源有限 | 滚动部署 |

### 6.3 回滚策略

**自动回滚触发条件**：
- 健康检查连续失败
- 错误率超过阈值
- 响应时间超过阈值

**回滚执行**：
- 立即停止发布
- 恢复到上一稳定版本
- 通知相关人员
- 保留现场供排查

## 七、环境管理

### 7.1 环境分层

**开发环境（Dev）**：
- 开发人员本地或共享
- 频繁变更
- 可能不稳定

**测试环境（Test/QA）**：
- 集成测试使用
- 相对稳定
- 定期刷新数据

**预发布环境（Staging）**：
- 与生产环境一致
- 生产发布前验证
- 可连接生产数据副本

**生产环境（Production）**：
- 面向用户
- 最严格的变更控制
- 完善的监控告警

### 7.2 环境配置管理

**配置与代码分离**：
- 配置不进入代码仓库
- 使用环境变量或配置中心
- 敏感信息加密存储

**配置管理工具**：
- Kubernetes ConfigMap/Secret
- HashiCorp Vault
- AWS Parameter Store
- 配置中心（Apollo、Nacos）

### 7.3 Infrastructure as Code

**IaC原则**：
- 基础设施定义为代码
- 版本控制
- 可重复创建环境

**常用工具**：
- Terraform：多云基础设施
- Ansible：配置管理
- Helm：Kubernetes应用

## 八、安全实践

### 8.1 流水线安全

**代码安全扫描**：
- SAST：静态应用安全测试
- SCA：依赖组件漏洞扫描
- Secret检测：防止密钥泄露

**镜像安全扫描**：
- 容器镜像漏洞扫描
- 基础镜像更新策略
- 签名验证

**权限控制**：
- 最小权限原则
- 生产部署需要审批
- 操作审计日志

### 8.2 密钥管理

**密钥存储**：
- 不在代码中硬编码
- 使用密钥管理服务
- 定期轮换

**流水线中使用密钥**：
- CI/CD平台的Secret功能
- 运行时注入
- 不在日志中打印

## 九、度量与改进

### 9.1 核心指标

**DORA四大指标**：
- **部署频率**：多久部署一次
- **变更前置时间**：从提交到生产的时间
- **变更失败率**：导致问题的部署比例
- **恢复时间**：从故障到恢复的时间

### 9.2 指标参考值

| 级别 | 部署频率 | 前置时间 | 失败率 | 恢复时间 |
|------|----------|----------|--------|----------|
| 精英 | 每天多次 | <1小时 | <15% | <1小时 |
| 高效 | 每天~每周 | 1天~1周 | 16-30% | <1天 |
| 中等 | 每周~每月 | 1周~1月 | 16-30% | <1天 |
| 低效 | 每月~6月 | 1月~6月 | 16-30% | 1周~1月 |

### 9.3 持续改进

**识别瓶颈**：
- 哪个阶段耗时最长
- 哪个阶段失败最多
- 等待时间在哪里

**改进方向**：
- 优化慢速测试
- 增加并行度
- 减少手动环节
- 提高测试稳定性

## 十、总结

### 10.1 CI/CD成熟度

**Level 1 - 基础**：
- 代码提交触发构建
- 自动化单元测试
- 手动部署

**Level 2 - 进阶**：
- 完整测试金字塔
- 自动部署到测试环境
- 制品版本管理

**Level 3 - 成熟**：
- 自动化部署到生产
- 完善的回滚机制
- 度量和持续改进

**Level 4 - 精英**：
- 持续部署（每天多次）
- 特性开关
- 自动化安全扫描
- 混沌工程

### 10.2 实施建议

1. 从简单开始，逐步完善
2. 自动化是基础，测试是保障
3. 关注指标，持续改进
4. 团队文化比工具更重要
