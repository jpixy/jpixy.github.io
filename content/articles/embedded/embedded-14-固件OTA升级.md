# 固件OTA升级设计

OTA（Over-The-Air）升级是物联网设备的核心能力。本文系统讲解OTA系统的设计原理、安全机制与可靠性保障。

---

## 一、OTA升级概述

### 1.1 为什么需要OTA

**业务需求**：
- 功能迭代：持续增加新功能
- Bug修复：远程修复已部署设备的问题
- 安全补丁：及时修补安全漏洞
- 合规要求：满足行业法规

**成本考量**：
- 避免召回：一次召回成本可能是OTA系统成本的百倍
- 减少现场维护：人工升级成本高昂
- 延长产品生命周期：持续更新保持竞争力

### 1.2 OTA面临的挑战

| 挑战 | 说明 |
|-----|------|
| 可靠性 | 升级失败不能变砖 |
| 安全性 | 防止恶意固件注入 |
| 资源受限 | Flash空间有限 |
| 网络不稳定 | 断点续传、重试机制 |
| 多样性 | 不同硬件版本兼容 |

### 1.3 OTA系统组成

**设备端**：
- Bootloader：负责固件选择和加载
- 升级Agent：下载固件、验证、触发升级
- 分区管理：存储多个固件版本

**云端**：
- 固件管理：版本管理、灰度发布
- 设备管理：设备分组、升级策略
- 监控分析：成功率、失败分析

**通信协议**：
- HTTP/HTTPS：简单通用
- MQTT：适合IoT场景
- CoAP：轻量级，适合资源受限设备

## 二、分区设计

### 2.1 单分区方案

```
┌─────────────────────────┐
│      Bootloader         │  固定区域
├─────────────────────────┤
│      Application        │  运行/升级区
├─────────────────────────┤
│    Download Buffer      │  下载缓存
├─────────────────────────┤
│    Config/Data          │  用户数据
└─────────────────────────┘
```

**工作流程**：
1. 下载新固件到Buffer
2. 验证通过后，擦除Application区
3. 将Buffer数据拷贝到Application区
4. 重启运行新固件

**优点**：节省空间，仅需约1.5倍固件大小
**缺点**：拷贝过程断电会导致设备变砖

### 2.2 双分区方案（A/B分区）

```
┌─────────────────────────┐
│      Bootloader         │  固定区域
├─────────────────────────┤
│      Slot A (Active)    │  当前运行
├─────────────────────────┤
│      Slot B (Backup)    │  待升级/备份
├─────────────────────────┤
│    Config/Data          │  用户数据
└─────────────────────────┘
```

**工作流程**：
1. 下载新固件直接写入非活动分区（如Slot B）
2. 验证通过后，更新分区标志
3. 重启，Bootloader加载新固件
4. 若失败，自动回滚到旧分区

**优点**：
- 原子升级：任何时刻断电都安全
- 快速回滚：出问题可立即切回
- 下载与运行解耦

**缺点**：需要2倍固件空间

### 2.3 分区标志设计

Bootloader需要知道启动哪个分区，通过标志位实现：

**标志内容**：
- 活动分区指示：A或B
- 尝试启动次数：用于失败检测
- 固件状态：待验证、已验证、已确认

**存储位置**：
- Flash固定区域（需考虑擦写寿命）
- 备份寄存器（掉电保持）
- OTP区域（一次性可编程）

**状态机**：
```
下载完成 → 待验证 → 启动成功 → 应用确认 → 已确认
                ↓               ↓
             启动失败        超时未确认
                ↓               ↓
              回滚 ←──────────┘
```

## 三、Bootloader设计

### 3.1 Bootloader职责

| 功能 | 说明 |
|-----|------|
| 分区选择 | 根据标志选择启动分区 |
| 完整性检查 | 验证固件CRC/签名 |
| 回滚决策 | 检测启动失败，触发回滚 |
| 紧急恢复 | 提供最后的恢复手段 |
| 跳转执行 | 设置栈指针，跳转到应用 |

### 3.2 启动流程

```
上电
  │
  ├─► 硬件初始化（最小化）
  │
  ├─► 读取分区标志
  │
  ├─► 检查恢复条件（如按键、GPIO）
  │     │
  │     └─► 进入恢复模式
  │
  ├─► 选择活动分区
  │
  ├─► 验证固件完整性
  │     │
  │     └─► 失败 → 尝试备份分区
  │
  ├─► 增加启动计数
  │
  └─► 跳转到应用程序
```

### 3.3 启动失败检测

**看门狗法**：
- Bootloader启动看门狗
- 应用正常运行后喂狗
- 若应用崩溃无法喂狗，复位后检测到连续失败

**启动确认法**：
- 应用启动后需主动调用"确认"接口
- 超时未确认视为失败
- 更可控，但需要应用配合

**启动计数法**：
- Bootloader记录尝试次数
- 超过阈值（如3次）触发回滚
- 简单有效

### 3.4 紧急恢复

即使双分区都损坏，仍需要恢复手段：

**串口/USB恢复**：
- 检测特定按键组合或GPIO
- 进入恢复模式，通过串口接收固件
- 类似"刷机模式"

**网络恢复**：
- Bootloader内置简化的网络栈
- 从固定服务器下载恢复固件
- 复杂但自动化程度高

## 四、安全机制

### 4.1 固件完整性

**CRC校验**：
- 简单快速，防止传输/存储错误
- 不能防止恶意篡改

**哈希校验**：
- SHA-256等密码学哈希
- 固件附带哈希值，下载后校验
- 哈希值本身需要安全传输

### 4.2 固件签名

签名是防止恶意固件的核心机制：

**原理**：
1. 开发者用私钥对固件哈希签名
2. 签名附加到固件包
3. 设备用公钥验证签名
4. 验证通过才允许升级

**算法选择**：
- RSA-2048/4096：成熟，计算量较大
- ECDSA P-256：同等安全性，签名更短
- Ed25519：高性能，推荐

**密钥管理**：
- 私钥绝对保密，离线存储
- 公钥烧录到设备，或存于安全区
- 考虑密钥轮换机制

### 4.3 安全启动链

完整的安全需要从Bootloader开始：

```
ROM Bootloader（不可修改）
      │
      │ 验证签名
      ▼
Second Bootloader
      │
      │ 验证签名
      ▼
Application
```

每一级验证下一级，形成信任链。根在于ROM中的不可修改代码和公钥。

### 4.4 传输安全

**HTTPS**：
- TLS加密传输
- 验证服务器证书
- 防止中间人攻击

**MQTT over TLS**：
- 类似HTTPS的安全保障
- 适合IoT场景

## 五、差分升级

### 5.1 为什么需要差分

**全量升级问题**：
- 固件100KB，每次下载100KB
- 带宽成本高
- 低速网络体验差

**差分升级**：
- 只下载新旧版本的差异
- 通常差分包仅为全量的10-30%
- 大幅减少流量和时间

### 5.2 差分算法

**bsdiff**：
- 广泛使用的二进制差分算法
- 生成patch文件
- 设备端需要足够RAM进行合并

**VCDIFF (RFC 3284)**：
- 标准化差分格式
- 流式处理，内存占用低

**商业方案**：
- Mender、Pelion等平台内置差分
- 优化的算法和工具链

### 5.3 差分升级挑战

**内存限制**：
- 合并过程需要缓存
- 可能需要分块处理

**兼容性**：
- 每个差分包只针对特定源版本
- 需要管理多版本差分包
- 或强制用户升级到最新版再差分

**恢复复杂**：
- 差分合并过程需要原子性保护
- 失败时的状态恢复更复杂

## 六、可靠性保障

### 6.1 断点续传

网络不稳定时，下载中断是常态：

**Range请求**：
- HTTP支持Range头指定下载范围
- 记录已下载位置
- 重连后从断点继续

**分块下载**：
- 将固件分成多个块
- 每块独立请求和校验
- 支持乱序和重试

### 6.2 重试策略

**指数退避**：
```
重试间隔 = min(base × 2^n + random, max_interval)
```
- 避免大量设备同时重试冲击服务器
- 随机因素分散请求

**重试限制**：
- 设置最大重试次数
- 持续失败需报告错误，人工介入

### 6.3 灰度发布

不要同时升级所有设备：

**分批策略**：
1. 内部测试设备（1%）
2. 早期用户组（5%）
3. 逐步扩大（20% → 50% → 100%）

**监控指标**：
- 升级成功率
- 设备在线率
- 异常报告数

**回滚决策**：
- 成功率低于阈值，暂停推送
- 发现严重问题，全量回滚

### 6.4 版本管理

**版本号设计**：
- 语义版本：MAJOR.MINOR.PATCH
- 构建号：持续递增，唯一标识

**兼容性检查**：
- 设备报告当前版本和硬件版本
- 服务器判断可升级的目标版本
- 防止不兼容固件下发

**强制升级**：
- 关键安全补丁可强制升级
- 旧版本拒绝服务，必须升级

## 七、实施建议

### 7.1 Flash空间规划

```
例：1MB Flash分配

Bootloader:   32KB  (固定，尽量小)
Slot A:       448KB (应用)
Slot B:       448KB (应用)
Config:       64KB  (配置数据)
OTA Meta:     8KB   (分区标志)

应用最大 = 448KB - 签名开销
```

### 7.2 开发阶段建议

**早期设计**：
- 预留足够Flash空间
- Bootloader独立开发，稳定后锁定
- 定义清晰的升级协议

**测试重点**：
- 断电测试：任意时刻断电不变砖
- 回滚测试：故意制造失败，验证回滚
- 边界测试：空间不足、网络中断

### 7.3 运维阶段建议

**监控**：
- 记录每次升级的详细日志
- 分析失败原因分布
- 监控设备健康度变化

**应急预案**：
- 准备回滚固件
- 明确回滚触发条件
- 演练回滚流程

## 总结

OTA升级设计的核心原则：

| 原则 | 要点 |
|-----|------|
| 永不变砖 | 双分区、回滚机制、恢复模式 |
| 安全第一 | 签名验证、安全启动链 |
| 可靠传输 | 断点续传、重试机制 |
| 渐进发布 | 灰度升级、监控回滚 |
| 版本管理 | 兼容性检查、强制升级策略 |

OTA是设备生命周期管理的关键能力，投入设计一个健壮的OTA系统，将在产品运营中持续受益。
