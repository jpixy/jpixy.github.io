# 数据中心网络架构详解

本文深入介绍现代数据中心网络架构，包括大二层/大三层概念、Spine-Leaf 架构、Overlay 网络技术等。

> **前置知识**：本文假设读者了解 MAC 地址、ARP、VLAN、STP 等二层网络基础。如需复习，请参阅：[二层三层网络基础详解](/articles/networking/net-00-二层三层网络基础详解/)

## 一、传统数据中心网络架构

### 1.1 经典三层架构

**定义**：传统数据中心采用 Core-Aggregation-Access 三层架构。

```
                    ┌─────────┐
                    │  Core   │  核心层：高速转发，连接外网
                    │ (L3路由) │
                    └────┬────┘
                         │
            ┌────────────┼────────────┐
            │            │            │
       ┌────┴────┐  ┌────┴────┐  ┌────┴────┐
       │  Agg 1  │  │  Agg 2  │  │  Agg 3  │  汇聚层：VLAN间路由，策略
       │ (L2/L3) │  │ (L2/L3) │  │ (L2/L3) │
       └────┬────┘  └────┬────┘  └────┬────┘
            │            │            │
       ┌────┴────┐  ┌────┴────┐  ┌────┴────┐
       │ Access  │  │ Access  │  │ Access  │  接入层：连接服务器
       │  (L2)   │  │  (L2)   │  │  (L2)   │
       └────┬────┘  └────┬────┘  └────┬────┘
            │            │            │
         服务器        服务器        服务器
```

### 1.2 传统架构的问题

| 问题 | 说明 |
|------|------|
| **STP 限制** | 生成树协议阻塞冗余链路，带宽利用率低 |
| **VLAN 数量** | 最多 4096 个 VLAN，大规模租户不够用 |
| **南北流量设计** | 设计针对南北向（客户端↔服务器），东西向（服务器↔服务器）效率低 |
| **VM 迁移困难** | 跨子网迁移需要改 IP，影响业务 |
| **扩展性差** | 增加设备时 STP 重新收敛，影响全网 |

```
南北向流量 (传统):           东西向流量 (云/AI):
                              
  客户端                      服务器 ←──→ 服务器
     │                            │
     ↓                            ↓
  ┌──────┐                   ┌──────────────┐
  │ Core │                   │ 大量横向通信  │
  └──────┘                   │ (分布式计算)  │
     │                       └──────────────┘
     ↓                       
  服务器                      
```

## 二、大二层网络 (Large Layer 2)

### 2.1 痛点：为什么传统二层网络不够用？

#### 痛点一：VLAN 只有 4096 个，为什么？

```
以太网帧结构（802.1Q）:
┌────────────┬────────────┬──────────────────┬────────┬──────┐
│  Dst MAC   │  Src MAC   │   802.1Q Tag     │  Type  │ Data │
│   6字节    │   6字节     │     4字节        │  2字节  │      │
└────────────┴────────────┴──────────────────┴────────┴──────┘
                                │
                                ↓
                ┌───────────────────────────────┐
                │ TPID(2B) │ PRI(3b) │ VLAN ID │
                │  0x8100  │  优先级  │  12 bit │
                └───────────────────────────────┘
                                        ↓
                               12 bit = 2^12 = 4096

答案：VLAN ID 只分配了 12 个 bit，所以最多 4096 个。
     这是 1998 年设计的，当时没想到云计算需要百万租户。
```

**4096 个够用吗？**

```
传统企业（2000年代）:           云计算时代:
┌─────────────────────┐        ┌─────────────────────┐
│ 研发部 VLAN 10      │        │ 租户A: 100个VLAN    │
│ 财务部 VLAN 20      │        │ 租户B: 50个VLAN     │
│ 销售部 VLAN 30      │        │ 租户C: 200个VLAN    │
│ ...                 │        │ ...                 │
│ 总共几十个部门      │        │ 1万个租户 × 平均50  │
│                     │        │ = 50万个VLAN需求    │
└─────────────────────┘        └─────────────────────┘
      够用 ✓                         严重不够 ✗
```

#### 痛点二：VM 热迁移为什么必须同一二层？

```
场景：VM 从物理机A迁移到物理机B

方案1：跨三层迁移（改IP）
┌────────────────────────────────────────────────────────────┐
│  迁移前: VM IP = 10.1.1.100                                │
│                                                            │
│  物理机A (10.1.1.0/24)  ──迁移→  物理机B (10.2.1.0/24)     │
│                                                            │
│  迁移后: VM 必须改成 10.2.1.x                               │
│                                                            │
│  问题:                                                      │
│  1. 所有客户端的连接断开（IP变了）                          │
│  2. DNS 记录需要更新                                        │
│  3. 防火墙规则需要修改                                      │
│  4. 负载均衡配置需要调整                                    │
│  5. 应用内硬编码的IP全部失效                                │
│                                                            │
│  结论: 业务中断，无法做到"热"迁移                          │
└────────────────────────────────────────────────────────────┘

方案2：同一二层迁移（保持IP）
┌────────────────────────────────────────────────────────────┐
│  迁移前后: VM IP = 10.1.1.100 （不变）                      │
│                                                            │
│  物理机A ─────────迁移─────────→ 物理机B                    │
│      │                              │                      │
│      └──────── 同一个二层网络 ───────┘                      │
│                                                            │
│  实现:                                                      │
│  1. IP 不变，连接不断                                       │
│  2. 客户端无感知                                            │
│  3. ARP 更新后流量自动切换到新位置                          │
│                                                            │
│  结论: 真正的热迁移 ✓                                       │
└────────────────────────────────────────────────────────────┘

技术原理：
同一二层 = 同一广播域 = ARP 可达 = MAC 直接通信

迁移时：
1. VM 内存状态复制到新物理机
2. 新位置发送免费 ARP（Gratuitous ARP）
3. 交换机更新 MAC 表：该 MAC 现在从新端口可达
4. 流量无缝切换，IP 层完全无感知
```

#### 痛点三：STP 的扩展性噩梦

```
为什么传统二层网络难以扩展？

                    ┌─────┐
                    │ Core│
                    └──┬──┘
               ┌──────┼──────┐
               │      │      │
            ┌──┴──┐ ┌─┴──┐ ┌─┴──┐
            │Agg1 │ │Agg2│ │Agg3│
            └──┬──┘ └─┬──┘ └─┬──┘
               │   ╲  │  ╱   │
               │    ╲ │ ╱    │
               │     ╲│╱     │
               │      ╳      │     ← 这些交叉连接形成环路
               │     ╱│╲     │
               │    ╱ │ ╲    │
               │   ╱  │  ╲   │
            ┌──┴──┐ ┌─┴──┐ ┌─┴──┐
            │Acc1 │ │Acc2│ │Acc3│
            └─────┘ └────┘ └────┘

STP 的问题：

1. 阻塞链路：为防止环路，STP 会阻塞冗余链路
   ┌─────────────────────────────────────────┐
   │  8条链路，STP阻塞4条 → 带宽浪费50%      │
   └─────────────────────────────────────────┘

2. 收敛慢：设备故障时，STP 重新计算需要 30-50 秒
   ┌─────────────────────────────────────────┐
   │  交换机故障 → 等待30秒 → 流量才恢复      │
   │  这对云服务是不可接受的                  │
   └─────────────────────────────────────────┘

3. 规模限制：STP 不建议超过 100 台交换机
   ┌─────────────────────────────────────────┐
   │  大型数据中心需要数千台交换机            │
   │  STP 根本无法支撑                        │
   └─────────────────────────────────────────┘
```

### 2.2 解决方案：大二层技术

**核心思路**：在三层网络上"虚拟"出二层网络，既有三层的扩展性，又有二层的语义。

```
                         ┌─────────────────────────────────────┐
                         │         Overlay（虚拟二层）          │
                         │  VM看到的：同一个二层，ARP可达       │
                         └─────────────────────────────────────┘
                                          ↑
                                     封装/解封装
                                          ↓
                         ┌─────────────────────────────────────┐
                         │       Underlay（物理三层）           │
                         │  实际是：纯IP路由，无STP，可扩展     │
                         └─────────────────────────────────────┘
```

### 2.3 VXLAN 深入剖析

#### 为什么是 VXLAN？

```
VXLAN 解决的核心问题:

┌─────────────────┬───────────────────┬───────────────────────────┐
│     问题        │    传统方案       │      VXLAN 方案           │
├─────────────────┼───────────────────┼───────────────────────────┤
│ VLAN 不够       │ 12位 = 4096      │ 24位 VNI = 1600万         │
│ STP 扩展性差    │ 二层环路问题      │ 底层是三层，无 STP        │
│ VM 跨机房迁移   │ 需要二层直连      │ 三层网络上虚拟二层        │
│ 多租户隔离      │ VLAN 划分，易耗尽  │ 每租户独立 VNI           │
└─────────────────┴───────────────────┴───────────────────────────┘
```

#### VXLAN 封装原理

```
原始以太网帧 (VM 发出):
┌──────────┬──────────┬──────────┬───────────────┐
│ Dst MAC  │ Src MAC  │   Type   │   Payload     │
│ (VM2的)  │ (VM1的)  │          │               │
└──────────┴──────────┴──────────┴───────────────┘
     ↓
     ↓ VTEP 封装
     ↓
VXLAN 封装后 (物理网络传输):
┌────────────────────────────────────────────────────────────────────────┐
│ 外层   │ 外层   │ 外层IP头      │ UDP    │ VXLAN  │ 原始以太网帧      │
│ DstMAC │ SrcMAC │ Src: VTEP1    │ Dst:   │ Header │                   │
│ (下一跳)│(VTEP1) │ Dst: VTEP2    │ 4789   │ VNI    │ (完整保留)        │
└────────────────────────────────────────────────────────────────────────┘
     │         │           │            │       │
     │         │           │            │       └─ 24位，标识虚拟网络
     │         │           │            └─ 标准端口，防火墙/NAT友好
     │         │           └─ 底层路由用这个转发
     │         └─ 物理网卡的MAC
     └─ 物理网络的下一跳MAC

MTU 问题:
原始帧 + VXLAN头(50字节) = 封装后大小
1500 + 50 = 1550

解决: 物理网络 MTU 需设为 1550+ (推荐 9000 Jumbo Frame)
```

#### 为什么选择 UDP 封装？

```
VXLAN 用 UDP 而非 TCP/GRE 的原因:

1. ECMP 负载均衡友好
   ┌─────────────────────────────────────────────────────────────┐
   │ 传统 GRE: 外层IP相同，无法做五元组Hash                       │
   │          所有流量走同一路径，负载不均                        │
   │                                                             │
   │ VXLAN UDP: 外层UDP端口可变，五元组Hash有效                   │
   │            VTEP 根据内层流量计算外层源端口                   │
   │            不同内层流→不同外层五元组→负载均衡                │
   └─────────────────────────────────────────────────────────────┘

2. 穿透 NAT 和防火墙
   ┌─────────────────────────────────────────────────────────────┐
   │ UDP 4789 是标准端口，容易配置防火墙规则                      │
   │ 比私有协议更容易穿透中间设备                                 │
   └─────────────────────────────────────────────────────────────┘

3. 无需可靠性保证
   ┌─────────────────────────────────────────────────────────────┐
   │ 内层已经有 TCP 保证可靠性，外层不需要重复保证                │
   │ UDP 开销更小，性能更好                                       │
   └─────────────────────────────────────────────────────────────┘
```

#### VXLAN 关键组件

| 概念 | 技术含义 | 类比理解 |
|------|----------|----------|
| **VNI** | 24位网络标识，1600万个 | 相当于"超级VLAN号" |
| **VTEP** | 封装/解封装的隧道端点 | 相当于"翻译官"，把二层翻译成三层 |
| **Underlay** | 底层物理IP网络 | 高速公路系统 |
| **Overlay** | 上层虚拟二层网络 | 公路上跑的"虚拟专线" |

```
实际部署架构:

                    Overlay (虚拟网络，VNI 1000)
  VM1 ─────────────────────────────────────────── VM2
  10.0.1.1                                       10.0.1.2
  MAC1                                           MAC2
    │                                              │
    │ 虚拟网卡                              虚拟网卡 │
    ↓                                              ↓
┌────────────────┐                      ┌────────────────┐
│   VTEP1        │                      │     VTEP2      │
│ (运行在Leaf上)  │                      │  (运行在Leaf上) │
│ Underlay IP:   │                      │ Underlay IP:   │
│ 192.168.1.1    │                      │ 192.168.1.2    │
└───────┬────────┘                      └───────┬────────┘
        │                                       │
        │        Underlay (物理网络)             │
        │     ┌─────────────────────┐           │
        └────►│  Spine-Leaf 路由    │◄──────────┘
              │  纯三层，ECMP负载均衡 │
              └─────────────────────┘
```

**VXLAN 配置示例 (Linux)**：

```bash
# 创建 VXLAN 接口
ip link add vxlan100 type vxlan id 100 \
    local 192.168.1.1 \
    remote 192.168.1.2 \
    dstport 4789 \
    dev eth0

# 启用接口
ip link set vxlan100 up

# 添加到网桥
ip link add br0 type bridge
ip link set vxlan100 master br0
ip link set br0 up

# 查看 VXLAN 信息
bridge fdb show dev vxlan100
ip -d link show vxlan100
```

## 三、大三层网络 (Routed Layer 3)

### 3.1 痛点回顾：为什么要抛弃二层？

```
传统三层架构的流量路径问题:

场景：同一机架内两台服务器通信（理想情况应该直接通信）

实际路径（传统三层）:
Server1 → Access → Aggregation → Core → Aggregation → Access → Server2
          ↑                    ↑
       二层交换             三层路由（网关在这里）

问题：
1. "发夹"流量：即使两台服务器挨着，也要绕到上层网关
2. 核心层成为瓶颈：所有东西向流量都经过核心
3. 延迟增加：多跳导致延迟累积
```

### 3.2 解决方案：Spine-Leaf 架构

**核心思想**：消除传统三层架构的层级瓶颈，实现无阻塞、低延迟的互联。

```
为什么叫 Clos 网络？

Charles Clos 在 1953 年提出的电话交换机拓扑理论:
┌─────────────────────────────────────────────────────────────────┐
│  核心原理：通过多级全互联，用廉价小交换机构建大容量无阻塞网络    │
│                                                                 │
│  传统思路：一台超大交换机（贵，有上限）                          │
│  Clos思路：多台小交换机全互联（便宜，可扩展）                    │
└─────────────────────────────────────────────────────────────────┘
```

```
              Spine 层 (脊)
        ┌─────┐         ┌─────┐
        │Spine│         │Spine│
        │  1  │         │  2  │
        └──┬──┘         └──┬──┘
           │╲             ╱│
           │ ╲           ╱ │
           │  ╲         ╱  │      全互联
           │   ╲       ╱   │      任意两个Leaf
           │    ╲     ╱    │      最多2跳可达
           │     ╲   ╱     │
           │      ╲ ╱      │
           │       ╳       │
           │      ╱ ╲      │
           │     ╱   ╲     │
           │    ╱     ╲    │
           │   ╱       ╲   │
        ┌──┴──┐       ┌──┴──┐
        │Leaf │       │Leaf │
        │  1  │       │  2  │      Leaf 层 (叶)
        └──┬──┘       └──┬──┘
           │              │
      ┌────┴────┐    ┌────┴────┐
      │ Server  │    │ Server  │
      │ Rack 1  │    │ Rack 2  │
      └─────────┘    └─────────┘
```

**Spine-Leaf 特点**：

| 特点 | 说明 |
|------|------|
| **无 STP** | 全三层路由，无需生成树 |
| **ECMP** | 等价多路径，所有链路同时使用 |
| **可预测延迟** | 任意两点最多 2 跳（Leaf→Spine→Leaf） |
| **水平扩展** | 增加 Spine/Leaf 即可扩容 |
| **东西向优化** | 适合服务器间大量横向通信 |

### 3.3 大三层 + Overlay

**现代主流方案：Spine-Leaf (Underlay) + VXLAN (Overlay) + BGP EVPN (控制面)**

```
┌────────────────────────────────────────────────────────────────┐
│                     Overlay (VXLAN)                            │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │  租户A VNI 1000      租户B VNI 2000      租户C VNI 3000  │  │
│  │  10.1.0.0/16         10.2.0.0/16         10.3.0.0/16     │  │
│  └─────────────────────────────────────────────────────────┘  │
│                              │                                 │
│                         VTEP 封装                              │
│                              ↓                                 │
├────────────────────────────────────────────────────────────────┤
│                    Underlay (Spine-Leaf)                       │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │              纯三层 IP 路由 (BGP/OSPF)                    │  │
│  │              Spine: 192.168.0.x                          │  │
│  │              Leaf:  192.168.1.x                          │  │
│  └─────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

## 四、BGP EVPN

### 4.1 痛点：VXLAN 的控制面问题

**VXLAN 只定义了数据面封装，但没有解决：谁在哪里？**

```
场景：VM1 (VTEP1) 想和 VM2 (VTEP2) 通信

┌────────────────────────────────────────────────────────────────────┐
│ 问题：VTEP1 不知道 VM2 的 MAC 地址在哪个 VTEP 后面               │
│                                                                    │
│ 方案1：数据面学习（泛洪）                                          │
│                                                                    │
│   VM1 发 ARP: "谁是 10.0.1.2?"                                    │
│        ↓                                                           │
│   VTEP1 封装后广播到所有 VTEP                                      │
│        ↓                                                           │
│   VTEP2, VTEP3, VTEP4... 都收到                                   │
│        ↓                                                           │
│   只有 VTEP2 有 VM2，回复 ARP                                      │
│        ↓                                                           │
│   VTEP1 学习到：VM2 的 MAC 在 VTEP2 后面                          │
│                                                                    │
│ 问题：                                                              │
│   1. 每次 ARP 都要泛洪，规模大了是广播风暴                         │
│   2. 1000 个 VTEP × 每秒 100 个 ARP = 10万 pps 广播开销            │
│   3. 完全不可扩展                                                   │
└────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────┐
│ 方案2：控制面分发（BGP EVPN）                                      │
│                                                                    │
│   1. VM2 启动时，VTEP2 通过 BGP 通告：                             │
│      "MAC2/IP2 在我这里（VTEP2）"                                  │
│                                                                    │
│   2. 所有 VTEP 收到路由，更新本地表：                              │
│      MAC2 → VTEP2 (192.168.1.2)                                   │
│                                                                    │
│   3. VM1 发 ARP 时：                                               │
│      VTEP1 直接代答（ARP Suppression），无需泛洪                   │
│                                                                    │
│   4. VM1 → VM2 通信时：                                            │
│      VTEP1 查表，直接封装发给 VTEP2，无广播                        │
│                                                                    │
│ 优点：零泛洪，可扩展到数万主机                                     │
└────────────────────────────────────────────────────────────────────┘
```

### 4.2 为什么选择 BGP？

```
控制面协议选择对比:

┌───────────────┬─────────────────────────────────────────────────────┐
│ 协议          │ 评估                                                │
├───────────────┼─────────────────────────────────────────────────────┤
│ 自定义协议    │ ✗ 需要重新开发，厂商不兼容                          │
├───────────────┼─────────────────────────────────────────────────────┤
│ OVSDB         │ △ OpenStack 用，但只适合 OVS 场景                   │
├───────────────┼─────────────────────────────────────────────────────┤
│ IS-IS         │ △ TRILL/SPB 用，但扩展性有限                        │
├───────────────┼─────────────────────────────────────────────────────┤
│ BGP           │ ✓ 互联网验证过的可扩展性（路由表百万级）            │
│               │ ✓ 成熟的 MP-BGP 扩展机制（Address Family）          │
│               │ ✓ 厂商广泛支持                                       │
│               │ ✓ 已有运维经验                                       │
└───────────────┴─────────────────────────────────────────────────────┘

BGP 的 Address Family 扩展:
- IPv4 Unicast      ← 传统路由
- IPv6 Unicast
- VPNv4             ← MPLS VPN
- L2VPN EVPN        ← VXLAN 控制面 ✓ 这个
```

### 4.3 EVPN 路由类型详解

| 类型 | 名称 | 用途 | 场景 |
|------|------|------|------|
| **Type-2** | MAC/IP | 通告主机的 MAC 和 IP | VM 上线时，通告"我在这" |
| **Type-3** | Inclusive Multicast | BUM 流量复制列表 | 哪些 VTEP 属于同一个 VNI |
| **Type-5** | IP Prefix | 通告子网前缀 | 跨 VNI 的三层路由 |
| Type-1 | Ethernet Auto-discovery | 多宿主冗余 | 双活接入场景 |
| Type-4 | Ethernet Segment | ES 选举 | 多宿主 DF 选举 |

### 4.3 BGP EVPN 工作流程

```
1. VM1 启动，VTEP1 学习到 MAC1/IP1

2. VTEP1 生成 Type-2 路由，通过 BGP 通告：
   ┌─────────────────────────────────────────────────┐
   │ Route Type: 2 (MAC/IP)                          │
   │ VNI: 1000                                       │
   │ MAC: aa:bb:cc:dd:ee:01                          │
   │ IP: 10.0.1.1                                    │
   │ Next Hop: 192.168.1.1 (VTEP1)                   │
   └─────────────────────────────────────────────────┘

3. 其他 VTEP 收到路由，更新转发表

4. VM2 → VM1 时，VTEP2 查表直接封装发送
   无需 ARP 广播
```

### 4.4 配置示例 (FRRouting)

```bash
# /etc/frr/frr.conf

router bgp 65001
 bgp router-id 192.168.1.1
 neighbor 192.168.0.1 remote-as 65000
 neighbor 192.168.0.1 update-source lo
 !
 address-family l2vpn evpn
  neighbor 192.168.0.1 activate
  advertise-all-vni
 exit-address-family
!
vni 1000
 rd 192.168.1.1:1000
 route-target import 65000:1000
 route-target export 65000:1000
```

## 五、Underlay 与 Overlay

### 5.1 概念区分

```
┌─────────────────────────────────────────────────────────────┐
│  Overlay (虚拟网络)                                          │
│  - 用户/租户看到的网络                                       │
│  - 可以重叠 IP 地址（不同租户可用相同 10.0.0.0/8）            │
│  - 技术：VXLAN、GRE、IPsec                                  │
│  - 控制面：BGP EVPN、OVSDB                                  │
└─────────────────────────────────────────────────────────────┘
                           ↑ 封装/解封装
┌─────────────────────────────────────────────────────────────┐
│  Underlay (物理网络)                                         │
│  - 底层物理互联                                              │
│  - 只需保证 VTEP 之间 IP 可达                                │
│  - 技术：纯 IP 路由 (BGP/OSPF/IS-IS)                        │
│  - 拓扑：Spine-Leaf                                         │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 为什么分离

| 好处 | 说明 |
|------|------|
| **解耦** | 上层虚拟网络变化不影响底层物理网络 |
| **简化** | Underlay 只需关心 IP 可达，配置简单 |
| **多租户** | 不同租户的 Overlay 完全隔离 |
| **灵活** | Overlay 可以跨越多个物理站点 |

### 5.3 完整数据流示例

```
VM1 (10.0.1.1, VNI 1000) → VM2 (10.0.1.2, VNI 1000)

┌─────────────────────────────────────────────────────────────────────────┐
│ 1. VM1 发送原始帧                                                        │
│    ┌──────────────────────────────────────────┐                         │
│    │ Dst: MAC2 │ Src: MAC1 │ IP: 10.0.1.1→.2 │                         │
│    └──────────────────────────────────────────┘                         │
│                          │                                               │
│                          ↓                                               │
│ 2. VTEP1 查 EVPN 路由表：MAC2 → VTEP2 (192.168.1.2)                      │
│                          │                                               │
│                          ↓                                               │
│ 3. VTEP1 封装 VXLAN                                                      │
│    ┌─────────────────────────────────────────────────────────────────┐  │
│    │外层MAC│外层IP: 192.168.1.1→.2│UDP:4789│VNI:1000│原始帧          │  │
│    └─────────────────────────────────────────────────────────────────┘  │
│                          │                                               │
│                          ↓                                               │
│ 4. Underlay 路由：VTEP1 → Spine → VTEP2                                  │
│                          │                                               │
│                          ↓                                               │
│ 5. VTEP2 解封装，转发原始帧给 VM2                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 六、关键技术补充

### 6.1 ECMP (Equal-Cost Multi-Path)

#### 痛点：链路利用率低

```
传统 STP 的问题:

     ┌─────┐
     │Core │
     └──┬──┘
   ┌────┴────┐
   │         │
┌──┴──┐   ┌──┴──┐
│Agg1 │───│Agg2 │    ← 这条链路被 STP 阻塞
└──┬──┘   └──┬──┘
   │    ╳    │        ╳ = 阻塞
   │         │
┌──┴──┐   ┌──┴──┐
│Acc1 │   │Acc2 │
└─────┘   └─────┘

结果：4条链路只用2条，浪费50%带宽
```

#### ECMP 解决方案

```
ECMP 让所有链路同时使用:

          ┌─────┐
          │Spine│
          └──┬──┘
     ┌───────┼───────┐
     │       │       │      
     ↓       ↓       ↓      路由表：到 10.0.0.0/8
  ┌─────┐ ┌─────┐ ┌─────┐     nexthop 1: Leaf1
  │Leaf1│ │Leaf2│ │Leaf3│     nexthop 2: Leaf2
  └─────┘ └─────┘ └─────┘     nexthop 3: Leaf3
                              权重：1:1:1
```

#### ECMP Hash 原理

```
为什么要 Hash？为什么不能轮询？

问题场景（轮询）:
┌─────────────────────────────────────────────────────────────────┐
│  TCP 连接的 3 个包:                                             │
│                                                                 │
│  包1 → 路径A (延迟 1ms)                                         │
│  包2 → 路径B (延迟 5ms)   ← 不同路径延迟不同                    │
│  包3 → 路径A (延迟 1ms)                                         │
│                                                                 │
│  到达顺序: 包1, 包3, 包2   ← 乱序！                             │
│  TCP 认为丢包，触发重传，性能暴跌                                │
└─────────────────────────────────────────────────────────────────┘

解决（Hash）:
┌─────────────────────────────────────────────────────────────────┐
│  Hash = f(SrcIP, DstIP, Protocol, SrcPort, DstPort)             │
│                                                                 │
│  同一个 TCP 连接的所有包，五元组相同，Hash 值相同               │
│  → 走同一路径 → 不会乱序                                        │
│                                                                 │
│  不同连接，五元组不同，Hash 值不同                              │
│  → 走不同路径 → 负载均衡                                        │
└─────────────────────────────────────────────────────────────────┘

ECMP Hash 的坑:
┌─────────────────────────────────────────────────────────────────┐
│  问题：如果只有一个大流（大象流），Hash 无法分散                 │
│                                                                 │
│  例如：1个 100Gbps 的大文件传输                                 │
│       五元组固定 → 只走一条路径 → 其他路径空闲                  │
│                                                                 │
│  解决：Flowlet / 自适应路由 / 应用层多连接                      │
└─────────────────────────────────────────────────────────────────┘
```

### 6.2 MLAG / VPC (多机箱链路聚合)

#### 痛点：服务器单点故障

```
传统单上行:

     ┌─────┐
     │Leaf │
     └──┬──┘
        │        ← 这条线断了，服务器断网
        │
   ┌────┴────┐
   │ Server  │
   └─────────┘

双上行 + STP:

   ┌─────┐     ┌─────┐
   │Leaf1│     │Leaf2│
   └──┬──┘     └──┬──┘
      │     ╳     │      ← STP 阻塞一条，还是只有单活
      │           │
   ┌──┴───────────┴──┐
   │     Server      │
   └─────────────────┘
```

#### MLAG 解决方案

```
MLAG 让两台交换机"假装"是一台:

               ┌─────┐     ┌─────┐
               │Spine│     │Spine│
               └──┬──┘     └──┬──┘
                  │           │
        ┌─────────┴───────────┴─────────┐
        │                               │
   ┌────┴────┐    Peer Link        ┌────┴────┐
   │ Leaf 1  │◄════════════════════►│ Leaf 2  │
   │         │   (控制面同步)       │         │
   │  MLAG   │   (数据面备份)       │  MLAG   │
   │ Member  │                      │ Member  │
   └────┬────┘                      └────┬────┘
        │                               │
        └──────────┬────────────────────┘
                   │ LACP Bond (服务器看到是一个链路)
              ┌────┴────┐
              │ Server  │
              └─────────┘

工作原理:
1. Peer Link 同步 MAC 表、ARP 表、LACP 状态
2. 服务器配置 Bond（LACP），看到两条线是一个逻辑链路
3. 两条线同时转发（Active-Active），带宽翻倍
4. 任一 Leaf 故障，另一台接管，服务器无感知

厂商实现:
┌──────────────┬────────────────┐
│ 厂商          │ 名称           │
├──────────────┼────────────────┤
│ Cisco        │ vPC            │
│ Arista       │ MLAG           │
│ Juniper      │ MC-LAG         │
│ 华为         │ M-LAG          │
│ 开源         │ Linux Bonding  │
└──────────────┴────────────────┘
```

### 6.3 Anycast Gateway (分布式网关)

#### 痛点：集中式网关的瓶颈

```
场景：VM1 (Leaf1) 访问 VM2 (Leaf2)，但它们在不同子网

传统集中式网关:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  VM1 (10.1.1.1) ──┐                    ┌── VM2 (10.2.1.1)      │
│                   │                    │                        │
│              ┌────┴────┐          ┌────┴────┐                  │
│              │ Leaf 1  │          │ Leaf 2  │                  │
│              └────┬────┘          └────┬────┘                  │
│                   │                    │                        │
│                   └────────┬───────────┘                        │
│                            │                                    │
│                       ┌────┴────┐                               │
│                       │   GW    │  ← 集中式网关                 │
│                       │10.1.1.254│    所有跨子网流量都经过这里   │
│                       │10.2.1.254│                               │
│                       └─────────┘                               │
│                                                                 │
│  流量路径: VM1 → Leaf1 → GW → Leaf2 → VM2                       │
│           (绕了一大圈)                                          │
│                                                                 │
│  问题:                                                          │
│  1. 网关成为性能瓶颈                                            │
│  2. 流量"发夹"，延迟增加                                       │
│  3. 网关故障 = 全网故障                                         │
└─────────────────────────────────────────────────────────────────┘
```

#### Anycast Gateway 解决方案

```
分布式网关 (每个 Leaf 都是网关):
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  VM1 (10.1.1.1)                        VM2 (10.2.1.1)          │
│       │                                      │                  │
│       │ GW: 10.1.1.254                      │ GW: 10.2.1.254   │
│       │ (本地就是网关!)                      │ (本地就是网关!)  │
│       ↓                                      ↓                  │
│  ┌─────────┐                            ┌─────────┐            │
│  │ Leaf 1  │                            │ Leaf 2  │            │
│  │ GW: .254│ ─────── Spine ─────────── │ GW: .254│            │
│  │ MAC:同一│                            │ MAC:同一│            │
│  └─────────┘                            └─────────┘            │
│                                                                 │
│  流量路径: VM1 → Leaf1(路由) → Spine → Leaf2 → VM2             │
│           (最短路径，无发夹)                                    │
│                                                                 │
│  关键配置: 所有 Leaf 配置相同的网关 IP 和 MAC                   │
│           GW IP: 10.1.1.254, 10.2.1.254, ...                   │
│           GW MAC: 00:00:5e:00:01:01 (全网统一)                  │
│                                                                 │
│  为什么能工作?                                                  │
│  1. VM 只和本地 Leaf 通信（ARP 解析到本地）                     │
│  2. Leaf 收到跨子网包后，查路由表，直接三层转发                 │
│  3. 对端 Leaf 解封装后，用相同的网关 MAC 发给目标 VM            │
└─────────────────────────────────────────────────────────────────┘

优点总结:
┌────────────────┬─────────────────────────────────────────────┐
│ 集中式网关     │ 分布式 Anycast Gateway                      │
├────────────────┼─────────────────────────────────────────────┤
│ 单点瓶颈       │ 负载分散到所有 Leaf                         │
│ 发夹流量       │ 最优路径                                     │
│ 单点故障       │ 任一 Leaf 故障不影响其他                    │
│ 延迟高         │ 本地路由，延迟低                             │
└────────────────┴─────────────────────────────────────────────┘
```

### 6.4 ARP Suppression

**定义**：VTEP 本地代答 ARP，避免广播泛洪。

```
无 ARP Suppression:           有 ARP Suppression:

VM1: Who has 10.0.1.2?         VM1: Who has 10.0.1.2?
      ↓                              ↓
   广播到所有 VTEP               VTEP1 查 EVPN 表
      ↓                              ↓
   大量 BUM 流量                 本地代答：10.0.1.2 is MAC2
                                     ↓
                                  无广播
```

### 6.5 VRF (Virtual Routing and Forwarding)

**定义**：虚拟路由实例，实现路由表隔离，不同租户可用相同 IP。

```
┌───────────────────────────────────────────────────────────┐
│                      物理交换机                            │
│                                                           │
│   ┌─────────────┐      ┌─────────────┐                   │
│   │   VRF-A     │      │   VRF-B     │                   │
│   │ 租户A路由表  │      │ 租户B路由表  │    相互隔离       │
│   │ 10.0.0.0/8  │      │ 10.0.0.0/8  │    IP可重叠       │
│   └─────────────┘      └─────────────┘                   │
└───────────────────────────────────────────────────────────┘
```

### 6.6 BFD (Bidirectional Forwarding Detection)

**定义**：毫秒级故障检测协议，快速发现链路/邻居故障。

```bash
# 典型配置
BFD 间隔: 100ms
检测倍数: 3
故障检测时间: 300ms (vs OSPF 默认 40秒)
```

## 八、SDN 与数据中心网络

### 8.1 SDN 架构

**一句话：SDN 将网络的控制面从设备中抽离，集中到控制器统一管理**

```
传统网络:                       SDN:

┌───────┐  ┌───────┐           ┌──────────────────┐
│ Switch│  │ Switch│           │   SDN Controller │ ← 控制面集中
```

## 九、AI/GPU 集群网络

### 9.1 AI 训练网络需求

| 需求 | 说明 |
|------|------|
| **超高带宽** | 梯度同步需要 100-400 Gbps |
| **超低延迟** | 集合通信对延迟敏感 |
| **无阻塞** | 全互联带宽 |
| **大规模** | 数千 GPU 互联 |

### 9.2 典型架构

```
                    AI 集群网络架构

┌─────────────────────────────────────────────────────────────┐
│                      存储网络                                │

└─────────────────────────────────────────────────────────────┘
                           │

│                   (SSH/监控/API)                             │

└─────────────────────────────────────────────────────────────┘
                           │
┌─────────────────────────────────────────────────────────────┐
│                    计算/训练网络                             │
│              InfiniBand (200-400 Gbps) 或                   │
│              RoCE v2 (100-400 Gbps)                         │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              Fat-Tree / Rail-Only 拓扑               │   │
│  │                                                      │   │

│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### 9.3 Rail-Optimized 拓扑

**定义**：针对 GPU 间通信模式优化的拓扑，每个 Rail（轨道）连接所有节点的对应 GPU。

```
传统 Fat-Tree:              Rail-Optimized:

所有 GPU 共享同一网络         每个 GPU 位置有独立 "Rail"
带宽竞争                      同位置 GPU 通信无阻塞

Node1: GPU0 GPU1 GPU2 ...    Rail0 ─ GPU0 ─ GPU0 ─ GPU0 (所有Node的GPU0)
Node2: GPU0 GPU1 GPU2 ...    Rail1 ─ GPU1 ─ GPU1 ─ GPU1 (所有Node的GPU1)
Node3: GPU0 GPU1 GPU2 ...    Rail2 ─ GPU2 ─ GPU2 ─ GPU2 ...
        ↓                          ↓
      共享交换机                 独立交换机
```

## 十、网络虚拟化技术

### 10.1 Open vSwitch (OVS)

**定义**：软件实现的多层虚拟交换机，支持 OpenFlow。

```bash
# 创建 OVS 网桥
ovs-vsctl add-br br0

# 添加端口
ovs-vsctl add-port br0 eth0
ovs-vsctl add-port br0 vxlan0 -- set interface vxlan0 \
    type=vxlan options:remote_ip=192.168.1.2

# 查看信息
ovs-vsctl show
ovs-ofctl dump-flows br0

# VXLAN + OVS
ovs-vsctl add-port br0 vxlan100 -- set interface vxlan100 \
    type=vxlan \
    options:key=100 \
    options:remote_ip=192.168.1.2
```

### 10.2 Linux Bridge vs OVS

| 特性 | Linux Bridge | Open vSwitch |
|------|--------------|--------------|
| 复杂度 | 简单 | 复杂 |
| 功能 | 基础二层 | 丰富（OpenFlow、隧道等） |
| 性能 | 原生 | 接近原生（DPDK 加速） |
| 管理 | ip/brctl | ovs-vsctl |
| 适用 | 简单场景 | 云平台/SDN |

### 10.3 SR-IOV

**定义**：Single Root I/O Virtualization，让网卡硬件虚拟化出多个虚拟网卡，直通给 VM/容器。

```
传统虚拟网络:                  SR-IOV:

  VM1      VM2                  VM1      VM2
   │        │                    │        │
   ↓        ↓                    │        │
┌──────────────┐                 │        │
│   vSwitch    │ ← CPU处理       │        │
└──────┬───────┘                 │        │
       │                         ↓        ↓
   ┌───┴───┐                ┌─────────────────┐
   │  NIC  │                │   SR-IOV NIC    │
   └───────┘                │  VF1   VF2  PF  │ ← 硬件虚拟化
                            └─────────────────┘
                            
性能：                       性能：
  VM → vSwitch → NIC          VM → VF → Wire
  延迟高，CPU开销大            接近裸机性能
```

```bash
# 启用 SR-IOV
echo 4 > /sys/class/net/eth0/device/sriov_numvfs

# 查看 VF
ip link show eth0

# 绑定 VF 到 VM (libvirt)
<interface type='hostdev'>
  <source>
    <address type='pci' domain='0x0000' bus='0x03' slot='0x10' function='0x0'/>
  </source>
</interface>
```

## 十一、常用命令与排查

### 11.1 VXLAN 调试

```bash
# 查看 VXLAN 接口详情
ip -d link show vxlan100

# 查看 FDB 表（MAC → VTEP 映射）
bridge fdb show dev vxlan100

# 抓取 VXLAN 流量
tcpdump -i eth0 port 4789 -nn

# 查看 VXLAN 统计
ip -s link show vxlan100
```

### 11.2 BGP EVPN 调试

```bash
# FRRouting
vtysh -c "show bgp l2vpn evpn"
vtysh -c "show bgp l2vpn evpn route type macip"
vtysh -c "show evpn vni"
vtysh -c "show evpn mac vni 1000"

# 查看路由表
ip route show vrf vrf1
```

### 11.3 OVS 调试

```bash
# 查看流表
ovs-ofctl dump-flows br0

# 追踪包路径
ovs-appctl ofproto/trace br0 in_port=1,dl_dst=aa:bb:cc:dd:ee:ff

# 查看端口统计
ovs-ofctl dump-ports br0

# 日志
ovs-appctl vlog/set dpif:dbg
```

### 11.4 Underlay 路由调试

```bash
# BGP 状态
vtysh -c "show bgp summary"
vtysh -c "show ip bgp"
vtysh -c "show ip route"

# OSPF 状态
vtysh -c "show ip ospf neighbor"
vtysh -c "show ip ospf route"

# BFD 状态
vtysh -c "show bfd peers"

# ECMP 验证
ip route show | grep nexthop
```

### 11.5 常见故障排查

| 故障现象 | 可能原因 | 排查命令 |
|----------|----------|----------|
| VM 间不通 | VNI 不匹配 | `ip -d link show vxlan*` |
| VTEP 不通 | Underlay 路由问题 | `ping <remote_vtep>`, `traceroute` |
| MAC 学习慢 | EVPN 未同步 | `show bgp l2vpn evpn` |
| 单向通信 | ARP/MAC 未学习 | `bridge fdb show` |
| 性能差 | MTU 问题 (需 ≥1550) | `ip link show`, 抓包看分片 |
